> 依据：`1004推进文档/01_数据合成管线`、`1004推进文档/02_模块功能与输入输出示例`、现有 `new_demo/` 代码、
> `1007推进文档/对齐09_一次性调度与持久化调度`、`1007推进文档/对齐15_目前方案与交付接口`，
> 以及 `simuprocject` 里 SimuHome 的时间机制分析。
> 定位：这是新方案的总体讨论，讲清"加什么任务、各模块怎么变、数据管线怎么跟着走"。
> 只讨论方向与边界，不写实现细节；例子用来把边界讲清楚，不当作最终数据集。

## 0 一屏

```text
这一版要加两族任务：
  TC6 时间调度   绝对时间一次性 + 相对时间一次性（持久化规则不做）
  TC7 记忆       1) 读预写记忆（单轮）
                 2) 单轮内读写记忆
                 3) 多轮交互，轮与轮之间不 reset

三条工作线：
  任务定义    TC6/TC7 每个子类的成功标准与边界例子
  仿真器      既要支持这两族任务，也要保持通用支持能力
  数据管线    跟着任务走：模板 → 任务 → 成功轨迹 → 评测集

一句话判断：
  环境加的是四个通用原语——时钟、一次性调度、记忆、会话；
  "绝对还是相对""读到还是写对"这些任务差异，留在数据层与判定层，
  不要为每个子类各写一套环境接口。
```

## 1 先看现在的家底

现在的任务族是 T1~T5（单设备控制、多设备控制、模糊意图、危险拒绝、环境查询），数据管线是 D0~D6 主链，ABCD 四个模块各管一段：

```text
A_policy           多轮里一次输出一个 JSON 工具调用，最多 10 步，finish 结束
B_home_env         只执行 4 个家庭工具：observe_home / inspect_room /
                   inspect_device / execute_action；finish 不归它管
C_episode_runner   一次 episode 一次 reset，一个用户请求，10 轮交互上限
C_episode_evaluator C-1..C-4 程序判定 + D6 语义三票（只审 T3/T4/T5）
D 管线             D0 静态库 → D1 造家 → D2 写 task / 写用户话 → D3 审话
                   → D4 Oracle 验可行 → D5 跑轨迹 → D6 复核 → 进数据集
```

对照这一版要加的东西，缺口很清楚：

```text
能力            现在                      缺什么
时间            只能读当前时间             没有时间推进，没有到点执行，没有相对时间
预约            没有                       一次性预约单的写 / 查 / 取消
记忆            没有                       跨步骤、跨轮保留的文本记忆
会话            一个请求一个 episode       多个用户请求共享一个不 reset 的环境
评测            即时设备控制 + 查询        调度是否正确、记忆是否被正确使用
数据形态        单请求轨迹                 带时钟事件、预约单、记忆快照、轮次的轨迹
```

## 2 TC6 时间调度怎么定义

### 2.1 绝对时间调度

例子：现在是 10 月 8 日 09:30，用户说"今晚 10 点把客厅灯关掉"。

```text
模型应该做的：
  1) inspect_time                → now = 2026-10-08 09:30
  2) 算目标时刻                  → 今晚 10 点 = 2026-10-08 22:00
  3) time_control.schedule       → at=2026-10-08 22:00,
                                   steps=[{客厅灯, turn_off}]
  4) finish completed            → summary 说明已预约

到点之后（不是模型做，是环境做）：
  22:00 环境执行 steps → 客厅灯 on 从 true 变 false
  list 里这张单从 pending 变 done
```

成功标准天然分两段：**下单正确**（时刻算对、动作写对、订单真的建立）和**到点执行正确**（设备确实变化、只执行一次）。这两段要分别记分，后面第 6 节展开。

### 2.2 相对时间调度

例子：当前 09:30，用户说"40 分钟后把加湿器关掉"。

```text
  inspect_time → 09:30 → 加 40 分钟 → 10:10 → schedule(at=10:10, steps=[关加湿器])

变体：
  "再过半小时"      → +30 分钟
  "一个小时以后"    → +60 分钟
  "等我睡醒以后"    → 模糊，不属于本版范围（无法自动判定）
```

相对时间和绝对时间**不是两个工具**，差别只在"at 怎么算出来"：绝对时间是读时钟 + 填时刻，相对时间是读时钟 + 做一次加法。工具面完全一样，这样可以复用 15 号文档已经定好的 `time_control.schedule`。

### 2.3 边界与歧义（建议都变成独立评测点）

```text
"今晚 10 点关灯"    一次性，TC6-A
"每晚 10 点关灯"    持久化规则，本版不做 → 模型应识别为超出范围
"10 分钟后关灯"     一次性，TC6-B
"过去时间"          例如现在 10:00 却写 09:00 → INVALID_TIME
"超过 7 天"         15 号文档已定义为 INVALID_TIME
"过一会儿"          无明确数值 → 本版不收录，或收成"拒绝模糊时间"的负例
```

## 3 TC7 记忆怎么定义

记忆服务的形态已由 15 号文档定死：整段文本、读原文 / 整段替换写入、写不超过 200 token、读超 300 token 截断。三小类任务的差别不在工具，而在**记忆是谁写的、什么时候写、环境要不要 reset**。

### 3.1 类一：读预写记忆（单轮）

```text
环境预置记忆："用户对花粉过敏，不要开窗"
用户请求："把卧室空气弄舒服点"

期望轨迹：
  memory.read → 看到花粉过敏
  inspect_room / inspect_device → 开空调或净化设备
  execute_action → 不碰窗户，不执行开窗
  finish completed

考的是：读记忆 + 把记忆变成约束；写不写记忆不是重点。
```

### 3.2 类二：单轮内读写记忆

```text
环境记忆为空
用户请求："记住：我睡觉要关客厅灯；顺便把卧室灯调暗一点"

期望轨迹：
  memory.write("睡觉时要关客厅灯")     ← 先写
  memory.read                          ← 回读确认（可选）
  inspect_device / execute_action      ← 执行调暗（真正的动作）
  finish completed

考的是：识别"哪句话是要记住的、哪句话是要做的"，写得准、不把记忆当动作。

反面例子：把"关客厅灯"当成现在就要执行的动作 → 错；
         记忆里写进用户没说的内容（例如自己补"还要关卧室灯"）→ 错。
```

### 3.3 类三：多轮交互（轮与轮之间不 reset）

```text
一个会话 3 轮，B 不 reset，记忆跨轮保留：

第 1 轮   用户："记住：我睡觉要关客厅灯"
          模型：memory.write → finish

第 2 轮   用户："我要睡了"
          模型：memory.read → 关客厅灯 → finish

第 3 轮   用户："客厅灯关了吗？"
          模型：inspect_device → 如实回答 → finish

考的是：跨轮记忆保留、环境状态延续、每一轮仍然守协议（一次一个 JSON）。
```

### 3.4 三小类对照

```text
项目            类1 读预写          类2 单轮读写        类3 多轮不reset
用户轮数        1                   1                   2~3
记忆谁写        数据预置            模型写              模型写
环境 reset      每 episode reset    每 episode reset     会话内不 reset
核心考察        读取并遵守          识别+写准+不误执行   跨轮保留+延续使用
判定重点        行为符合记忆约束    记忆内容准确        第2轮是否用上第1轮的记忆
```

### 3.5 记忆的生命周期（需要在环境层定死）

```text
写入时机    模型通过 memory.write；数据侧也可以预置（类1）
保留范围    建议按"会话"保留：单轮任务 = 一个会话；多轮任务 = 整个会话
清空时机    episode / 会话结束时清理，防跨任务串味（类比 schedules.db 的隔离问题）
容量        15 号文档：写 200 token 上限、读 300 token 截断；多轮连续写入会撞上限，
            需要定义"覆盖还是拒绝"的策略
```

## 5 仿真器改造：任务支持 + 综合支持

### 5.1 四个通用原语

```text
时钟      读 now，可区分 real / virtual；harness 可推进，模型只能读
调度器    一次性预约单：写 / 查 / 取消；到点执行与 execute_action 共内核
记忆      整段文本读 / 写；per 会话生命周期
会话      多轮共享一个不 reset 的环境与记忆
```

任务族只是这些原语的组合：TC6 = 时钟 + 调度器；TC7 类1 = 记忆（预置）；类2 = 记忆（写）；类3 = 记忆 + 会话。这样新增任务不需要新增环境接口，仿真器保持"综合支持"。

### 5.2 逻辑时钟与快进（参考 SimuHome）

SimuHome 的时间机制值得直接借鉴：它用 tick 离散时间，`get_current_time` 读虚拟时间，`schedule_workflow` 把绝对时间换算成 due_tick 放进调度队列，`fast_forward_to` 一跳走到目标 tick，还有 `run_workflow_now` 立即执行。

放到我们的 TC6 上，训练时验证"到点执行"有两条路：

```text
方案 A（有快进）  下单 → harness 快进到 due → 检查设备变化 → 记两段分
方案 B（无快进）  下单只算"下单成功"；到点执行另外由环境离线验证

建议：训练/评测默认用 A 的虚拟时钟版本；B 只作为没有快进能力时的兜底。
注意 15 号文档写明"模型不能快进、没有 advance"——快进是 harness 能力，
不给模型，避免模型学会"跳过等待"这种作弊行为。
```

### 5.3 预约单的生命周期

```text
创建     schedule(at, steps) → pending
查询     list → pending / done / cancelled
取消     cancel → cancelled，到点不执行
到点     执行 steps；某步失败记录该步，继续执行剩余步骤（T2 口径）
结束     episode / 会话结束清理，绝不带到下一个任务
```

### 5.4 与 MCP v2 的对接建议

```text
如果直接用 MCP v2 当训练环境：
  工具面      observe_home / inspect_room / inspect_device / execute_action /
              finish / inspect_time / time_control / memory（8 个）
  要确认      clock=virtual 时谁负责推进（模型不能推进，harness 用什么接口）
  要确认      schedules.db 与 memory 文件的 per-episode 清理由谁做
  要适配      observe_home 输出还是 rooms 字典，与数据合成端的 rooms 列表不统一

如果先用本地 B 模块模拟：
  好处    轨迹格式、状态字段、错误码都在我们手里，改起来快
  代价    后面接 MCP v2 时要再做一次接口对齐
```

## 6 ABCD 各自怎么调

### A：提示词与策略

```text
工具面      从现在的 4+finish 扩到 8 个（新增 inspect_time / time_control / memory）
新增两节    时间调度：先 inspect_time，再算 at；绝对/相对各给完整例子
            记忆：什么时候读、什么时候写、写了不确认不算完成
finish 语义 调度任务里 finish 表示"下单完成"还是"到点执行完成"，必须定义清楚
多轮协议    会话内每一轮仍然"一次一个 JSON、等 observation、再下一个"
边界例子    今晚10点 vs 每晚10点；过去时间；模糊相对时间
```

### B：环境与仿真器

```text
新增原语    时钟、一次性调度、记忆（见第 5 节）
会话模式    reset 只发生在会话开始；会话内多轮共享环境与记忆
清理        每个会话结束清 schedules / memory，防跨任务污染
数据模型    Scenario 需要能表达：预置记忆、多轮用户请求、调度型任务的期望
            （TaskSpec / EpisodeConfig 要不要加字段，属于实现细节，先记方向）
```

### C：判定与 runner

```text
runner      从"一个请求一个 episode"扩成"一个会话多个请求"；
            轮与轮之间只 reset 一次；期间保留 B 的状态与记忆
TC6 判定    两段计分：下单（at 换算正确、steps 正确、单建立）
            + 到点执行（设备变化、只执行一次、取消生效）
TC7 判定    类1：行为是否符合预置记忆
            类2：记忆内容是否准确 + 是否把记忆误当动作
            类3：第 2 轮是否用上第 1 轮写的记忆；第 3 轮回答是否与真实状态一致
污染检查    会话结束后记忆/预约是否清干净；跨任务是否串味
评测集      新增 TC6/TC7 评测集，保留 T1~T5 当锚点
```

### D：数据管线

```text
原则    数据管线跟着任务走：新任务族在 D0 加模板、D2 加字段、D4 加验证、
        D5 加轨迹形态、D6 加判定，主链结构不变
D0      新增 TC6/TC7 的任务模板与示例记忆/预约场景
D1      家里的初始状态不变；新增"基准时间"与"预置记忆"两个可选输入
D2-1    隐藏 task 需要表达：任务子类、绝对/相对时间、steps、预置记忆内容、会话轮次
D2-2    用户话要自然：相对时间用"40 分钟后""半小时后"这类口语，不写死时刻
D3      审查重点从"泄露 task"扩展到"不泄露答案时刻/不泄露该用哪条记忆"
D4      Oracle 要能做：写预约单 + 快进到点 + 验证设备变化；
        记忆类要验证"按预置记忆执行是可行的"
D5      轨迹新增字段：clock / schedule_id / at / memory 快照 / session_id / turn_index
D6      TC6 大多是规则可验证，可不走语义三票；TC7 的 summary 是否违背记忆需要复核
数据集  新增任务族字段与分账本（每条轨迹属于哪个子类、几段分）
```

## 7 两个完整的例子（从 D0 到数据集）

### 7.1 TC6 相对时间任务

```text
D0  模板：TC6-relative
D1  造家：客厅有 main_light，加湿器在卧室
D2  task：{子类: relative, 偏移: 40min, steps: [{加湿器, turn_off}]}
    用户话："40 分钟后把加湿器关掉"
D3  审查：没有泄露"10:10"，没有说错设备
D4  Oracle：注册预约 → 快进到点 → 加湿器确实关闭 → 可执行
D5  轨迹：inspect_time → 算 10:10 → schedule → finish
D6  规则判定：at 是否等于 now+40min；到点后状态是否变化
数据集字段：task_class=TC6-relative, schedule_id, at, verified, 两段得分
```

### 7.2 TC7 多轮会话任务

```text
D0  模板：TC7-session
D1  造家：客厅灯初始开着
D2  task：{子类: 多轮, 轮次: [写记忆, 用记忆, 查状态], 记忆内容: "睡觉要关客厅灯"}
    用户话（三轮）："记住：我睡觉要关客厅灯" / "我要睡了" / "客厅灯关了吗"
D3  审查：第 1 轮不泄露第 2 轮要做什么；三轮都自然
D4  Oracle：按记忆内容执行 → 关灯成功 → 可执行
D5  轨迹：轮1 write；轮2 read + execute；轮3 inspect + 回答（同一个 session，不 reset）
D6  复核：第 2 轮是否真的读了记忆；summary 是否与状态一致
数据集字段：session_id, turn_index, memory_before/after
```

## 11 例子小抄（一页）

