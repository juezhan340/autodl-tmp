# 02 时间机制方案对比：照搬 Home 的 tick 内核 vs 静止时间

> 依据：`1004推进文档/02_模块功能与输入输出示例`（B/C 现状）、`对齐_一次性调度与持久化调度`、
> `对齐_目前方案与交付接口`（v2）、`simuprocject` 的 SimuHome 时间机制分析，以及当前 `new_demo` 代码。
> 定位：只讨论时间机制本身，不写实现细节；用同一个任务把两种方案各走一遍。

## 0 一屏

```text
两种方案的本质区别：时间是不是一个"会自己走"的系统。

方案一 照搬 Home   时间会走：逻辑时钟 + 推进机制 + 事件队列 + 到点执行。
                   它是一个内核，和状态演化、调度、episode 生命周期绑在一起。

方案二 静止时间    时间不动：now 全程固定；预约单只写不跑；
                   校验时用"影子执行"把 steps 在一个状态副本上走一遍，
                   看"如果到点执行，会不会变成期望的样子"。

本期推荐：方案二（静止时间 + 影子执行 + 到点状态快照）。
理由一句话：TC6 要考的是"读时间、算时间、把单写对"，
这三件事在静止时间下全部可测；内核多出来的能力（执行时冲突、连续物理过程）
本期任务用不上，但成本是全链路的。

代价数量级：
  实现   方案一：B 新增时钟/推进/事件队列/调度引擎等 5 类组件，C 改两阶段
          方案二：B 加一个预约单存储 + 一个校验器，C 加一个 TC6 判定
  数据   方案一：Oracle 要跑时间内核，轨迹加 tick/事件
          方案二：Oracle 静态校验 + 影子执行，轨迹格式基本不变
  训练   方案一：rollout 要带时间推进（连续 tick 时成本随 tick 数增长）
          方案二：rollout 成本和现在一样
  评测   方案一：能测执行时刻的掉线/冲突/顺序
  方案二：默认测不了；加"到点状态快照"后大部分可测，成本仍然很低
```

## 1 同一个任务，两种方案各走一遍

任务：现在是 10 月 8 日 09:30，用户说"40 分钟后把加湿器关掉"。

### 方案一（时间会走）

```text
1) 模型 inspect_time        → 09:30
2) 模型算 10:10，写单        → schedule(at=10:10, steps=[关加湿器])
3) 环境把单换成 due_tick 放进事件队列
4) harness 推进时间（快进到 10:10 或逐 tick 走）
5) 到点：调度器取单 → 执行 steps → 加湿器 off
6) 需要的话模型再 inspect_device 查结果，或者由 harness 直接判分

episode 里真的发生了"时间流逝"；期间环境可能自己变化
（温度漂移、别的预约到点、设备掉线）。
```

### 方案二（时间不动）

```text
1) 模型 inspect_time        → 09:30（全程都是 09:30）
2) 模型算 10:10，写单        → schedule(at=10:10, steps=[关加湿器])
3) 环境只做三件事：
     a. 校验 at：未来时间、不超过 7 天、分钟级
     b. 校验 steps：设备存在、动作支持、参数在范围（和 execute_action 同一套闸门）
     c. 影子执行：把 steps 在一个状态副本上应用一次，得到"到点后的状态"
4) 判定：单子合法 + 影子结果符合目标 → 这条预约记成功
5) 模型 finish

时间始终停在 09:30；没有任何东西"到点"。
```

关键差别：方案一是"跑一遍未来"，方案二是"把未来在纸上推演一遍"。

## 2 方案一：照搬 Home 需要做什么

### 2.1 内核组件

```text
① 逻辑时钟        base_time + tick；now 从时钟算，不从系统时间读
② 推进机制        tick 循环 / fast_forward / fast_forward_to / run_now
③ 事件队列        预约单换 due_tick，按时间排序；到点触发，保证只执行一次
④ 状态演化        每个 tick 里环境自己变不变？这是最贵的一块：
                  温度漂移、洗衣机周期、设备自动关闭都要在这里定义
⑤ 生命周期        每个 episode 的时钟重置、随机种子、确定性、隔离
⑥ 观测接口        inspect_time；query_events 记录"到点执行"的事件
```

其中 ④ 是分水岭。如果只是"到点执行预约单"，那是事件驱动的跳跃，不算连续时间；如果要"空调开 10 分钟温度降 2 度"这种物理过程，就必须逐 tick 演化，内核立刻变重。

### 2.2 ABCD 各要改什么

```text
B 仿真器
  新增 ①~⑥ 的组件；B_models 要能表达 Clock / Schedule / TickEvent；
  env 要新增推进接口（模型不能调，harness 调）；
  reset 语义从"复制状态"变成"复制状态 + 重置时钟与事件队列"；
  所有时间相关的状态演化规则要一条条写出来，并配测试。

C 回合引擎
  从"单阶段交互"变成三阶段：交互（模型下单）→ 推进（harness 快进）→ 验证；
  finish 的语义要重新定义：下单后结束，还是等到点执行完再结束；
  多轮会话与时间的关系要定义（每轮之间时间走不走？用户第二句话是几点说的？）；
  截断、超时、取消这些边界都要在推进阶段重新处理。

A 策略
  提示词新增"下单不等于执行"；模型不能推进时间，只能写单 / 查未执行的单 / 取消，
  而且看不到单的状态变化（list 只列还没执行的单）；
  如果任务要求回报执行结果，模型要知道自己在哪个阶段说话。

D 数据管线
  D4 Oracle 要跑时间内核：登记 → 推进 → 验证，替代现在的"打一遍动作看终态"；
  D5 轨迹要加 tick/事件/预约单快照；
  D6 判定要区分"下单对"和"执行对"；
  每个任务的合成时间变长（连续 tick 时与 tick 数成正比）。
```

### 2.3 对训练、微调、强化学习的增量

```text
SFT 数据合成
  每条任务的 Oracle 验证从"几个动作"变成"几个动作 + 时间推进 + 结果核对"；
  事件驱动跳跃的增量小，连续 tick 的增量按 tick 数线性增长。

轨迹形态
  模型看到的还是每轮一个 observation；多数任务里模型看不到推进过程，
  所以监督信号还是"下单是否正确"，内核更多是在环境侧花成本。
  只有设计成"下单 → 查状态 → 回报"的任务，模型才会真正用到时间推进的结果。

GRPO
  同一任务 G4 条 rollout 都要跑同一套推进逻辑；连续 tick 时是 4 × 任务数 × tick 数；
  事件跳跃时成本接近现在。时间推进还不确定性时要锁种子，否则同组四条不可比。

评测
  能测执行时刻的边界：到点时设备掉线、多张单顺序、取消后不执行、只执行一次；
  代价是 fixture 数量翻倍，评测时间变长。
```

### 2.4 收益与风险

```text
收益
  支持"执行时"的行为测试；支持连续物理过程；时间基准与 SimuHome 同类；
  论文里"temporal environment"的卖点更硬。

风险
  内核是新子系统，正确性、确定性、隔离都要重新测；
  连续演化会让 RL 吞吐下降，训练预算被时间模拟吃掉；
  本期 TC6 的任务只要求"一次性预约"，内核能力大概率用不满。
```

## 3 方案二：静止时间要做什么

### 3.1 把语义写死

```text
now        整个 episode 固定为 scenario.base_time；inspect_time 永远返回它，clock=virtual
           （时间格式与存储口径见 3.7）
schedule   只写单：校验 at 与 steps，写入 episode 级预约单列表，不真正执行
list       只列还没执行的单（{schedule_id, at}）；取消 / 已执行 / 失败的单不再下发
cancel     取消后 list 里立刻看不到，到点什么都不会发生
finish     表示"下单完成"；到点执行结果不由模型在本次 episode 里承担
可见性     模型永远只看到"在列表里的未执行单"或"不在列表"两种状态，
           没有 pending → done → cancelled 的状态流转（对齐_目前方案 10-09 修订）
```

### 3.2 校验方法：三项检查 + 影子执行（3.3 用的也是这一套）

```text
先记住复用关系：
  方案二只有一套执行逻辑，就是 execute_action 用的那套
  （四道闸门 + 动作应用）。校验时把它作用在一份状态副本上，
  这就是"影子执行"。3.3 不另起一套，只是给它换一个起点状态。

校验顺序：
  ① at 校验      now 冻结；格式 YYYY-MM-DD HH:MM、晚于 now、不超过 7 天；
                 过去 / 超窗 → INVALID_TIME
  ② steps 校验   把 steps 喂给和 execute_action 相同的四道闸门：
                 设备存在 → 实体可用 → 动作支持 → 参数范围
  ③ 影子执行     copy 一份起点状态 → 应用 steps → 得到"如果到点执行后的状态"
  ④ 结果比对     影子结果 vs 任务的 conditions / keep；满足记成功，
                 不满足记失败（到点掉线本期不处理）

  ③ ④ 合起来就是"目标对齐"；② ③ 与真实执行共用同一内核，
  不另写校验器，保证"校验能过"和"真到点能执行"语义一致。
```

### 3.3 到点状态快照：给同一套影子执行换一个起点

```text
和 3.2 的关系：不新增校验方法，只把影子执行的"起点状态"换掉。

3.2 默认     当前状态 → copy → 影子状态 → 应用 steps → 结果比对
3.3 加快照   当前状态 → copy → 影子状态 ← 用快照覆盖指定字段
                                     → 应用 steps → 结果比对
                                    ↑ 唯一多的就是这一步

所以"3.3 是不是也复用仿真器"——是：同一套仿真器、同一套四道闸门、
同一套影子执行；快照只是它的一个可选输入。不跑第二套仿真器，不做时间推进。

是什么    静止时间下世界不动，默认"到点时的世界 = 现在的世界"。
          要测"到点时世界已经变了"时，就在任务里写一份到点时刻的状态快照。

例子      任务："40 分钟后关加湿器"
  不写快照     影子执行用当前状态，加湿器在线 → 关成功 → 判成功
  快照=被改过  到点时空调已被别人调到 26 度，预约是"设为 24 度"
               → 影子执行仍然把它设成 24 → 判成功
  快照=已关着  影子执行 changed=false → 按任务定义记"目标已达成"

快照从哪来
  来源一   生成任务时直接声明（最常见）：{加湿器: {available: false}}
  来源二   影子实例里预演后导出：先假设性打几个动作，再把状态 dump 出来
  来源三   以后有时间内核时由环境自己产生（本期不做）

在哪用    生成阶段（D2/D4）    写进蓝图 / task，和 conditions 一样是隐藏真值
          交互阶段（D5）       模型看不到；episode 内世界不动
          结算阶段（D5/评测）  3.2 的影子执行读它（没有就用当前状态）→ 比对 → 打分

好处      不跑内核也能覆盖执行时刻的主要边界：被别人改过、目标已达成
代价      只是一个假设的快照，不是真的未来
```

### 3.4 时间与记忆的数据归谁（D → C → B → A）

```text
模块   存什么                                              生命周期
A      不存任何东西；只拿 context、输出工具调用            单次调用
B      世界状态：设备状态 + 冻结时间 now + 预约单列表 + 记忆文本
       并且是全部工具的宿主：observe / inspect_room / inspect_device /
       execute_action / inspect_time / time_control / memory   单 episode / 单会话
C      会话编排与判定：turns 记录、收取 finish、条件比对、
       调用 B 的影子执行结算；自己不另存时间或记忆             单 episode / 会话
D      任务真值 + 数据落盘：base_time、memory_initial、
       expected.at / steps、due_state、轨迹文件、数据集          跨批次，写文件
```

```text
数据流：
  D 写任务文件（持久）
    blueprint / task: {home, tc:{base_time, memory_initial, session...}, expected, due_state}
        │ D5 运行时读取任务并交给 C
        ▼
  C 编排（不存数据）
    reset(B, scenario) → 交互循环 → 收 finish → 结算 → 返回 record
        │                                              │
        ▼                                              ▼
  B 运行时（内存，单会话）                        D5 落盘（轨迹文件，持久）
    reset 初始化：devices   ← home 副本
                  now       ← base_time（整个会话冻结）
                  memory    ← memory_initial（类1 有内容，类2/3 空）
                  schedules ← []
        ▲
        │ A 通过工具读写；A 不知道这些数据存在哪
```

reset 前后对照：

```text
现在 reset(scenario)
  devices ← scenario.home 的副本

以后 reset(scenario)
  devices   ← scenario.home 的副本
  now       ← scenario.tc.base_time（整个会话不变）
  memory    ← scenario.tc.memory_initial
  schedules ← []
```

几条规则：

```text
reset 签名不变，还是 reset(scenario)；变的是 scenario 多了可选字段块 scenario.tc，
B 从这块里读 base_time / memory_initial / 会话配置，B_schema 同步扩展。
reset 次数由 C 决定：单轮任务一次；多轮任务一个会话一次，轮与轮之间不 reset。
会话结束 B 的运行时状态直接丢弃，不落盘；持久化的只有 D 的任务文件与 D5 的轨迹。
inspect_time / time_control / memory 都是 B 的工具路由，与 execute_action 平级；
finish 仍由 C 收；结算是 C 调 B 的影子执行，B 不改真实状态。

base_time 与 now 的关系：
  base_time 是任务文件里的输入（字符串，持久，D 写）；
  now 是 B 在 reset 时解析出来的运行时值（整数分钟，内存）；
  工具只读 now；base_time 只用于 reset、校验、日志与复现；
  静止时间下两者数值相等；将来若加时间推进，now 会变、base_time 不动。
```

### 3.5 改动清单

```text
B 仿真器
  加三个世界状态字段（冻结时间 now / 记忆文本 / 预约单列表）+ 三个工具路由
  （inspect_time / time_control / memory）+ 预约校验与影子执行函数；
  reset 从 scenario 读 base_time / memory_initial 完成初始化，B_schema 同步扩展；
  设备状态引擎与原有四个工具不动；不需要时钟循环、事件队列、状态演化。

C 回合引擎
  加一个 TC6 判定器：at 正确性（与任务期望比对）+ steps 正确性 + 影子结果；
  reset 次数由 C 控制：单轮一次、多轮每会话一次；结算时由 C 调 B 的影子执行；
  runner 循环不变（仍然单 episode、最多 12 轮、finish 收尾）；
  多轮会话是 TC7 的改造，和 TC6 无关。

A 策略
  提示词加一节时间调度：先 inspect_time，再算 at，再写单；
  绝对/相对各给例子；过去时间、超 7 天、模糊相对时间的处理写清楚。

D 数据管线
  D0 加 TC6 模板；D2 的 task 增加"时间类型（绝对/相对）+ 偏移/时刻 + steps"；
  TC7 还需要 memory_initial；TC6 可选 due_state（到点状态快照）；
  D4 复用同一套校验器（不跑快进）；D5 轨迹加 clock / schedule / memory 快照 /
  session_id / turn_index；
  D6 对 TC6 基本可跳过（规则可验证）。
```

### 3.6 能测什么、测不了什么

```text
能测    读时间；绝对/相对换算；单子合法性；steps 与目标是否匹配；
        取消语义；错误处理（过去时间/超范围/未知设备）；
加了到点状态快照后：状态被改、目标已达成等（掉线不处理）
测不了  真实的时间流逝本身；多张单之间的真实先后冲突；
        连续物理过程（空调开 10 分钟降 2 度）；"到点后环境自然变化"
```

### 3.7 时间表示规格（2026-10-09 拍板）

```text
格式        YYYY-MM-DD HH:MM，家庭时区，不带时区后缀
精度        分钟；秒不进模型视野，±30 秒只是环境侧验收窗口
绝对性      指向日历上唯一时刻，可比较、可加减、可算两时刻差
冻结        scenario.base_time 由数据管线选定，整个 episode 不变
星期        不存储；字符串里只有日期与时分，需要时由日期派生显示
内部存储    整数分钟（now 与 at 都存分钟），展示或交互时格式化成字符串
调度窗口    7 天 = 10080 分钟：at 必须晚于 now，且不超过 now + 10080
时区        Asia/Shanghai（家庭时区）固定，不做时区转换
```

字段落地：

```text
B base_time        string   "2026-10-09 09:30"  scenario 自带，episode 内不变
B now              int      由 base_time 换算的分钟；inspect_time 返回格式化串 + clock
B schedules[].at   int      写单时由模型给的字符串解析；内部比较用分钟
time_control.at    string   "2026-10-09 22:00"  模型输出格式；
                            解析失败 / 过去 / 超 7 天 → INVALID_TIME
```

例子（now = 2026-10-09 09:30；当天其实是周五，但周五不存储、不下发）：

```text
"今晚 10 点"            → at = 2026-10-09 22:00
"40 分钟后"             → at = 2026-10-09 10:10
"明早 7 点"             → at = 2026-10-10 07:00
"23:40 时说 40 分钟后"   → at = 2026-10-10 00:20   ← 跨天，日期必须参与运算
"预约到 8 天后"          → INVALID_TIME（超 7 天窗口）
```

对任务范围的影响：

```text
本期收录    今晚 / 明早 / 后天 / 几分钟后 / 几小时后 / 具体时刻（同天或跨天）
本期不收录  "下周一""每周三"这类依赖星期的表达；等确认要做，
            再讨论在显示层加"周五"派生字段（存储格式不变）
数据侧      日期池覆盖早上 / 下午 / 晚上 / 深夜与工作日 / 周末；
            月初月末、闰年边界先避开；跨午夜作为独立边界样例
```

## 4 对比表

```text
维度              方案一 照搬 Home                方案二 静止时间（+影子执行）
本质              时间会走的内核                  时间冻结的校验器
B 改动            5 类组件（时钟/推进/队列/演化/生命周期）
                                                  1 个存储 + 1 个校验函数

```

## 5 推荐路线

```text
本期（TC6）
  方案二：静止时间 + 影子执行 + 到点状态快照。
  接口语义与对齐_目前方案一致：inspect_time 只读、time_control 只写单、
  list 只列未执行的单（10-09 修订）、finish 表示下单完成。
  真实执行交给"校验器"，训练与评测成本不变。

二期（可选，事件跳跃）
  只加"跳到 due 时刻"的能力：不做连续 tick，只处理到期事件，
  用来验证"下单 → 到点真的执行"的端到端流程。
  这一步能补上"多张单真实顺序"等少量行为，成本远低于完整内核。

三期（可选，tick 内核）
  只有当我们确实要做连续物理过程（温度演化、设备运行周期）时才上，
  参考 SimuHome 的 tick + fast_forward_to + schedule_workflow。
  到那时再动 B 的内核，本期不预留复杂度。
```

## 6 和 TC7、整体排期的关系

```text
TC7 记忆不依赖时间机制：读预写记忆、单轮读写、多轮不 reset 都能在现有
B/C 上小改完成（多轮需要 session 改造，但不是时间改造）。

建议排期：TC7 先做（快、判定清楚），TC6 静止版并行；两者共用 D 管线与评测框架。
时间内核留到有明确任务需求时再做，避免为了"机制完整"拖慢数据与训练。
```

## 7 待拍板问题

```text
1  确认本期采用"静止时间 + 影子执行"；内核留二期/三期。
2  到点状态快照（due_state）收不收？收的话，任务数据里允许指定"到点时刻的状态"。
3  finish 语义：TC6 的 completed 是否只表示"下单完成"；要不要在 summary 里
   明确说"已预约 X 点执行"。
4  是否需要"下单 → 查单 → 回报"的多轮 TC6 变体；需要的话它属于多轮改造，
   和时间内核无关，可以单独排期。
5  影子执行的判分口径：只判"单子对"，还是同时要求"影子结果达成目标"。
6  评测集里是否放少量"到点会失败"的负例（参数越界、目标已达成）。
```
