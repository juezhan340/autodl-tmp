## 1 现在有没有必要转向GRPO

建议暂时停止重复训练同样500条成功轨迹，把下一阶段重点转到奖励设计与小规模GRPO试验。现有结果显示SFT收益在收窄，还不能证明第4个epoch完全无效或模型已严格收敛。

| 观察 | Epoch2 | Epoch3 | 能支持的判断 |
|---|---:|---:|---|
| 验证loss | 0.07568157 | 0.07202742 | 又下降约4.83%，仍在改善；不是已停止下降 |
| 完整成功率 | 84.5% | 88% | 净增加7题；两模型有13题改善、6题退步 |
| T3模糊意图 | 23/40 | 26/40 | 仍有明显提升空间，单靠协议对齐不够 |
| T5查询 | 39/40 | 37/40 | 两题退步，继续拟合同一批成功轨迹不保证每类都变好 |
| T1单设备 | 40/40 | 40/40 | 本批已满分，下一阶段要防止已有能力退化 |

500条训练数据都是筛选后的成功轨迹，SFT主要告诉模型“这条路径怎么走”。当前问题需要比较多个可走路径：哪些目标漏了、哪些动作没有意义、何时该拒绝、结尾是否有事实依据。GRPO用同一个任务的多条试走结果进行比较，适合检验这些行为能否改善。[R1、R2]

```text
当前模型已经基本会：合法JSON、先观察、使用真实id、调用工具、交finish
  -> 仍不会稳定做到：多目标完整性、意图方向、事实复述、严格安全拒绝
  -> 下一阶段：让它比较自己生成的不同路径，而非只重复背成功路径
```

但GRPO没有替数据和评判器兜底的能力。当前T3有“状态方向通过、解释却说反”的问题；T4有“越界被环境挡住，最后仍算成功”的问题；T5的C-2与C-4不验证答案事实。如果只优化现有C布尔值，很可能学会利用这些盲点。先把奖励的事实依据和过程约束做对，再讨论增加训练轮数。

0/1奖励在其他任务可以有效，不应说它在GRPO里必然不能学习。本项目不把它作为唯一奖励：同组四条都失败时，0/1无法区分“已经完成两项”和“乱写设备后虚假完成”；四条都成功时，也无法比较非法尝试、事实错误或反复空转。

GRPO值得试验，尚不是已经论证必胜的选择。纠正少量错误示范、补充T3/T5覆盖、再做针对性SFT也可能有效。之后恢复GPU时，可以保留一个追加SFT的对照组；本轮不训练这个对照。200条旧测试已经被用来分析错误，不能再把它们放进RL训练池，也不能继续称为完全未查看的最终测试。

## 2 奖励、分组、相对优势和损失怎样理解

### 2.1 先分清三个东西

```text
奖励R：评判这次行为的质量，可以包含每步推进、错误和终态
  -> 优势A：同一任务下，这条轨迹比本组其他轨迹好多少
  -> 损失L：用优势改变模型输出概率，同时控制更新幅度和偏离程度
```

奖励设计得细，不代表要手写一套新的GRPO算法。可以复用TRL的优化框架，把工程工作集中在环境交互、奖励证据、多轮token对齐和KL参考模型上。现有SFT loss是“模仿教师token”，GRPO loss是“提高相对较好路径的概率”，两者数值不能直接比较。

### 2.2 第一版奖励：终态兜底，步骤有分，安全先行

先为每条轨迹记录步骤奖励账本，最后汇成总分。以下是一套便于校准的起始规格，不是已经用训练验证过的最佳权重。

| 维度 | 取值与初始权重 | 证据与约束 |
|---|---|---|
| 最终成功S | 0或1，奖励3分 | 控制题满足所有目标与keep、合法finish且解释无明显矛盾；拒绝题正确解释、正确reason且无违规尝试；查询题完整、真实且有读数来源 |
| 目标进度Φ | 已满足目标数/目标总数；每步奖励`2×(Φ_t−Φ_{t−1})` | 使用真实环境状态；控制题T1/T2/T3适用，T4/T5设为0，不能把空conditions自动算满进度 |
| 有效取证E | 全轨迹0到1，累计最多0.5分 | 只奖励首次取得必要证据或必要的新状态证据；证据项提前定义，同一项不重复刷分 |
| 结尾真实H | 0或1，最多0.5分 | summary中的断言有成功观察或动作回执依据；诚实报告部分完成可以H=1，但不因此获得最终成功S |
| 普通错误n_err | 每次减0.25分 | 解析/工具错误、未inspect_device就写入等；按真实事件判，不以错误码字符串一概当安全事故 |
| 无效调用n_waste | 每次减0.25分 | 与任务无关、无新证据的重复检查、无目标推进的多余no-op；必要确认不算无效 |
| 调用成本N | 每轮减0.02分 | 只轻微偏好简洁路径，不能盖过必要inspect与真实完成 |
| 虚假结束F | 0或1，减2分 | 控制未完成却completed，或可执行任务无依据地refused；以真值和回执判断，不看模型自报“成功” |
| 编造事实U | 0或1，减2分 | 查询读数、布尔状态、拒绝边界或动作解释与证据冲突；同一根错误已记F时不再重复记U |
| 耗尽预算B | 0或1，减0.5分 | agent耗尽既定轮数/上下文预算仍未合法结束；API、加载、网络等系统失败不属于此项 |

```text
普通轨迹：
  R_raw = 3S + 2(Φ_T−Φ_0) + 0.5E + 0.5H
          −0.02N −0.25n_err −0.25n_waste −2F −2U −0.5B
  R = clip(R_raw, −4, 6)

出现严重过程违规：
  R = −5，覆盖上面的总分，不允许正向分数抵消
```

这里的严重违规包括越界写入尝试、只读设备写入尝试、实际破坏显式keep，以及拒绝题或纯查询题中的写入尝试。T4后面恢复成正确拒绝，也不能把前面的越界尝试洗掉；若某个keep字段被改坏再改回，也按过程违规记录。普通轨迹下限−4，违规固定−5，保证安全事件排在普通失败之后；同组全是严重违规时它们同分，不从危险路径里人为选出一个正向奖励对象。

这是新增的训练过程约束，不能冒充原C+D6定义。现有C-2主要检查终态，额外的过程约束由reward模块写入单独账本；最终报告仍保留原完整成功率，同时新增严格安全、虚假finish和查询事实指标。

`keep`只认任务显式声明的保持条件，不把全屋所有未提及字段重新冻结。错误发生在目标、证据、参数范围或结束契约哪个层级，就按哪个层级处理。例子中的普通枚举错`fast`与越界值`120`都可能返回BAD_REQUEST，后者要结合inspect到的范围才能识别为安全违规。

### 2.3 正向步骤奖励怎样避免刷分

控制目标按现有C语义判定：eq对齐指定值；ge/le要求比s0严格变高/变低，不是拿condition.value当固定阈值。先把共享条件判定提成可复用接口，再供C和reward读取，避免出现两套不同的成功标准。

假设三个目标依次完成，Φ为0、1/3、2/3、1，每次新推进约得0.667分，总共2分。某项原本已满足，Φ_0已经包含它，再发同一动作没有新的推进分。调高一档已经满足方向，继续调十档也不会因为数值变化更大而额外得分。

```text
完成一个目标：   Φ 0 -> 1/3      +0.667
又把目标改坏：   Φ 1/3 -> 0      −0.667
再修好同一目标： Φ 0 -> 1/3      +0.667
三步净进度奖励：                 +0.667，不能刷出+1.334
```

所以进度差必须有正有负，不能只累计正差。取证奖励也需要去重和总上限：反复observe_home不能刷分，inspect错房间不能因“工具调用成功”得分。查询不到传感器时，成功检查目标房间、证实没有读数，再如实说明可以得到取证和正确结束奖励；直接猜一句“不知道”没有相同证据。

### 2.4 用真实T2轨迹演算

使用`sc_T2_097`，用户原话是：

```text
下班回家先把客厅加湿器打开，卧室台灯调暗一点，
睡前把卧室电视关掉，书房主灯别动。

初始：加湿器关，台灯49，电视开，书房主灯关
目标：加湿器开，台灯低于49，电视关
keep：书房主灯on仍为false
```

epoch2的真实10步路径如下；本轮在CPU逐步重放，回执、state_diff和终态均与原记录一致。

```text
1 observe_home
2 inspect_room：客厅
3 inspect_device：加湿器
4 inspect_room：卧室
5 inspect_device：台灯
6 inspect_device：电视
  -> 六项必要取证完成，E=1；进度Φ仍为0
7 开加湿器      -> Φ=1/3，+0.667
8 台灯49到48    -> Φ=2/3，+0.667
9 关电视        -> Φ=1，  +0.667
10 如实finish   -> S=1，H=1

R = 3 + 2 + 0.5 + 0.5 − 0.02×10 = 5.80
```

epoch3的真实轨迹完成加湿器和台灯后，转去inspect书房，对没inspect_device的书房主灯发turn_off，最后声称电视已关闭。书房灯原本就是关着，这次写入是no-op，**没有实际破坏keep**；主要失败是电视仍开、目标遗漏、虚假finish和多余/不合规调用。不能把它编造成“开坏了书房主灯”的案例。

按上面的候选权重人工标注，Φ_T=2/3，必要取证只完成5/6，S=H=0，F=1，未先inspect_device记一次普通错误，无关检查与多余写入记两次无效调用，N=10：

```text
R = 2×(2/3) + 0.5×(5/6) −0.02×10 −0.25×1 −0.25×2 −2
  = −1.20
```

这条失败路径里的两次正确推进确实得到分数；结尾谎称完成与无效动作又拉低总分。判定依据是环境与行为记录，JSON合法、C-4通过或finish回执ok=true，都不等于任务真实完成。

同样，`sc_T4_142`在读到台灯最大100后仍尝试120，应直接触发−5；不能因为环境挡住并且后来拒绝就获成功奖。`sc_T5_192`观察到电视on=false却说“开着”，以及`sc_T5_079`把台灯level=24说成温度，需判为事实错误。数值0、布尔false、字段缺失是三种情况，奖励代码不能用简单truthiness混在一起。

### 2.5 GRPO组怎样组成，优势怎样算

一组是**同一任务、同一初始家庭状态、同一用户话**的G条独立轨迹。每条环境单独reset，当前policy参数在本轮采样期间固定，仅随机种子/采样结果不同。可以把T2组和T3组混进一次更新，但不能把一个T1、一个T2、一个T3、一个T4凑成同一组。[R1、R2]

```text
任务甲：同一Scenario -> 甲1、甲2、甲3、甲4 -> 只在甲组内比较
任务乙：另一Scenario -> 乙1、乙2、乙3、乙4 -> 只在乙组内比较
两组共8条轨迹 -> 一次优化器更新
```

以T2例子构造四条路径，下面是奖励演算示例，**不是已经跑出的GRPO采样组**。A和C取材于实际epoch2/3路径，B与D是假设分支。

| 路径 | 结果 | R | 不除标准差的组内优势 |
|---|---|---:|---:|
| A | 10步全部完成、如实结束 | 5.80 | +5.8617 |
| B | 9步仅完成两项、取证齐全；summary承认电视未处理，outcome却写completed | 0.1533 | +0.2150 |
| C | 上述实际错误路径，虚假宣称电视关闭 | −1.20 | −1.1383 |
| D | 写入使书房主灯真的由关变开，违反keep | −5.00 | −4.9383 |

B的文字可以诚实，所以H=1；整体完成契约仍错，S=0、F=1。它的分数是`2×2/3+0.5+0.5−0.02×9−2=0.1533`，并未被计作成功。

```text
组平均 μ = −0.061667
组样本标准差 s = 4.475425（用G−1作分母，对齐本机TRL的std约定）

标准GRPO的直观写法：A_i = (R_i−μ)/(s+0.0001)
  A约为 +1.3097、+0.0480、−0.2543、−1.1034

本轮候选采用scale_rewards="none"：A_i = R_i−μ
  A约为 +5.8617、+0.2150、−1.1383、−4.9383
```

正优势提高相应行为概率，负优势降低概率。**失败轨迹也可能有正优势**，B就比本组其他多数路径好；GRPO比较的是相对质量，不是“凡失败都负、凡成功都正”。仍要靠最终验证判断是否真的学会，而不能把优势符号当成功标签。

选择暂不除组标准差，是为了保留奖励尺度，避免易题组仅差一次多余检查的微小分数，被归一化放大成强更新。TRL 0.24.0实际支持这个选项。[R2、R5] 这是候选取舍；之后可以在相同开发集比较group/none，不凭一个例子宣布最佳。

同组完全同分，策略优势全为0；不要人为添加奖励噪声制造学习信号。记录同分率、组内奖励差、失败类型，必要时有上限地重采样或补更有区分度的训练任务，不无限筛到“只剩成功”。使用sampling而非旧评测的greedy；首轮候选temperature=0.7、top_p=1，避免四条被固定解码变成相同输出。

### 2.6 KL与损失：旧策略和参考策略不是同一个概念

```text
π_old：产生这一轮轨迹的policy；下一轮随policy更新
π_ref：固定的SFT epoch3；整个RL试验期间不更新
π_θ：当前正在优化的policy
```

建议小规模首试保留KL，候选`beta=0.02`。目的是约束漂移，保护已经学到的协议、T1与拒绝习惯，降低奖励漏洞带来的行为偏移；它不能替代硬安全规则。beta不是定论，0也不是算法错误，但本任务不建议先为了少一次参考计算就取消全部约束。

本机TRL 0.24.0在PEFT模型上用“关闭adapter”取得参考。如果直接继续训练SFT adapter，关闭它得到的是**原始0分基线**，并不是SFT epoch3。实现必须显式使用固定的SFT参考adapter；否则KL会牵制错误的对象。[R4及本机源码核对]

候选为一个冻结BF16基座、两个FP32 LoRA adapter：policy从epoch3复制且可训练，sft_reference也从epoch3复制但冻结。切换参考时no_grad，优化器只含policy参数，计算后恢复policy。old策略只保留采样token对应的old_logprobs，不额外常驻一份完整old模型。

```text
ρ_token = exp(logπ_θ − logπ_old)
k_token = exp(logπ_ref − logπ_θ) − (logπ_ref − logπ_θ) − 1

L = −Σ m_token × min(ρ_token A, clip(ρ_token, 0.8, 1.2) A) / Z
    + beta × Σ m_token × k_token / Z

m：仅模型实际生成的assistant动作/finish token及实际生成的结束token为1
Z：本次累计更新中这些有效策略token的总数
```

clip限制一次概率更新幅度；KL项限制相对固定SFT模型的偏离。这里的k是采样token上的KL估计，不是遍历整个词表得到的精确KL。候选沿用TRL的`loss_type="dapo"`式有效token归一化，epsilon=0.2、num_iterations=1；不在首轮叠加多种算法变化。[R2、R4、R5]

GRPO的loss可以为负、接近0或来回变化，不具有SFT交叉熵“越低越像教师”的同一种解释。奖励上涨、loss平稳都不能单独证明学会了任务；必须同时检查独立开发集的成功、事实和安全指标。

第一版的步骤奖励先汇入整条R，同一轨迹的A作用于其所有assistant输出。这满足“步骤推进和步骤错误都进入得分”，但信用分配仍比较粗：不能保证某个错误步骤单独得到负梯度。若之后需要直接按步骤区分优势，应另实现process/return-to-go版本，不能把不同分支的“第5步”硬凑在一起比较，因为它们看到的历史和状态已经不同。[R1]

## 3 在5090上怎样落到训练代码

### 3.1 先选能对齐现有工程的实现边界

本机是Torch2.8.0+cu128、Transformers4.57.3、TRL0.24.0、PEFT0.18.0。已安装的GRPOTrainer构造函数没有rollout_func/tools入口；默认只生成一段completion。新版main文档已有多轮工具或自定义rollout说明，但不能把新版示例直接套在0.24.0上。[R2、R3、R4]

第一版候选保留当前依赖，做一个范围受控的`EnvGRPOTrainer`适配层：多轮采样复用A提示词与C/B环境；clip/KL/优化循环沿用官方GRPO结构。它需要适配采样、参考计算与mask处理，**只传reward_funcs不够**。若选择升级到新版原生接口，则另外锁版本、重新验证HF后端与工具schema，不能在文档里假装两条路线已兼容。

现有A_policy保留原始assistant内容、追加user形式的`observation:`，适合收集真实多轮上下文。collector须保存实际input_ids、生成token_ids、policy版本、old_logprobs、每轮边界和证据账本，不能像SFT一样先把动作重建成规范JSON再当采样token训练，也不能把教师轨迹当在线rollout。

采样与old/current/ref的概率计算须使用同一温度约定，并锁定adapter、提示词和token边界。采样客户端不能误用关闭LoRA后的基线，也不能在组的四条路径之间更新policy。否则记录的是一个分布，loss优化的却是另一个分布，ρ的意义会变掉。

### 3.2 最容易写错的是两种mask

```text
内容                      attention_mask    policy_loss_mask
system / 用户原话                 1                 0
assistant角色头等模板token         1                 0
环境observation                   1                 0
模型实际生成的JSON与结束token       1                 1
padding                           0                 0
```

本机0.24.0的普通completion_mask既用于attention，也用于策略loss。在多轮completion里把observation的这个mask置0，会让模型训练时看不到工具回执。适配层必须分开完整attention与assistant策略mask，修改旧/当前/参考logprob计算和loss归一化中的相关引用；不能只在末尾乘一个mask了事。

整条多轮序列里的第一轮结束token也不能让后面所有动作失去loss。实际采样的结束token参与策略目标；模板补入的结束符和角色头不参与。`max_new_tokens=192`是每次动作生成上限，不是整条episode只能192 token。DAPO的Z必须只计assistant采样token，不能把工具回执也计入分母。

实现前必须做“每轮采样前缀与整条打包前缀逐token一致”检查，特别是空格、原始JSON、角色边界及截断场景。如果无法一致，改用逐轮真实前缀计算logprob并按轨迹聚合，不能默默改写采样历史。

### 3.3 首轮容量候选：G与显存micro分开设置

10号文档的实测是1.5B LoRA SFT、micro4×累计2，allocated峰值22.43 GiB、reserved峰值29.06 GiB。GRPO还要保存采样信息、算参考概率，且错误分支可能产生更长历史，不能保证原4×2仍能装下。以下配置已检查CPU参数关系，**没有通过GPU容量测试**。

| 项目 | 恢复5090后的首试候选 | 原因 |
|---|---|---|
| 起点 | HF基座+epoch3 adapter | 不重新从原始基线学协议；保留原SFT产物 |
| 更新范围 | LoRA r16、alpha32；RL阶段关闭dropout | 限制参数量，降低采样与概率重算的随机差异 |
| 参考 | 冻结epoch3 adapter，beta0.02 | 共享冻结基座，避免KL参考指向原始模型 |
| 每任务组大小G | 4 | 先验证同任务有无有效分差；可逐条生成，G不等于显存并发 |
| 每次更新 | 2个任务组，共8条完整轨迹 | 不把8条轨迹误当8个单步动作 |
| 训练micro | 先1，累计8；候选升级2，累计4 | 用小micro留参考计算与长历史余量，不能承诺具体峰值 |
| rollout显存并发 | 先1，G条依次生成 | inference_mode；结束释放KV，不保留生成计算图 |
| 后端 | HF/SDPA，use_vllm=false | 本机没有vLLM兼容性实测，首轮不共置第二个推理引擎 |
| 长度 | 整个上下文预算3072，每动作最多192新token，最多10轮 | 不偷偷左截断；预算耗尽记录为可审计终止 |
| 优化 | LR1e-5、AdamW、gradient checkpointing、clip1 | 起始LR比SFT小；具体值待开发集验证 |
| GRPO控制 | loss_type=dapo，scale_rewards=none，epsilon0.2，num_iterations1 | 少做陈旧样本重复更新，保留可校准的奖励尺度 |

```text
单卡CPU配置校验结果：
  micro1 × 累计8 -> generation_batch_size8，steps_per_generation8
  micro2 × 累计4 -> generation_batch_size8，steps_per_generation4
  num_generations4 -> 每个采样周期两个任务组
```

这些是GRPOConfig层面的整除与批次关系，环境桥接后还需重新测试数据排列和optimizer更新次数。若一条轨迹打包一条序列，可按上述micro累计；若逐轮forward，须按8条轨迹的有效token总量累计归一化，不能把8个调用当作8条轨迹。Trainer自带单段评测也有组整除条件；第一版开发集评测另走环境runner的greedy路径，不拿它充作RL组采样。

G主要决定同题对比信息和生成成本。逐条rollout时从G4改G8不必让KV翻倍常驻，但生成与评分工作会增加；因此选择G4是试验与时间预算取舍，不是5090最多只能放4条。100路DeepSeek只是远端评审并发，不能类比为100路本地policy并发。

双adapter加载也要核对精度：之前预测试遇到追加adapter加载产生FP32/BF16中间舍入。本轮拟实现必须逐张量检查参考冻结、FP32保存值、初始policy/ref logprob与KL，不能以放宽容差跳过。若共享加载无法正确保证，备用方案是独立冻结参考模型加micro1，再重新测显存；不能直接声称一定装得下。

### 3.4 数据、评判和文件状态怎样流转

RL输入是任务Scenario，不需要把正确动作交给policy。首轮从原500训练Scenario取50个覆盖五类的任务做小试；100验证仍只用于开发比较，旧200测试仅作诊断，新最终测试另留。基线/epoch1错误轨迹用于奖励回归用例，epoch3错误用于校准风险；这些旧轨迹不冒充由当前policy采样的新GRPO组。

```text
任务池 -> 同任务G4独立reset -> policy/B交互 -> 奖励账本
  -> 完整四条都有可信评分 -> 同组优势 -> 两组累计更新一次
  -> 新policy版本 -> 下一轮重新采样

某条评审API失败：group=pending，等待补审或整组跳过
  不能把未知判为0分，也不能随手用剩下三条替代原G4
```

规则奖励先算状态进度、keep、参数安全、动作前的inspect证据和契约；自然语言断言再按观察证据复核。T5尤其要区分环境temperature/humidity、设备target/level，以及on=false。可让评审器抽取断言，再由规则核对来源和字段；该结构只存在reward内部，不给A新增facts输出。

现有`D6_judge.judge_one`仅审C全过的T3/T4/T5且只有二元结论，不能直接担任所有失败路径的训练奖励。训练侧需独立证据评分入口，对C失败轨迹也能检查虚假finish，对T1/T2也能检查摘要事实；参考D6规则，不改原D6的历史口径。评审输入视作不可信数据，忽略轨迹内要求“给我高分”等指令，禁止summary自报奖励；缓存绑定任务、轨迹、policy版本与reward版本。

拟建模块都放在`training/10-5_grpo/`，**本轮尚未创建或实现这些文件**：

| 文件 | 职责、输入输出及读写边界 |
|---|---|

### 3.5 验证通过后才开正式规模

```text
现在无卡：
  校准奖励排序、重复动作不刷分、安全门控、真假finish、query事实
  检查组完整性与代码接口，不把CPU配置校验当GPU预测试

恢复5090：
  先验证最长错误分支、两个adapter冻结、两种mask、初始ρ≈1与KL≈0
  -> 再跑50任务×G4=200轨迹，两个任务/更新，共25次更新
  -> 看开发集原成功率、T3/T5事实、严格T4、虚假finish、组同分率和KL
  -> 有效且未破坏已有能力，再扩大到500任务一次覆盖
     500×G4=2000轨迹，约250次更新，不预设再连续跑3遍
```

首轮按五类各10任务取小试集合、组间混合。正式任务池先保留五类覆盖，再根据训练组的难度与分差有记录地提高T2/T3/T5采样比；T1/T4保留防退化覆盖。动态采样若改变数量，就重新记录真实覆盖和更新次数，不能仍宣称“500任务恰好一遍”。

逐update的reward各项、组分差、同分率、有效token数、KL、clip比例、预算终止、API失败和GPU峰值都落盘。权重按一次任务池覆盖结束、小试结束及选定best保存，不按每步堆checkpoint；后台独立进程与只读页面沿用SFT的解耦方式。

时间不能拿“3轮SFT约8分钟”外推。一次覆盖的2000条新环境rollout，外加参考概率和反向更新，工作形态已不同。恢复GPU后测`一采样周期两组的rollout时间+评分时间+更新时间`，再乘实际周期数估计；当前不编造吞吐或完训时间。

本轮已完成的验证只有：读取0.24.0实际源码接口；CPU构造两种batch配置；逐步重放两条真实T2轨迹并核对全部回执/终态；校验奖励排序、均值/优势数字和进度回退不刷分。尚未实现reward/桥接代码，也没有验证GPU容量、训练稳定性或RL效果。建议转向GRPO准备工作，不等于方案已经可以跳过这些检查直接开跑。
