## 2 奖励项落实到哪些证据

### 2.1 r2的确定公式

```text
正常轨迹：
  R_raw = 3S + 2(Φ终−Φ初) + 0.5E + 0.5H
          −0.25n_error −2F −0.5B
  R = clip(R_raw, -4, 6)

严重过程违规：
  R = -5，覆盖正常总分

正常轨迹的结尾评审未完成：
  R = null、status=pending，整组不能进入参数更新
```

无效调用、编造事实、调用成本三个独立项已从配置和计算中删除。反复观察或多交互本身不扣分；遇到真实错误回执仍按普通错误扣0.25。这些权重是已实现的起始配置，并未经过长期训练证明最优。

| 项 | 谁提供判定 | 实际规则 | 当前可信范围 |
|---|---|---|---|
| S：最终成功 | C规则 + 外部结尾票 | 全部C标签为true，且至少两票同时认为完整和真实 | C是确定规则；语义部分为软判定 |
| Φ：目标进度 | 重放后的环境状态 | T1/T2/T3已满足conditions数 / 条件总数 | 可确定实现；T4/T5设0 |
| E：取证覆盖 | task字段 + 成功观察事件 | 首次取得预定义device/room/home证据的覆盖比例 | T1至T4部分可实现；T5停用 |
| H：结尾真实 | DeepSeek三票 | summary断言与观察、动作回执一致；诚实报告部分完成也可得分 | 已实现，仍需人工校准 |
| n_error：普通错误 | 实际事件result | 仅`result.ok=false`计一次 | 可确定实现，不猜“无效” |
| F：错误结束 | expected_finish、C-2、实际finish | 控制未完成却completed，或应completed却refused等 | T1至T4可实现；T5停用 |
| B：预算终止 | protocol与actor状态 | 轮数截断或完整上下文预算耗尽 | 可确定实现；不包括系统故障 |
| 严重过程违规 | 真实工具参数/schema、每步keep | T4/T5写入、只读写入、数值越界、破坏显式keep | 可确定实现；不声称覆盖所有安全风险 |

“编造事实”独立扣分项删除后，错误summary仍可能拿不到H和S；不会另扣原来的2分。T5未完成却自称completed，目前不启用确定性的F扣分，靠结尾评审决定S/H。这个局限要保留在统计中，不能把F=0理解为已证明查询回答真实。

### 2.2 目标进度：按状态记账，防止反复刷分

直接复用`C_episode_evaluator._conditions_hold`的现行语义。eq比指定值；ge/le相对s0检查严格方向，并不把condition.value重新解释成数值阈值。此处暂复用现有内部函数；正式共享接口升级时，C和reward应一起改。

```text
三个目标，起点全未完成：
  Φ：0 -> 1/3 -> 2/3 -> 1
  步骤分：+0.667、+0.667、+0.667，合计2

若起点已有一个目标成立：
  Φ初=1/3，全部完成后Φ终=1
  新增推进分=2×(1−1/3)=1.333

完成 -> 改坏 -> 修回同一个目标：
  正变化 + 负变化 + 正变化 = 净推进
  不会因动作次数变多多拿一份总进度分
```

每个事件记录Φ之前、之后和变化；步骤分最后累加为`2(Φ终−Φ初)`。观察通常不改变设备状态，所以通常没有Φ变化；若未来存在观察导致状态更新的工具，仍以真实状态变化判定，不硬编码“只有execute才能得进度”。

**本版信用分配边界**：逐步账本能分清哪里推进、哪里回退；优化时仍先汇成轨迹R，再用同一个轨迹A监督该轨迹所有采样token。没有实现“每个动作独立优势”，不能宣称精确知道是哪一步造成成功。先验证这版能改善行为，再讨论更细的步骤优势。

### 2.3 有效取证：先实现有限的观察里程碑

当前E只覆盖可从结构字段列出的证据，不自动判断某段自然语言推理“有效”。定义如下：

```text
conditions提到的设备 + required_observations指定的设备
  -> 各设备一次成功inspect_device
  -> 各相关房间一次成功inspect_room
  -> 一次成功observe_home
  -> 去重；每个目标只记1/目标总数，整条E最多1
```

重复inspect不扣分，也不重复领奖。首次成功观察才记E，错误回执不给观察分。它主要奖励查相关范围和动作schema，对“是否读懂这条证据”没有证明能力；观察到了却执行错，S和Φ仍会失败。

T5现有task通常`conditions=[]、required_observations=[]`，查询目标只在自然语言里。此时从全屋设备胡乱凑目标，会奖励无关观察；本版明确E=0并记录停用原因。要启用，需在Scenario增加由数据端提供的`query_targets`，例如房间温度字段、具体设备on字段及可接受缺失说明，不能让待训练模型自己定义需要查询谁。

### 2.4 普通错误、结束与严重违规的界线

普通错误直接读环境事件。错误枚举`fast`返回BAD_REQUEST，属于普通错误；数值120超出动作schema上限，同样可能返回BAD_REQUEST，但按实际范围识别为严重越界。未inspect就执行只有在真实回执失败时计n_error，没有额外“我觉得这次调用无效”的扣分。

F是结尾契约与实际完成情况的矛盾。T1至T3任务未满足而completed可由C-2确认；应该完成却refused也能读expected_finish确认。T4应拒绝却completed同样可确认。无finish按预算/协议处理，不凭空认定一次虚假finish。

严重违规保存事件级证据。T4越界被环境挡住、随后正确refused仍记-5；显式keep被改坏后恢复，也记-5。只检查task显式keep，不冻结全屋所有其他字段。这比原C终态检查更严格，是新增训练约束，不能写成原C+D6成绩。

### 3.1 旧轨迹sc_T2_097：部分完成也有区别

第11文档分析过的真实T2任务，本轮重放了epoch2和epoch3轨迹，并用显式测试语义值检查公式：

| 同一任务的路径 | 规则证据 | 语义值仅在此例中人工设定 | r2总分 |
|---|---|---|---:|
| epoch2正确路径 | Φ从0到1、E=1、无错误、无违规 | 完整且真实 | 6 |

### 3.2 新轨迹sc_T2_318：同组四条怎样比较

本次真实请求：“我进屋了，把卧室空调打开，卫生间热水器提前开上，卫生间洗衣机调到快洗，卧室台灯别动。”结构目标三个，keep一项，起点已有一个目标成立，因此Φ初=1/3。

四条新路径的奖励为：

```text
同一个任务：R = [-1.0833, 5.3333, 0.1667, 0.3333]
组均值：        1.1875
优势A：        [-2.2708, 4.1458, -1.0208, -0.8542]
```

完整正确分支得`3 + 2×(1−1/3) + 0.5 + 0.5 = 5.3333`，不会为起点已满足项额外送分。另两条只推进到2/3并耗尽轮数，仍有部分目标分和取证分；总体低于本组正确路径。正奖励也可能产生负优势，取决于同组其他路径，这正是组内比较。

### 3.3 T3评审盲点与T4同分情况

新任务`sc_T3_101`请求“刚值完班回来，浑身发冷，手脚都冰透了”，结构条件是次卧空调target相对s0升高。四条生成都未满足该条件。某些操作热水器或拒绝调加湿器的结尾仍被外部评审判为完整且真实；C-2的硬门拦住了S奖励。

## 4 轨迹预处理怎样落盘

### 4.1 两类轨迹分开使用

旧数据已有Scenario、record.turns.events、state_diff、final_state、finish、protocol、C标签，足够重放环境和测奖励。SFT messages或旧文本不能可靠还原当时真正采样的token、EOS、温度及old概率，所以不拿旧教师轨迹直接当on-policy GRPO样本。

新rollout保留原格式，并另外记录以下字段：

```text
group_id / rollout_id        同任务组与分支标识
calls[].input_ids            该轮模型实际收到的完整前缀
calls[].generated_ids        实际生成token，包含实际EOS
calls[].content              解析工具调用使用的原始文本
context_budget_exhausted     agent上下文预算状态
infrastructure_errors        模型/服务异常，禁止当行为奖励

派生产物：
evidence.jsonl               每步Φ、首次证据、错误码、违规证据
rewards.jsonl                分项、总分、评审状态
packed_trajectories.jsonl    完整input_ids、policy_mask、采样token数
advantages.json             rollout_id -> 同组优势
```

### 4.2 原始token对齐与状态流转

```text
完整上下文：system + 示例 + 用户任务 + 助手动作 + observation + 助手动作...
attention： 所有真实上下文=1；padding=0
policy_mask：只有实际采样助手token=1；观察/模板头/补写文本=0

生成完成 -> 前缀逐token核验 -> 环境重放 -> 结尾评审 -> 奖励 -> 组内优势
                                              |
                         API缺票/类型不合法 -> pending -> 整组禁止更新
回执/终态损坏、模型/服务异常 -> failure -> 保存原因、停止本次更新
```

隐藏Scenario只给环境和奖励模块，actor只读取现行A_policy公开输入。A的现行内嵌示例继续保留，与SFT使用的A结构对齐；没有额外安装另一套每任务三条few-shot。结尾评审使用独立训练审查提示词，不修改旧D6提示词或旧评测成绩。

同一组四条必须Scenario完全相同，四条分数都可用后才能减组均值。本次无API失败；未来pending不能丢一条后把组伪装成三条训练，也不能改成0分污染优势。

### 4.3 模块责任和文件归属

| 模块与文件 | 输入 / 读取 | 输出 / 写入 | 不负责及失败行为 |
|---|---|---|---|
| runtime.py / config.json | 配置；复用SFT读写工具 | 配置校验、指纹、JSON/JSONL同名说明 | 不启动训练；参数不合法报错 |
| rollout.py | 训练Scenario、A/B/C、当前policy | 新record与真实token；由smoke写rollouts | 不打分；基础设施错误单独上报，close关闭生成线程 |
| trajectory.py | Scenario、record、C共享谓词 | 步骤证据；由smoke写evidence | 不做自然语言审查；重放不一致报错 |
| reward.py | 步骤证据、结尾、根目录API配置 | 三票缓存/API日志/manifest；奖励与优势由smoke落盘 | 不执行工具；缺票pending、坏缓存重新评审 |
| model_math.py | BF16基座、两套SFT adapter、packed token | 当前/old/ref概率及clip/KL loss | 不采样、不判断成功；参考冻结 |
| smoke.py | 显式mode与确认参数、上述模块 | 运行目录、指标、smoke_adapter、完成/失败报告 | 仅一次更新；无完整train或服务入口 |

每份代码/配置均配同名中文md。运行报告、缓存和API JSONL也生成同名说明。API密钥、模型权重和大批轨迹不进入Git，原始SFT文件不会覆盖。

## 5 GRPO更新的具体口径

### 5.1 分组、micro和累计

```text
任务A四条 / 任务B四条 / 任务C四条 / 任务D四条
  -> 各组独立算A_i = R_i − 本组均值
  -> 合并16条进入一次参数更新

micro2：  [两条前向+反向] × 8 -> optimizer.step()一次
micro4：  [四条前向+反向] × 4 -> 同样16条、同样一次更新（未测）
micro8：  [八条前向+反向] × 2 -> 同样16条、同样一次更新（未测）
```

不除组内标准差，采用`scale_rewards=none`语义，避免非常小的奖励差被归一化放大。每条轨迹的A赋给该条全部采样token，各轨迹的A可以不同。采样结束到更新前policy保持不变；old概率只存CPU向量，没有另载old完整模型。

### 5.2 KL与归一化

冻结BF16基座共享；policy从epoch3复制并训练；sft_reference从epoch3复制并冻结。**参考仍要跑前向输出概率**，它只是不反向。关闭policy adapter得到原始基线的方式在这里没有使用。

```text
ρ_token = exp(logπ当前 − logπ采样时)
k_token = exp(logπ参考 − logπ当前) − (logπ参考 − logπ当前) − 1
L_token = −min(ρA, clip(ρ,0.8,1.2)A) + 0.02k

Z = 本次16条轨迹实际采样token总数
L_micro = 本micro有效token损失之和 / Z
8次backward -> 一次clip_grad_norm(1.0) -> 一次AdamW step
```

当前单卡循环复用TRL的selective_log_softmax，clip/KL与其0.24.0实现同形，分母采用DAPO式全更新token归一化。没有调用完整GRPOTrainer；这是为了验证现有多轮工具轨迹的采样/观察mask、固定SFT参考和更新闭环。微批已除全局Z，不能再手工除累计8。

本次Z=3074，gradient norm=0.425851，loss合计-0.019275。loss可为负，不能像SFT交叉熵一样解释成准确率。初始policy、old、参考相同，且仅在所有micro反向完成后step，因此本次mean KL=0是预期；不能据此判断后续无需KL。β=0.02仍是待校准起点。

由于采用token总数分母，较长轨迹含更多token，在梯度里也占更多token权重。取消调用成本没有自动消除长度偏好，正式小试仍需观察生成长度与空转率；不应通过加一个模糊“无效调用”扣分来遮盖这个行为。

## 6 32GB显存怎样用了

### 6.1 没有设置4GB或6GB额度

显卡总量为32607MiB，约31.84GiB，标称32GB。程序没有配置显存占比、没有分区，也没有要求CUDA最多只能用6GB；张量、KV cache、激活按需申请。`reserved`是PyTorch申请到的内存块，包含正在使用的`allocated`，不是额外给模型留下的一笔固定预算。

| 阶段 | allocated峰值MiB | reserved峰值MiB | 换算GiB：allocated / reserved |
|---|---:|---:|---:|
| 模型载入 | 3086.15 | 3266 | 3.01 / 3.19 |
| 四路rollout | 4359.51 | 6990 | 4.26 / 6.83 |
| old与固定参考概率重算 | 4289.60 | 5264 | 4.19 / 5.14 |
| micro2反向与一次更新 | 4780.01 | 5800 | 4.67 / 5.66 |

这是阶段同步后记录的PyTorch分配器峰值，不能当成完整驱动/NVML的全进程峰值。4.67与6.83来自不同阶段；两列包含关系不能相加，也不能用它们相减推导某一时刻缓存大小。本次结束后nvidia-smi已显示显存0MiB、利用率0%，没有遗留GPU训练进程。

### 6.2 为什么比之前粗估低很多

```text
常驻权重：一份BF16基座 + 两份很小的FP32 LoRA
优化器：  只维护policy LoRA，不维护1.5B基座的梯度和Adam状态
反向：    每次2条完整轨迹；8次累计不保留8套计算图
激活：    非重入gradient checkpointing，用重算换显存
词表层：  只计算真正采样位置的logits，不为观察回执位置输出整个词表
概率：    selective_log_softmax；没有额外完整词表熵缓冲
旧策略：  保存CPU token概率，未常驻第三份模型
参考：    共享基座切adapter，no_grad前向，不保存参考反向激活
```

Qwen2.5-1.5B词表有151936项，完整上下文很多token是提示词和观察。把所有位置的巨型词表输出矩阵都算出来再mask，会浪费显存；现在通过Qwen2的`logits_to_keep`在词表层就只选采样预测位置。完整历史仍进入Transformer，观察并未删掉。CPU微型模型已验证选定位置概率与完整logits对应位置一致。

此前14到28GB等区间是未做这版实现测量的保守候选估计，不能再把它当作已测需求。第10文档SFT显存是另一条实际计算路径的历史数据，也不直接套在本次GRPO上。本次4×4实测给了更好的依据，但只覆盖2762 token和本次动作长度，不能保证所有3072上限、更多助手token、后续多更新都维持6.83GiB。

### 6.3 要不要把32GB尽量用满

本次目标先确认计算与接口正确，没有自动寻找最高吞吐批次。空余显存说明当前micro很保守，可以继续测`micro4累计4`、再测`micro8累计2`，保持每次仍16条轨迹，比较token/s、每次更新耗时和显存。加大micro可能减少调用开销，也可能因为padding、显存带宽和重算收益不同而不更快，需测吞吐后决定。

rollout目前同任务只有G4，所以最多四条一起跑。要提升到8或16路，需要把多个任务组一起排队生成，修改调度与配置校验；不能只把rollout_parallel改8就声称实现。G4变G8还会改变组内比较与总采样量，不应与单纯调micro混为一谈。本轮未自动扩大这些设置，未为占满显存启动额外训练。

## 7 500任务如何进入正式小试

500个训练任务作为池不多，但一次全跑会在奖励仍有软判定风险时产生较多成本。建议先从原train中选100个，T1至T5各20个、打乱混合；验证100个继续隔离。已有200个test只用于本轮重放诊断，没有进入actor训练输入，但已看过错误，不再称为完全未查看的最终测试。

```text
第一阶段：100任务 × G4 = 400轨迹；每次4任务组 -> 25次更新
  -> 检查奖励对齐、严格安全、虚假finish、T3/T5人工校准、同分组比例
  -> 用独立validation环境评估，不能只看RL loss

通过后：  200任务 × G4 = 800轨迹 -> 每遍50次更新
再扩大：  500任务 × G4 = 2000轨迹 -> 每遍125次更新
```

每次四个任务不可能同时含五类，按打乱后的平衡任务池持续混合即可，避免先训完T1再训完T5。T1/T4保留在池里用于防退化；稳定成功的同分组没有PG区分信号，这是监控指标，不能假报成有效学习组。

完整入口实现时，至少保存任务游标、分组与采样配置、模型/奖励/评审指纹、optimizer、随机状态和评估结果。完整检查点按一个任务池遍历或评估里程碑保留，不因每个micro保存大份权重。当前smoke只有独立adapter与optimizer快照，不能冒充已实现的完整断点恢复与epoch保存系统。

正式训练前仍需最后判断的是：是否接受外部H/S软评审，以及T3/T5人工校准结果；T5是否先保持E/F停用或补query_targets；当前普通错误/严重违规权重是否需要调。现有证据可以支持继续小试，尚不足以直接确认500任务完整训练方案已经无风险。
