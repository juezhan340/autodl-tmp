# 1.5B 的 SFT 与后续 GRPO：监督轮次、框架、数据量和 Batch

> 日期：2026-10-04。
> 接续：`15_SFT方案第一部分_数据选择与轨迹组织.md`。
> 范围：回答这次提出的四组问题，给出第一轮可采用的实验规模与 batch 建议；不创建训练脚本、不转换正式训练数据、不启动训练。
> 模型：先只讨论本地 `Qwen2.5-1.5B-Instruct` 的 HF 原始权重，服务器为单张 RTX 5090 32GB。
> 术语：本篇将“500 个任务 rollout 后继续训练”按项目既定的 GRPO 理解。HomeFlow 论文自己的强化学习阶段称为 step-wise RLVE，不把它的实现直接等同于本项目的 GRPO。

## 1 一条轨迹有五次助手输出，是不是做五轮 SFT

可以理解为“这五次输出都会得到监督”。其中“交互轮”“训练 epoch”和“优化器更新”是三件不同的事，不能都叫训练轮。

```text
交互轮 turn
  用户话 -> A1 -> O1 -> A2 -> O2 -> A3 -> O3 -> A4 -> O4 -> A5 finish
  一条轨迹有 5 次助手决策，形成 5 段监督目标

训练样本
  上面完整对话作为 1 条样本
  一次前向计算中，在 5 段 assistant 输出上计算 token 预测损失
  用户话、system 和 observation 提供条件，不作为生成目标

训练 epoch
  训练集整体被学习 1 遍，称为 1 个 epoch
  与某条轨迹有 5 次还是 10 次助手输出无关

优化器更新
  一个或若干个 micro-batch 累积梯度后，更新 1 次参数
  不因为一条样本有 5 次输出，就自动更新 5 次参数
```

沿用第 15 篇中的冰箱样本：A1 学 observe_home，A2 学 inspect_room，A3 学 inspect_device，A4 学合法设置 8.0，A5 学 completed 的 finish。它们都属于同一条因果序列上的监督目标。

每段目标内部也是逐 token 预测。例如 A4 不只监督 `execute_action` 这个名字，还监督 device_id、动作名、参数键和值，以及 JSON 结构。SFT 在给定正确历史的条件下提高这些目标 token 的概率；无需在每条训练样本上实际再调用五次 HomeEnv [R1]。

因此，你说的“每一次模型输出都进行 SFT 对齐”基本正确；这里的“对齐”具体指行为示范的监督学习，不等同于对每个输出单独做一次 RL 奖励更新。

## 2 框架选什么，哪些部分需要我们写

建议使用 **Transformers + TRL + PEFT**。首轮采用 TRL 的 SFTTrainer 配合 LoRA，保持原有 A / B / C 业务接口；不手写损失反传、优化器训练循环或分布式训练框架。

| 部分 | 交给谁 | 在本项目中的职责 |
|---|---|---|
| 模型与 tokenizer | Transformers | 加载本地 HF 权重、使用该模型的聊天模板和 token 化规则 |
| SFT 训练循环 | TRL SFTTrainer | 组织训练、损失计算、梯度累积、验证和检查点 |
| LoRA 参数适配 | PEFT | 在基础模型上附加并训练少量适配参数 |
| 张量和 GPU 执行 | PyTorch / Accelerate | 反向传播、设备管理、梯度累积等底层执行 |
| 数据和业务接入 | 项目代码 | 从现有轨迹恢复可见消息、设置监督范围、关联原始场景、接入环境评测 |

TRL 官方支持会话格式、助手区域监督及 PEFT 集成；PEFT 的 LoRA 提供低秩适配方式 [R1 / R2]。选这些组件并不意味着把 `D_dataset.jsonl` 整包直接传给 Trainer：第 15 篇确定的数据可见性和消息恢复仍然是我们自己的职责。

先用 LoRA 是为了让第一轮实验的训练参数、显存成本和检查点管理更容易控制。这并不证明 1.5B 全参数训练不可行，也不保证 LoRA 不会过拟合；本篇暂不比较两种方法的最终上限。

### 2.1 目前实际写到哪一步

目前新增的是方案文档，尚未写训练器或训练脚本。现场检查时，已有 PyTorch `2.8.0+cu128`，独立模型工具 venv 中尚未安装 Transformers、TRL、PEFT、Datasets 和 Accelerate。

本次只在 `/tmp/qwen-sft-tokenizer-probe` 放置了临时 `tokenizers 0.23.2`，用于读取已有的官方 tokenizer 文件测序列长度；没有加载模型权重、没有计算梯度，也没有把这组分析工具当作训练环境。

### 2.2 “只监督助手”还需要验证一处接入

本地 1.5B 的 `tokenizer_config.json` 聊天模板没有 `{% generation %}` 助手区域标记。它可以正确渲染对话，但不能据此宣布“打开助手监督开关，就一定能得到正确 mask”。官方的助手区域监督要求模板提供相应区域信息 [R1]。

后续需要补一层能识别 assistant 区域的训练模板或等价的数据适配。原则是角色边界、JSON 正文、观察消息和停止 token 的实际序列保持一致，仅明确哪些位置参与损失。

```text
我们需要补的数据接入
  原始轨迹 -> 可见 messages -> 模板渲染 -> 监督位置检查
                                          |
                                          v
                               交给 TRL / PEFT 训练

不需要重新实现
  Transformer 前向、交叉熵反传、优化器训练循环
```

这里还有一个格式边界：公开工具 schema 已经写进 system 正文，assistant 输出是纯 JSON 文本；不能无意间切到 Qwen 的 XML 原生工具调用格式，否则训练和当前 A 的推理协议会不一致。

### 2.3 后续 GRPO 也优先用框架，但需要环境连接

TRL 有 GRPO 的组生成、自定义 rollout 和多轮工具交互接口 [R3]。我们的 HomeEnv、C 标签和 D6 判断仍需要接入；不能只把普通问答样例换成家庭用户话，就视为多轮 GRPO 已经实现。

一次家庭 rollout 要经过多次 A 生成和环境执行，环境回执由程序产生。只有模型实际生成的助手动作参与相应策略学习，工具观察不能被当成模型生成 token。这个接入下一阶段再设计；本篇先分析数据规模。

## 3 六七百条 SFT 数据是否合理

**600 条可以作为第一轮行为 SFT 基线，700 条可以作为增量对照。** 对当前五类任务，这个规模值得先试；没有依据承诺它一定足够达到某个成功率。

“模型更小，所以一定需要更少数据”不能直接成立。参数量较小不自动降低任务覆盖要求；设备动作、数字边界、模糊说法、跨房间组合和拒绝类型，仍需要样本覆盖。小模型还可能更依赖清楚一致的示范。

HomeFlow 的论文实验使用 Qwen3-8B，并报告 26,000 条验证过的多轮 SFT 轨迹 [R4]。这只是它的实验条件，不是本项目的最低门槛；本项目的模型、五类任务、环境范围和研究目标都不同。

### 3.1 “600 条”具体指什么

这里的 600 条是 600 条完整家庭轨迹，不是 600 条单独的 assistant 消息。第 15 篇核实的 994 条候选轨迹包含 5588 次助手决策，平均每条约 5.62 次。

```text
600 条完整轨迹
  -> 约 3300–3400 段助手决策目标，具体数量取决于抽到哪些轨迹
  -> 每个目标仍包含多个需要预测的 JSON token

如果只取 600 条单步消息
  -> 只有 600 个决策目标
  -> 数据规模和跨轮覆盖明显不同
```

600 条能够先用于学习一套稳定的工具协议和五类常见行为。它不代表已有 600 种互不相关的能力；每条轨迹中大量发现动作是共享的，罕见设备和罕见行为仍可能缺样本。

### 3.2 先定划分，再讨论是否扩到 700

建议在 994 条无错误成功候选池内，先按完整场景划分。以下是拟议数量，尚未写出划分文件。

| 类别 | SFT 训练 | 验证 | 新保留测试 | 备用 | 候选总量 |
|---|---:|---:|---:|---:|---:|
| T1 | 120 | 20 | 20 | 40 | 200 |
| T2 | 120 | 20 | 20 | 40 | 200 |
| T3 | 120 | 20 | 20 | 40 | 200 |
| T4 | 120 | 20 | 20 | 34 | 194 |
| T5 | 120 | 20 | 20 | 40 | 200 |
| 合计 | 600 | 100 | 100 | 194 | 994 |

验证集用于选训练后的模型、判断是否过拟合和是否值得增加数据；新保留测试集用于方案确定后的最终检查，不反复用来挑选配置。原有 250 条评测集继续保留作历史对照，不能把它已经参与过提示词调试这一事实忽略掉。

若增加到 700 条，只把每类 SFT 训练从 120 增加到 140，保持同一份验证和测试集合不变；备用数量从 194 降到 94。这样才比较得清“多 100 条数据”带来的增量。

真正的分组依据是场景内容和蓝图关系，不是跨批次可能重号的 `sc_T1_001` 字符串；同一场景的各个助手轮不能跨训练与验证集合。

### 3.3 比再加一百条更重要的，是类内覆盖

五类每类 120 条只是第一层均衡。类内还要检查设备类型、动作、eq / ge / le、跨房间组合、keep、拒绝原因和查询信息来源，避免随机抽样漏掉少量关键行为。

本次读取候选池发现两个具体例子：

```text
T3：200 条轨迹的 execute_action 中
  turn_on 99 次，set_mode 86 次，set_temperature 129 次
  turn_off 只有 7 次，set_percentage 只有 9 次
  -> 只看“T3 有 120 条”，仍可能忽略少量关设备或调百分比示范

T4：194 条无错误成功轨迹
  finish.reason_code 全部是 OUT_OF_SAFE_RANGE
  READ_ONLY_DEVICE 为 0 条
  -> 当前池里没有只读设备写入拒绝的直接示范
```

如果希望学生模型也稳定拒绝传感器写入，应补相应类型，而不只是再增加一批热水器或空调越界题。公开 system 中提过 READ_ONLY_DEVICE，也不能替代这一行为的实际训练和评测覆盖。

### 3.4 怎样判断 600 条是否够

首轮关注各类环境成功率、finish 契约、方向参数和安全拒绝是否改善，并看训练与验证的差距。不能只看训练 loss 已经下降。

如果训练表现持续改善、验证改善有限，应先检查覆盖、噪声和过拟合；如果某个罕见动作持续失败，优先补那个行为。700 条可以检验边际收益，不应在尚无基线结果时就假设必须扩到上万条。

100 条新保留测试意味着每类只有 20 条，因此它适合发现明显退化，不能支撑非常细的百分比差异结论。几个任务的偶然成败就能改变单类成绩，报告时应同时给成功条数。

## 4 500 个任务做 GRPO，是否合理

**合理作为首轮 RL 任务池规模，但 500 个任务不等于 500 条 rollout。** 还要确定每个任务生成多少条候选轨迹，以及同一个任务池被使用多少次。

GRPO 比较同一任务下的一组模型输出与奖励 [R3]。在本项目中，应按同一家庭初态、同一用户请求和隐藏目标来定义组；组内各条轨迹分别重置环境，再由学生自己逐轮生成。

```text
一个家庭任务，从同一份 s0 开始
  rollout 1：A -> B -> A -> ... -> finish，得到 R1
  rollout 2：A -> B -> A -> ... -> finish，得到 R2
  rollout 3：A -> B -> A -> ... -> finish，得到 R3
  rollout 4：A -> B -> A -> ... -> finish，得到 R4
                         |
                         v
                 组内比较，再用于优化
```

以每个任务 4 条候选作规模示例：

```text
任务池 500，组大小 G=4
  每个任务用一次 -> 2000 条完整 rollout
  每个任务用三次 -> 6000 条完整 rollout

若平均每条 rollout 有 5–6 次助手生成
  2000 条 rollout -> 约 1万–1.2万次逐轮模型生成
```

上面的 5–6 次只是估算，学生可能提前 finish、出错或走到轮数上限，不能把教师轨迹均值直接当成学生吞吐实测。G=4 是分析起点，也不是这次已经设置好的训练参数。

### 4.1 500 个 RL 任务能否与 SFT 任务重合

可以重合，二者都是训练用途：SFT 学教师示范，GRPO 让学生在任务上重新交互并获得奖励。必须隔离的是验证和测试任务，不能把它们拿来更新模型。

先走通闭环时，可以从 600 个 SFT 训练场景中选每类 100 个，共 500 个 RL 任务。这样的实验能回答“RL 是否改善了同一训练任务池上的策略”，还需要未参与更新的任务验证泛化。

如果希望 RL 使用全新、与 SFT 不重合的 500 个任务，则只看 994 条成功候选池，数量不够：

```text
600 SFT + 100 验证 + 100 测试 + 500 全新 RL = 1300 个任务
现有无错误成功候选池 = 994
缺口 = 306

先保留 SFT / 验证 / 测试后，当前备用池为 194
  -> 可以提供部分新 RL 场景
  -> 仍需再补 306 个，才能凑齐完全不重合的 500
```

上面的缺口只针对“994 条无错误成功候选池”。同批另有 268 条未进集轨迹，其蓝图也可能提供 RL 任务；RL 任务本身不要求教师轨迹一定成功。但这些蓝图需再检查目标、keep、观察要求及回合预算，不在这里直接计为可用数量。

尤其 D4 只证明动作能够执行，不保证在 10 轮内完成发现、全部动作和 finish。例如三个不同房间的目标，若都需要 observe、各自 inspect_room / inspect_device / execute，再 finish，就需要 11 次决策；不应让学生在当前 10 轮契约下训练一个没有合法完成路径的任务。

### 4.2 任务数足够，也可能没有有效的组内差异

如果某个任务的四条 rollout 全部失败或全部成功，标准组内相对奖励就没有成功 / 失败差异可以利用 [R3]。因此要看奖励分布和组内差异，不能只报告“做了 500 个任务”。

以二值奖励为例：

```text
[0, 0, 0, 0] -> 全失败，组内没有差异
[1, 1, 1, 1] -> 全成功，组内没有差异
[0, 1, 0, 1] -> 有成败差异，可以比较
```

这要求 SFT 先让学生具备基本协议和任务能力，同时 RL 任务不能全是它已经稳定做对的简单题。后续再根据实际表现调整难度和覆盖，不先把 GRPO 任务数量当作效果保证。

### 4.3 还要把环境与裁判成本算进去

如果沿用现有成功判定，T3 / T4 / T5 的语义部分仍需要 D6 或等价的可靠判断。特别是 T5，C 的空 conditions 和空 required_observations 不能单独证明读数回答正确；不能为了加速，把“直接 finish 但没查传感器”的行为奖励成成功。

500 个任务若每类 100、每任务 4 条 rollout，每次使用任务池最多有 1200 条 T3 / T4 / T5 轨迹进入三票语义复核，即最多 3600 次外部裁判调用，假设这些轨迹的 C 标签全过且不计重试。实际数量会随 C 通过率变化。

因此，RL 的主要预算除了 GPU 生成，还包括多轮环境执行、语义裁判和重复采样。这个预算与 SFT 中“一个 batch 放两条现成对话”不是同一概念。

## 5 1.5B 的 Batch 先设多大

建议首轮从 **micro-batch=2、梯度累积=4、单卡有效 batch=8 条完整轨迹** 开始。它是保守的试训起点，尚未经过显存与吞吐压测，不能宣布这个组合已经在本机跑通。

### 5.1 先看真实对话长度

本次对 994 条候选轨迹测了长度。恢复的是第 15 篇所定义的可见消息：公开 A 提示词与工具表、用户原话、规范化助手 JSON、真实 observation；没有加入隐藏 task 或全屋 s0。

使用本地官方 `tokenizer.json` 和 `chat_template` 渲染，保留 Qwen 的角色与消息结束边界，不添加最后的生成提示；工具表已经在 system 中，不启用原生 XML tools 分支。

| 类别 | 条数 | 平均 tokens | P95 | 最大 tokens | 超过 2048 的条数 |
|---|---:|---:|---:|---:|---:|
| T1 | 200 | 1739.0 | 1883 | 2037 | 0 |
| T2 | 200 | 2375.3 | 2629 | 2696 | 195 |
| T3 | 200 | 1903.3 | 2251 | 2524 | 43 |
| T4 | 194 | 1672.0 | 1746 | 1778 | 0 |
| T5 | 200 | 1583.5 | 1934 | 2578 | 6 |
| 全体 | 994 | 1855.7 | 2530 | 2696 | 244 |

全体 P99 为 2632 tokens，总 token 数为 1,844,598。P95 / P99 使用最近秩统计。这些是当前规范化消息的 token 长度，包含输入条件，不能把它们全部当成参与 loss 的助手目标 token。

据此，现有数据可以先以 **3072 tokens 为序列容量上限**，无需为了 SFT 先拆成单步样本。2048 会影响 244 条，尤其会截掉几乎全部 T2；不能用删掉末尾 finish 的办法硬凑进去。

3072 是容量上限，不要求把每条样本都强制补到 3072。batch 内动态补齐至本批最长样本，可以避免让短 T4 / T5 无谓承担长样本的 padding。后续若改 system、模板或追加内容，仍要重新测最终输入长度。

### 5.2 四个数字各是什么意思

```text
micro-batch = 2 条完整轨迹
  单次前向 / 反向，同时放入两段多轮对话
  两条各有五次助手输出时，共有十段监督目标
  仍然只是这一次 micro-batch 的损失与梯度

gradient accumulation = 4
  连续四个 micro-batch 累积梯度

GPU 数 = 1

有效 batch = 2 × 4 × 1 = 8 条轨迹
  累积结束，优化器更新一次参数
```

这是 Transformers 训练参数中 micro-batch 与梯度累积的通常语义 [R5]。有效 batch 计的是样本，样本中的助手轮数和目标 token 数仍会不同。

若该组合在最终模板下显存不足，保守退回 micro-batch=1、累积=8，仍保持有效 batch=8。若显存和吞吐有余量，再比较 micro-batch=4、累积=2。不要为了提升 batch，把完整历史或 finish 截掉。

这些组合只讨论单 GPU；以后增加 GPU 数时要重新计算有效 batch。SFT 的 batch=8，也不等于 GRPO 的同任务组大小 G=8。

### 5.3 600 条数据，对应多少次更新

在单卡有效 batch=8、不跨场景切分的假设下：

```text
600 条完整训练轨迹
  1 epoch -> 600 / 8 = 75 次优化器更新
  3 epoch -> 约 225 次优化器更新
  每条轨迹的全部 assistant 目标，在每个 epoch 中都受到监督

700 条完整训练轨迹
  1 epoch -> 约 88 次更新，最后一批可能不满
```

三遍只是首轮观察上限的建议，不是已经证明的最优 epoch；可以观察第 1、2、3 遍的验证变化选择检查点，不因为训练 loss 还在下降就一直重复。具体更新数还会受到末批处理等执行设置影响。

当前 GPU 查询为总显存 32607 MiB、空闲 32110 MiB。长度测量没有进行训练显存测试，也没有验证助手 mask；所以上面的 batch 与序列容量是有数据依据的候选配置，实际显存和速度仍要试训确认，不在这里估计“几分钟一定跑完”。

## 6 五类任务应该混合还是顺序训

建议第一轮 **五类混合、类别整体均衡、每个 epoch 打乱顺序**。不采用先全部 T1、再全部 T2、最后全部 T5 的单遍类别块顺序。

```text
训练池
  T1 120 + T2 120 + T3 120 + T4 120 + T5 120
                         |
                         v
                 每个 epoch 重排
                         |
                         v
  例如：T2、T4、T1、T5、T3、T2、T1、T4、...
                         |
                         v
            micro-batch 分组，累积梯度后更新
```

五类共享 observe、inspect、JSON 和 finish 协议，但结尾行为不同：有的执行设备，有的拒绝，有的只读后回答。混合能够让这些差异在整个训练过程中持续出现，减少尾部某一种任务长期主导更新的风险。

```text
若最后一大块全是 T5
  最近更新集中在“读完直接回答”，缺少控制和拒绝的共同约束

若最后一大块全是 T4
  最近更新集中在 refused，更需要检查正常控制是否被影响

混合训练
  完成、拒绝、查询在整个训练过程中交替出现
  同时按 T1–T5 分别看验证表现
```

micro-batch 只有两条，当然不可能每一批都含五类；也不要求每次有效 batch=8 都精确覆盖五类。应保证整个训练集和每个 epoch 的类别数量，先使用混合重排即可。

如果以后确实需要严格的类别均衡采样，可以另外设计 sampler；不必为了“每批都五类”而把 batch 固定成 5 或 10。8 也不是因为框架强制二的幂，而是这次选定的保守有效 batch 起点。

分阶段课程训练可以作为后续对照，例如先少量基础协议，再混合五类。但目前已有五类合格示范，先增加一个“按类别顺序训练”的变量，难以判断差异来自数据还是阶段安排，因此首轮不采用。

任务条数均衡也不代表目标 token 权重均衡。T2 对话更长、决策更多；若日后发现某类改善不足，应先看目标覆盖和实际监督权重，不只通过改变最后一个训练类别处理。

## 7 这轮建议收敛到什么方案

```text
先训练哪个
  Qwen2.5-1.5B-Instruct，已有本地 HF 权重

监督单位
  一条完整多轮轨迹为一个样本
  轨迹内每条 assistant JSON 都受监督；不是一条五轮轨迹训练五遍

训练组件
  Transformers + TRL SFTTrainer + PEFT LoRA
  项目只补数据、监督范围和环境评测接入

数据规模
  首轮 600：五类各 120
  同池留 100 验证、100 新测试、194 备用
  是否扩到 700，由固定验证集上的增量表现决定

Batch 与长度
  单卡 micro-batch 2，累积 4，有效 batch 8
  现有完整对话容量上限先取 3072，batch 内动态补齐
  显存不足时回退到 1 × 8，不截断末尾

任务顺序
  五类混合，每个 epoch 打乱；不先训完一类再长期转向另一类

后续 GRPO
  500 个任务可作起点；G=4 时，一次使用任务池产生 2000 条 rollout
  RL 可复用训练任务，验证 / 测试不参与更新
  若要求 500 个全新 RL 任务，需要另外解决任务数量和合法回合预算
```

已确认的是本地数据、模板、序列长度和硬件现场。600 / 700 的最终效果、LoRA 收益、实际 batch 显存与吞吐、GRPO 奖励分布都尚未经过训练验证。本文给出可比较的首轮方案，不给出“这些数量已经足够”的保证。
