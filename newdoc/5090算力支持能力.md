```text

  1.5B HF：LoRA SFT 4×2、三轮checkpoint、四模型并行评测
  DeepSeek D6：100路API并发补审，不占本地模型训练显存

尚未验证
  0.6B和2B完整SFT、1.5B全参数SFT、QLoRA、GRPO
  7B及以上模型、长上下文训练、大batch上限、多卡训练
```

“已经验证”给出的是可用配置，未寻找5090的极限。不同模型结构、序列长度、训练方法和并发方式不能直接沿用这一显存数字。

## 4 SFT能力的实测边界

| 条件 | 正式运行实际值 |
|---|---|
| 模型 | Qwen2.5-1.5B-Instruct HF基座；BF16，未做4bit量化 |
| 训练方式 | LoRA r16、alpha32、dropout0.05；18,464,768个可训练参数 |
| LoRA目标 | q/k/v/o_proj与gate/up/down_proj |
| 数据 | 500训练、100验证、200测试；五类训练任务各100条，混合打乱 |
| 样本形态 | 一整条多轮对话一个样本；assistant输出及结束token参与loss |
| 长度 | max_length3072；训练最长实际2689，验证最长2696；动态padding到8倍数，packing关闭 |
| batch | micro4 × 累计2 = 有效8；验证batch1 |
| 减少激活存储 | 非重入gradient checkpointing开启 |
| 优化器 | AdamW；学习率1e-4，线性调度，warmup19次更新 |
| 运行量 | 3个epoch，189次优化器更新，训练轨迹访问1500次 |
| 时间 | 02:06:02至02:13:57；端到端475.557秒，Trainer调用467.209秒 |
| 平均速度 | 端到端约2.52秒/优化器更新；包含启动、验证与保存，非纯GPU一步测速 |
| 显存峰值 | allocated22971.5 MiB = 22.43 GiB；reserved29760 MiB = 29.06 GiB |
| 保存 | 每个epoch一份完整训练checkpoint，共3份；另有selected_adapter |

```text
allocated：张量等实际分配
reserved：PyTorch分配器已预留的显存，包含allocated
  -> 两者不能相加
  -> 训练时还需留出驱动、CUDA上下文和其他进程的空间
  -> 29.06 GiB预留峰值说明4×2已靠近这张卡的实际容量
```

早期“两条轨迹冒烟约12.74 GiB”的结果不适用于正式4×2批次。不能因为allocated低于32 GiB就认定micro8也能跑；更不能把有效batch8误当成同时在显存里放8条轨迹。

这次最长输入不到2700 tokens，不能据此声称已经验证“每条都3072 tokens”的最坏情况。换成长轨迹、加长system示例、换2B模型或关闭gradient checkpointing后，都需要重新观察峰值。新机器初次迁移应验证代表性最长样本，再决定是否保持micro4；若降低micro至2、累计改4，有效batch仍为8，但该调整不保证速度或数值过程完全相同。

每份checkpoint目录约230 MiB，包含adapter、optimizer、scheduler、随机状态、tokenizer和Trainer状态；selected_adapter目录约89 MiB。其中adapter权重约70.49 MiB，单份optimizer约141.19 MiB。`sft-main/`合计约777 MiB，基础模型单独保留，没有在每轮复制3GB基础权重。

这些占用来自本轮LoRA，不能用于估算全参数checkpoint。本轮也没有实测断电或真实中断后的恢复训练。训练详情和完整日志指针见`19_1.5B_SFT训练复盘_数据方法日志与调整.md`。

## 5 推理与不同模型规模

| 工作负载 | 已验证内容 | 不能由此推导的结论 |
|---|---|---|
| Qwen3-0.6B Q8_0 GGUF | 2026-10-04历史冒烟：llama-cli单轮生成约576 tokens/s，GPU offload；llama-server两slot、总ctx参数32768启动成功，进程显存约4792 MiB | 不是长轨迹、多用户稳态吞吐基准；原登记把它称为“32k×2”，未保存每slot实际n_ctx证据，本文件不沿用这一乘法口径 |
| Qwen2.5-1.5B HF | 基线与epoch1/2/3各独立加载；四进程并行，每进程一次只处理一个episode，共800条环境轨迹、4285次generate，无生成异常 | 未测四进程显存峰值，也未测独占GPU的tokens/s；不能说支持100路本地模型推理 |
| Qwen3.5-2B | HF与Q8_0 GGUF已下载、文件已校验；HF含多模态部分 | 本轮未跑2B正式SFT或服务器吞吐测试；不能套1.5B时间与batch，多模态内存也未验证 |
| DeepSeek D6 API | 310条轨迹、930次调用、100并发上限，9.567秒，无API失败 | 模型在远端运行；速度依赖网络、服务端和缓存，与5090的本地算力无直接对应 |

0.6B服务冒烟使用Qwen3时关闭thinking，避免短输出额度被reasoning_content占用。已有模型目录为`/root/autodl-tmp/models/`，三个尺寸的HF与GGUF合计约13 GiB；详细文件、来源及校验值见`../source_server.md`和`../scripts/model_manifest.md`。

若以后选更大的模型，可以先做权重下界估算，再标记“待验证”。下表把型号中的B当作近似参数量，实际架构还需读模型配置。

| 近似参数量 | 仅BF16权重，按2字节/参数 | 判断范围 |
|---|---:|---|
| 0.6B / 1.5B / 2B | 约1.12 / 2.79 / 3.73 GiB | 尚未包含激活、KV、梯度、优化器；实际1.5B LoRA峰值见上节 |
| 7B | 约13.04 GiB | 仅权重有容量空间；推理与LoRA训练配置均待验证 |
| 14B | 约26.08 GiB | 仅权重已经接近容量，长上下文及训练余量不能按剩余数字乐观判断 |
| 32B | 约59.60 GiB | 不能把整份BF16权重放进单张5090；量化、offload或多卡另作实验 |

```text
推理占用 = 权重 + KV cache + 计算临时量 + 框架开销
LoRA训练 = 冻结基座 + 激活 + 小量LoRA参数/梯度/优化器 + 计算开销
全参数训练 = 全量权重 + 全量梯度 + 优化器状态 + 激活 + 计算开销
GRPO训练 = policy训练占用 + rollout/KV + 可能的reference或独立推理后端
```

例如在明确假设BF16权重与梯度、FP32 Adam一阶二阶状态时，全参数训练的参数相关存储下界约12字节/参数；若另有FP32主权重则约16字节/参数。1.5B对应约16.76至22.35 GiB，尚未加激活、临时量和额外副本。实现的dtype不同会改变这一公式，因此只能帮助预算，不能作为“本机已支持1.5B全参数4×2”的结论。

GRPO尚未执行，当前没有可复用的group size或耗时实测值。应先明确rollout条数、生成长度、是否共置推理引擎、reference是否常驻及reward调用方式，再验证显存；当前也没有QLoRA所需bitsandbytes的本机兼容性证据。

## 6 换服务器后的检查顺序

```text
先看实际GPU与显存、功率限制
  -> 再看容器CPU时间配额和内存限额，不能只看lscpu/free
  -> 确认PyTorch的CUDA构建、sm_120与BF16支持
  -> 恢复相同模型、数据manifest、训练库及run_config
  -> 先检查最长样本的代表性运行与显存
  -> 最后比较耗时，决定batch；保持有效batch并不等于相同吞吐
```

```bash
# 读取GPU、系统与数据盘；均为只读检查。

lscpu
free -h
df -hT / /root/autodl-tmp

# 以下路径适用于本实例的cgroup v2；其他容器需先确认挂载位置。
cat /sys/fs/cgroup/cpu.max
cat /sys/fs/cgroup/memory.max

# 在目标训练环境检查版本和架构，不会启动训练。
```
