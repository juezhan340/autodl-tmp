# A 与大模型交互的上下文最简模式

> 日期：2026-09-30
> 对照：`simuprocject/Simuhome_experiment/src/agents/strategies/react_agent.py`
> 我们现行：`new_demo/agents/A_policy.py` + `eval/C_episode_runner.py`
> 实例：sc_001 五回合（把主卧主灯调成暗档）
> 本稿只分析，不改代码。

## 0. 普通 agent 怎么拼上下文

先把「最简」说清楚。这不是我们家居流水线的特殊设计，是任意工具型 agent 跟 Chat Completions 说话的默认拼法。

HTTP 一次请求一次响应，服务端**不记得**上一轮。所以不能只把「本轮这一句」发出去。模型要接着干，你必须把已经发生过的对话再带上。最简模式是：**每次把完整 messages 列表寄出，列表只在尾部增长。**

```text
只发本轮问题？
  不行。第二步模型不知道用户原话，也不知道刚才 observe 看到了哪些房间。

多轮上下文都发过去？
  要发。但发的是「同一串 messages 再长一截」，
  不是把说明书、用户话、历史打成一张新的 user 考卷。
```

用一个不问家居的例子。用户说：北京明天出门带伞吗。

```text
第 1 次 HTTP
  messages:
    [0] system   你是助手。需要天气就调用 get_weather。
    [1] user     北京明天出门带伞吗？
  tools:        [get_weather]

  模型回        assistant.tool_calls = get_weather(city=北京, day=明天)

第 2 次 HTTP（不是只发「工具结果：小雨」这一句）
  messages:
    [0] system   （还是那一份，不要重写成新段落）
    [1] user     北京明天出门带伞吗？
    [2] assistant  get_weather(city=北京, day=明天)
    [3] tool       {"city":"北京","t":18,"rain":true}
  tools:        同一份

  模型回        明天北京有雨，带伞。
```

第 2 次看起来「多轮都发了」：system、原问题、助手那次调用、工具回执，四条都在。少任何一条，模型都会断档。第 2 次**没有**再写一遍「你是助手。需要天气就调用 get_weather」，也没有把四条压成一个超长 user。

```text
每次 HTTP 的 messages
  = 上一份 messages
    + 刚发生的 assistant
    + 刚发生的 tool/user 观察

变的是尾巴
不变的是已经说过的 system、用户原话、更早的工具来回
```

官方 function calling 用 `role=tool`。没有原生 tools 时，SimuHome 那种 `role=user` + `observation: {json}` 也是同一结构。两种都算最简。

不算最简的，是下面这种「每轮一张新卷」：

```text
第 2 次 HTTP
  messages:
    [0] user =
         你是助手。需要天气就调用 get_weather。
         用户原话：北京明天出门带伞吗？
         上一轮工具结果：{"rain":true}
         可用工具：get_weather(...)
         历史：[{assistant: get_weather...}, {tool: ...}]
```

内容看起来齐，结构错了：说明书每轮重印，历史变成正文里的附件，前缀对不齐，模型每步都在重新读规则。

所以「最简」两个意思要一起成立：

```text
1  每次都把到目前为止的对话带上（不能只发本轮）
2  带上的方式是 messages 数组追加，不是把旧内容折叠进一条新 user
```

下面用这个尺子量 SimuHome 和我们。SimuHome 走的是 1+2。我们每次确实带了历史，但走的是「折叠进一条新 user」，所以不是最简。

## 1. 我们现在怎么发

`DeepSeekPolicy.respond` 每回合做同一件事：把 `A_policy.md` 填七个占位符，打成**一条** `role=user` 的 content，然后 `chat.completions`。C 虽然在内存里有 `history` 列表，但没有把它当成 API 的多轮 messages，而是 `json.dumps` 塞进文末「历史：」。

```text
每一回合发出去的 messages（现行）
  [0] user = 规则头全文
            + 用户话
            + 回合  k / 10
            + 上一轮工具结果
            + 协议反馈
            + 可用工具 schema（四个家庭工具 + finish）
            + 历史 JSON（前面所有 assistant/tool 对）
```

sc_001 实测：第 1 轮这份 content 约 2085 字，第 5 轮约 5433 字。规则头和工具表五次一字不差地重复。工具 schema 还排在「上一轮结果」后面，前缀缓存也吃不满。

A 看不见 hidden task，这点没问题。问题是：它每回合都要重新阅读「你是智能家居助手……灯分三种能力……」才能决定下一步。

## 2. SimuHome 怎么发

`ReActAgent.run` 把 messages **建一次、后面只 append**：

```text
messages 初始
  [0] system   SYSTEM_PROMPT（角色、只许 JSON、工具表、Matter 规则）
  [1..]        一组 one-shot 示范（user/assistant 交替，教格式）
  [n] user     本轮真正任务：User Query + 人所在房间

循环
  调 LLM(messages)
  messages.append(assistant, 模型刚吐的 JSON)
  跑工具
  messages.append(user, "observation: " + 工具回包)
  再调 LLM(messages)
直到 action == finish
```

对应源码：`react_agent.py` 里 `system_content` 只 format 一次；循环内是 `messages.append(assistant)` 再 `messages.append(user, observation)`。工具表在 system 里，不会每步再贴一份。

它还带着 few-shot，所以第一轮并不「最瘦」。但结构是对的：说明书固定在左边，右边只长对话。

## 3. 用 sc_001 对照

用户话不变：直播刚结束，累得只想赶紧卸妆，把主卧主灯调成暗档吧。

**现行第 4 轮**（即将 `set_mode dim`）发出去的是一张新考卷：规则头 + 用户话 + `4 / 10` + 上一轮 inspect_device 整包 + 工具五份 schema + 前三轮历史 JSON。历史里的 inspect 结果和「上一轮工具结果」重复。模型必须从这坨里再把主灯 `enum: dim|bright` 找出来。

**改成 SimuHome 那种 append 之后**，第 4 次 HTTP 的 messages 是同一串对话长出来的：

```text
messages:
  [0] system     角色、每轮一个动作、主灯/台灯能力、越界拒绝、finish 字段、工具怎么用
  [1] user       直播刚结束……把主卧主灯调成暗档吧。
  [2] assistant  {"name":"observe_home","arguments":{}}
  [3] user       observation: {"ok":true,"data":{"rooms":[主卧、次卧、客厅、厨房、卫生间、阳台]}}
  [4] assistant  {"name":"inspect_room","arguments":{"room_id":"room_master"}}
  [5] user       observation: 主卧夜灯、主卧主灯（只有摘要，没有 mode）
  [6] assistant  {"name":"inspect_device","arguments":{"device_id":"device_master_light"}}
  [7] user       observation: on=true, mode=bright, set_mode.enum=[dim,bright]
```

模型这时只再吐一步：

```text
assistant  {"name":"execute_action","arguments":{"device_id":"device_master_light","action":"set_mode","params":{"mode":"dim"}}}
```

然后把这句 assistant 和工具回执 `state_after.mode=dim` append 上去，下一次再 finish。规则头不会再出现第四遍。

```text
              现行（每轮一张新 user）          应改成（messages 追加）
第 1 轮        ~2.1k                           system + user，说明书只付一次
第 4 轮        ~4.9k，工具表再印一遍            只比第 3 轮多一对 assistant / observation
第 5 轮        ~5.4k                           再多一对
重复付的       规则头 ×5，工具 schema ×5        0
```

## 4. 我们应该怎么改

应该。和 SimuHome 同一条路：先建好 messages，循环里只 append 模型输出和观察结果。不要再每回合 `build_a_prompt`。

SimuHome 的循环就是：

```text
messages = [system, few-shot..., 本轮 user]
loop:
  调 LLM(messages)
  messages.append(assistant, 模型刚吐的 JSON)
  跑工具
  messages.append(user, "observation: " + 回包)
直到 finish
```

我们对应过去：

```text
第 1 轮
  messages = [
    system   A 的短规则（怎么用四个工具、灯的三种能力、越界、finish）
    user     这一句用户话
  ]
  调 complete(messages)

以后每轮
  messages.append(assistant, 上一轮模型原文)
  messages.append(user, observation: 上一轮工具 result)
  再调 complete(messages)
  不再填 A_policy.md，不再把历史 json.dumps 进正文
```

C 已经在攒 `history`（assistant 决策 + events）。缺的是把这份 history 当成 API 的 messages 往下传。协议报错也当成 observation append，例如 `{"ok":false,"error":{"code":"TOO_MANY_TOOL_CALLS"}}`。

system 只写 A 怎么干活，不要把 T1–T5 的出题规则写进去。那些是 D2 的事。few-shot 可以后加，SimuHome 有、我们现在没有也能跑通 T1；先把 append 做对。

DeepSeek 可以继续让模型在 content 里吐 `{"name","arguments"}`，观察用 `role=user` + `observation:`，和 SimuHome 一致。官方 `tools` + `role=tool` 是后一步，不挡这一步。

不要做的：

```text
不要  每回合重新 render A_policy.md
不要  只把本轮观察发出去、丢掉前面的 messages
不要  把 history 再当成正文附件塞回一条新 user
不要  为了省事把 observe_home 回包扩成带工具参数
```

动手时改 `A_policy.py` / `DeepSeek_client.py`（A 持有会话 messages），`C_episode_runner` 继续提供 events。提示词从「每轮填七个坑的考卷」收成一份只出现一次的 system。
