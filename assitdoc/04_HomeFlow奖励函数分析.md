# HomeFlow 奖励函数分析（论文原文版）

> 来源：`论文/方法相关的论文/19_2026_arXiv_HomeFlow-Data-Flywheel-Smart-Home_数据飞轮智能家居训练_中.txt`
> 交叉参考：`doc/03_HomeFlow中HomeEnv面向SFT与强化学习的调整分析.md` 的 4.3–4.5 节
> 本文只做分析：公式按论文摘录；数值例子中的演示系数已单独标注。

## 0 一屏

```text
HomeFlow 的奖励是两级结构，全部由环境规则计算（不依赖 LLM 打分）：

① 终端验证奖励（定义"任务成功"）：
   R(s_T, Φ) = Σ_{k=1..K} φ_k(s_T)
   含义：终局状态满足几个条件就给几分，部分完成有部分分

② 逐步奖励（RLVE 实际训练使用的）：
   r_t = λ_prog·(m_t − m_{t−1}) + λ_succ·1[t=T ∧ m_T=1] − c_audit·1[blocked(a_t)]
   m_t = (1/K)·Σ_k φ_k(s_t)     ← 第 t 步时的条件完成率

三个组成部分：
   进度项（密集引导） + 成功项（终局大奖） + 审计惩罚（安全约束）
```

## 1 公式拆解

```text
符号            含义
──────────────────────────────────────────────────────────────
Φ = {φ1..φK}    K 个布尔谓词（对家庭状态求值的"条件"）
s_t             第 t 步之后的环境状态
m_t             完成率 = 满足条件数 / K
blocked(a_t)    动作被 HomeEnv 防火墙拦截（非法/越界/危险）
λ_prog          进度项权重（表 9"任务完成权重"给的是 1.0）
λ_succ          终局成功权重（摘录未给具体数值）
c_audit         审计惩罚（附录三个规则组件，各自权重 0.2）
```

三项各自什么时候生效：

```text
进度项  λ_prog·(m_t − m_{t−1})
   状态比上一步更接近目标 → 正分
   状态没变（无效动作）    → 0
   丢了已完成条件（m 下降）→ 负分
   作用：把"一路走到成功"拆成每步都能拿到的密集信号

成功项  λ_succ·1[t=T ∧ m_T=1]
   只在最后一步、且全部条件满足时触发一次
   作用：保证"真正做完"才拿大奖，防止半成品收敛

审计项  −c_audit·1[blocked(a_t)]
   动作被环境拦截时扣分（尝试非法/越界/危险操作）
   作用：把试错限制在安全边界内，防止破坏环境刷分
```

## 2 数值例子（3 条件任务，演示）

任务条件（对应论文里的 Φ）：

```text
φ1 = 空调已开启
φ2 = 模式为制冷
φ3 = 目标温度为 22°C
K = 3

演示系数（标注来源）：
  λ_prog = 1.0   （表 9"任务完成权重 1.0"）
  c_audit = 0.2  （表 9 规则组件权重的量级示范；附录里违规单次 −1 × 权重）
  λ_succ = 1.0   （演示值；论文摘录未给出该系数的具体数字）
```

逐步计算：

```text
步骤  动作                 m_t     进度项      其它项         该步奖励
──────────────────────────────────────────────────────────────────
t1    turn_on（开空调）     1/3     +1/3 ≈ +0.33                +0.33
t2    set_mode(cool)       2/3     +1/3 ≈ +0.33                +0.33
t3    set_temp(3°C) 越界   2/3     0          blocked → −0.2   −0.20
t4    set_temp(22°C)       3/3     +1/3 ≈ +0.33                +0.33
t5    finish               3/3     0          m_T=1 → +1.0     +1.00
──────────────────────────────────────────────────────────────────
轨迹总奖励（演示）= 0.33+0.33−0.20+0.33+1.00 ≈ +1.79
```

两种反例（同一套公式自动产生的结果）：

```text
半途放弃：m 只到 2/3 → 没有成功项，总奖励只有两个进度项 ≈ +0.66
破坏约束：为调温度把别的设备乱改 → 某个 φ_k 从 1 变 0，进度项倒扣
```

注意：GRPO 训练时用的是"同一任务 G 条轨迹的组内相对优势"（论文 G=8），
单条奖励的绝对数值只影响排序，上面的数字用于理解公式形状。

## 3 论文的消融证据（表 3）

```text
模型                   成功率    平均工具调用   平均 Tokens
────────────────────────────────────────────────────────
HomeFlow-SFT            82.45%   2.01          113.8
HomeFlow-RL (ST)        86.46%   2.25           79.0
HomeFlow-RL (Full)      87.03%   2.07           89.1
```

论文给出的结论：

```text
· Full 比 SFT 提升 4.58 个百分点（87.03 vs 82.45）
· ST（只在最后一步给反馈的稀疏版）成功率 86.46%，但策略熵急剧下降、
  早期容易崩溃——稀疏反馈让探索死掉
· Full（逐步密集奖励）能维持探索
· Full 比 ST 平均工具调用少 8%（2.07 vs 2.25）：逐步信用分配
  让规划更简洁、更有目的性
· 结论：在可验证环境里，密集逐步奖励是必要的
```

## 5 设计要点总结

```text
① 可验证：目标写成状态布尔谓词集合 Φ → 奖励可程序判定，不依赖 LLM 评分
② 部分分：R 用"满足条件数"累计 → 缓解长程稀疏奖励
③ 终局大奖：只有 m_T=1 才给成功项 → 防半成品收敛
④ 防投机：非法/越界动作被拦截并扣分 → 不能靠破坏环境刷分
⑤ 约束成本：代码安全、代码长度、回合数三个规则组件 → 限制动作空间和开销
⑥ 防漂移：Full 变体加 KL（3e-3）约束到 SFT 参考模型，替代 ST 的熵正则
```

## 6 与你们项目的映射（直接可借的部分）

```text
论文概念                  你们项目里的对应物
──────────────────────────────────────────────────────────────
Φ = {φ1..φK}             task.conditions + keep（C-1..C-4 判定的目标条件）
m_t 每步完成率           目前没有逐步钩子；你们是任务结束后一次性判定
blocked(a_t) 惩罚        环境拒绝的动作（如 UNKNOWN_DEVICE、越界参数）
λ_succ 终局成功           finish 且 C 全过的终局判定
代码/长度/回合规则组件    你们对应的是动作合法性检查 + 轮数上限（评测里 10 轮）
GRPO 组内比较（G=8）     评测侧已有 GRPO 计划；组定义=同家庭初态+同请求+同目标
```

复现逐步 RLVE 需要补的关键件：环境 step 里"每步重新求值全部条件、
记录 m_t 与 Δm"的钩子（`doc/03` 的 4.3/4.4 已给出系统层设计）。
另外注意口径差异：论文 RL 训练用"3 回合检查"封顶，你们评测是 10 轮；
做对比实验时要把这个上限写清楚。
