# HomeFlow 中 HomeEnv 面向 SFT 与强化学习的调整分析

> 分析日期：2026-09-20  
> 分析对象：HomeFlow、SMH-Bench 两篇论文及其本地 TXT/PDF。  
> 核心问题：HomeFlow 对 HomeEnv 的功能补充、功能精简和边界限制，归根结底是否都是为了支持 SFT 与强化学习。

## 1. 核心结论

从 HomeFlow 的系统目标看，答案基本是肯定的：HomeEnv 的整体演化方向，是从“能够执行和验证 benchmark 动作的模拟器”，转变为“能够持续生产训练数据并承载在线策略优化的训练环境底座”。

但需要把“支持 SFT 与强化学习”拆成一条完整因果链：

```text
低成本、确定性的家庭状态模拟
                |
                v
把开放式用户意图编译为可验证目标
                |
                v
在环境中搜索并筛选成功轨迹
                |
                v
形成高质量 SFT 冷启动数据
                |
                v
让 SFT 模型进入在线环境继续 rollout
                |
                v
按每一步状态进展计算 RLVE 奖励
                |
                v
更新策略，再产生新的交互轨迹
```

所以，HomeFlow 的 HomeEnv 调整不只是在接口上“接入 SFT 和 RL”。它把环境改造成了整个数据飞轮的共同真值源：

| 阶段 | HomeEnv 提供的核心能力 |
|---|---|
| Blueprint 过滤 | 判断目标条件是否可执行、参数是否越界 |
| MCTS-Flow | 执行候选分支、验证终局、回传真实奖励 |
| SFT 数据构建 | 只保留环境验证成功的多轮轨迹 |
| RLVE rollout | `reset/step`、部分观察、实时状态更新 |
| RLVE 奖励 | 目标完成度增量、终局成功、非法动作惩罚 |
| SmartHome-Bench | 用相同状态真值评测训练后的模型 |

因此，更准确的结论是：

> HomeFlow 中 HomeEnv 的功能补充、轻量化和边界收紧，共同服务于“可验证后训练”。SFT 和 RLVE 是最终落点，Blueprint 与 MCTS-Flow 是连接模拟器和 SFT 的数据生产层，SmartHome-Bench 则负责验证训练收益。

不过，不能把论文里所有差异都解释成 HomeEnv 代码本体的调整。HomeMaker、Blueprint、MCTS-Flow、动态用户模拟器和 SmartHome-Bench 属于 HomeEnv 外围系统；SmartHome-Bench 没有单列自动化和纯查询任务，也不能证明 HomeEnv 删除了这些能力。

## 2. 首先区分四个对象

讨论“HomeFlow 调整了 HomeEnv”时，容易把四个层级混在一起：

```text
第一层：HomeEnv 核心状态引擎
  房间、设备、组件、属性、服务、状态转移

第二层：HomeEnv 训练封装
  Gym reset/step、pyexec 沙箱、观察、终止、奖励、审计

第三层：训练数据生产系统
  HomeMaker、Blueprint、MCTS-Flow、轨迹过滤

第四层：训练与评测系统
  SFT、RLVE、动态用户、SmartHome-Bench
```

论文明确展示了第二至第四层的大量新增能力，但没有公开 SMH-Bench 版和 HomeFlow 版 HomeEnv 的源代码差异。因此本文使用以下证据等级：

| 等级 | 含义 |
|---|---|
| 论文事实 | 论文明确给出接口、公式、提示或实验配置 |
| 强工程推断 | 系统若要按论文工作，工程上必须具备相应能力 |
| 未知 | 没有代码和版本记录，无法确认具体实现方式 |

## 3. HomeEnv 的角色发生了什么变化

### 3.1 在 SMH-Bench 中：评测执行器

SMH-Bench 的 HomeEnv 主要回答一个问题：模型给出的结果能否在固定家庭状态中正确执行并满足任务目标。

```text
固定 benchmark 样本
  初始家庭状态 H0
  用户请求
  对话历史
  用户记忆
  真实目标
        |
        v
模型输出动作或工具调用
        |
        v
HomeEnv 执行、记录状态差异
        |
        v
最终验证器判定通过/失败
```

它强调：

```text
同一动作可重复回放
参数类型和范围严格检查
非法动作不改变环境
最终状态满足目标
无关状态保持不变
DR 与 EIA 使用同一真值层
```

环境的主要消费者是 benchmark runner 和 evaluator。

### 3.2 在 HomeFlow 中：训练环境底座

HomeFlow 要求 HomeEnv 在一次实验中被反复创建、重置、分叉和推进，并在每一步产生训练信号。

```text
HomeMaker 采样家庭
        |
Blueprint 注册目标条件
        |
        +------------------------------+
        |                              |
        v                              v
MCTS 数据搜索                    RLVE 在线 rollout
分支执行与终局验证                逐步执行与逐步奖励
        |                              |
        v                              v
成功轨迹 -> SFT 数据              策略梯度更新
```

环境的消费者变成：

```text
Blueprint 过滤器
MCTS 搜索器
SFT 数据构建器
RL rollout worker
奖励计算器
训练后 benchmark runner
```

这意味着 HomeEnv 的设计优先级从“评分正确”扩展为：

```text
评分正确
  + 单步执行便宜
  + 可大量 reset
  + 可支持状态分支
  + 每步可观测
  + 每步可计算目标进度
  + 非法探索可阻断
  + 输出可直接转为训练轨迹
```

## 4. HomeFlow 补充或强化了哪些能力

### 4.1 Gym 风格的环境生命周期

论文附录给出：

```python
env = gym.make("HomeEnv-v0", home=HomeSampler.sample_test())
observation, reward, terminated, truncated, info = env.step({
    "name": "pyexec",
    "code": "device('1001').set_brightness(80)"
})
```

这一接口把 HomeEnv 从一个“执行若干设备服务的对象”提升为标准的序列决策环境。

```text
reset()
  输入：家庭配置、Blueprint、随机种子
  输出：初始观察、回合元信息

step(action)
  输入：代码或 API 动作
  输出：观察、奖励、terminated、truncated、info
```

它与训练阶段的关系如下：

| 用途 | 作用 |
|---|---|
| MCTS | 每次节点扩展都需要推进一个环境分支 |
| SFT | 将成功分支转换为顺序的观察—动作轨迹 |
| RLVE | rollout worker 可以按统一接口在线采样 |
| 评测 | 训练和测试共用相同执行语义 |

这个调整主要直接服务 MCTS 和 RLVE，并间接服务 SFT。

### 4.2 `pyexec` / Python 代码动作空间

HomeFlow 明确允许智能体生成 Python 代码片段或 API 调用。示例为：

```python
light = device("1001")
if light.state == "off":
    light.turn_on()
light.set_brightness(80)
print(light.brightness)
```

相比 SMH-Bench 的单个结构化动作：

```json
{
  "did": "1001",
  "locator": "set_brightness",
  "arguments": {
    "brightness": 80
  }
}
```

代码动作空间可以在一次环境步中表达查询、条件判断和多个设备操作。它对训练的价值是：

```text
SFT：
  可以学习完整的环境操作程序，而不只学习一个扁平 API 参数对象。

RLVE：
  策略可探索多步骤代码方案，环境用真实执行结果提供反馈。

MCTS：
  同一状态前缀下可以展开不同代码实现，比较其可执行结果。
```

它也增加了新的失败面：语法错误、运行时异常、危险反射、超长代码和一次调用内的无关操作。因此 HomeFlow 同时增加了代码审计和长度限制。

### 4.3 可注册的目标条件与统一验证器

HomeFlow 把任务目标表示为布尔谓词集合：

```text
Phi = {
  phi_1(s): device("1001").state == "on",
  phi_2(s): device("1001").brightness > 60
}
```

环境需要支持：

```text
注册条件
  -> 每步重新求值
  -> 计算已完成条件数
  -> 判断是否全部完成
  -> 记录哪个条件何时完成或失效
```

这一调整同时连接 SFT 和 RL：

```text
Blueprint
  把自然语言生活目标编译为 Phi

MCTS
  用“所有 phi_k 是否在终局成立”筛选成功轨迹

SFT
  只学习通过终局验证的轨迹

RLVE
  用每一步 Phi 完成率变化形成密集奖励
```

如果没有统一条件层，SFT 仍会依赖 LLM judge 过滤，RL 也无法获得稳定的可验证奖励。该能力是 HomeFlow 数据飞轮的中心连接点。

### 4.4 逐步完成度与奖励钩子

HomeFlow 定义：

```text
m_t = 在状态 s_t 中满足的条件数 / 条件总数

r_t = lambda_prog * (m_t - m_(t-1))
    + lambda_succ * 1[终局全部完成]
    - c_audit * 1[动作被拦截]
```

SMH-Bench 只需要在执行结束后判断样本是否通过；HomeFlow 需要环境在每一步提供中间进度。

示例：

```text
目标条件：
  phi_1 = 空调已开启
  phi_2 = 模式为制冷
  phi_3 = 目标温度为 22°C

t0：0/3 完成
t1：执行 turn_on       -> 1/3，获得正进度
t2：执行 set_mode      -> 2/3，获得正进度
t3：执行 set_temp(22)  -> 3/3，获得正进度和终局成功奖励
```

这个调整直接服务 RLVE。MCTS 的论文公式使用终局二值成功，不依赖同样的逐步奖励；SFT 只消费成功轨迹，也不直接优化该奖励。

### 4.5 运行时动作审计

论文说明环境会阻止不存在的功能、越界参数、不安全或任务无关操作，并在 RLVE 中对被阻止动作施加惩罚。训练配置还限制：

```text
禁止或惩罚：
  getattr
  setattr
  eval
  exec
  compile

代码最大长度：
  1000 tokens

RL 交互范围：
  最多 3 个回合
```

审计器承担三类职责：

| 职责 | 对 SFT 的价值 | 对 RLVE 的价值 |
|---|---|---|
| 设备合法性 | 排除不可执行轨迹 | 给非法探索确定性负反馈 |
| 代码安全 | 防止训练数据包含危险程序 | 防止策略通过沙箱漏洞获取奖励 |
| 任务相关性 | 减少过度操作示范 | 抑制奖励投机和无关状态修改 |

如果环境只判断最终目标是否成立，模型可能通过修改大量无关设备碰巧完成任务。审计和边界约束让奖励更接近“按正确方式完成任务”。

### 4.6 部分可观测的执行反馈

HomeFlow 把任务形式化为 POMDP。模型不能直接读取完整底层状态，只能获得：

```text
用户话语
主动查询得到的设备信息
代码或 API 执行结果
运行时错误
环境返回的局部观察
```

部分可观测性服务于两类训练目标：

```text
SFT 学习：
  何时查询设备能力
  何时查询当前状态
  如何根据错误修正动作
  何时请求用户澄清

RLVE 学习：
  在信息获取成本和任务推进之间权衡
  从执行失败中恢复
  在多轮状态变化中更新策略
```

它也避免模型直接读取任务谓词或完整真值状态形成信息泄漏。

### 4.7 状态快照、复制或回滚能力（工程推断）

论文没有公开具体实现，但 MCTS-Flow 从同一个前缀展开多个候选动作：

```text
共同状态 s_v
  +-> agent candidate 1 -> s_1
  +-> agent candidate 2 -> s_2
  +-> agent candidate 3 -> s_3
```

工程上必须存在某种状态分支方案：

```text
完整深复制
快照与回滚
从根状态重放动作前缀
持久化状态或写时复制
```

具体采用哪一种属于未知项。但“能够从相同前缀独立执行多个候选”是 MCTS-Flow 成立的必要条件。

这一能力首先服务 MCTS 数据生成，最终服务 SFT；在线 RLVE 通常更需要高效 reset 和批量独立环境，而不一定需要树分支。

### 4.8 HomeMaker 接入与环境分布生成

HomeMaker 程序化采样天气、布局、房间、设备和初始状态。严格来说，它是 HomeEnv 的上游环境生成器，不属于状态转移内核。

```text
设备规格池 + 房间先验 + 天气 + 用户画像
                      |
                      v
                  HomeMaker
                      |
                      v
              初始家庭状态 s0
                      |
                      v
                   HomeEnv
```

它对后训练的作用是扩展初始状态分布：

| 阶段 | 作用 |
|---|---|
| SFT | 避免所有示范来自少数固定家庭 |
| RLVE | 让策略在不同家庭配置上在线探索 |
| 评测 | 检查模型是否只记住固定设备和房间模板 |

HomeMaker 是“为了训练而增加的环境供给系统”，但不能算成 HomeEnv 内核本身的功能。

## 5. HomeFlow 精简了什么

HomeFlow 的轻量化主要发生在世界模型和训练协议，而非简单删除设备功能。

### 5.1 符号状态代替连续物理

设备服务通常直接更新属性：

```text
set_target_temperature(22)
  -> target_temperature = 22

set_brightness(80)
  -> brightness = 80
```

论文没有展示：

```text
房间热力学
光照传播
空气流动
功耗模型
网络延迟
执行器响应时间
传感器噪声
设备故障
状态漂移
```

这项精简与训练直接相关：

```text
符号写入成本低
  -> 单步环境执行更快
  -> MCTS 可以展开更多候选
  -> SFT 可以生成更多验证轨迹
  -> RLVE 可以完成更多 rollout
```

同时，状态条件能够即时判断，避免真实物理中的长时间等待和延迟奖励。

### 5.2 确定性状态转移代替随机环境

相同状态下执行相同动作，会得到相同结果。确定性对训练的价值是：

```text
降低标签噪声
降低 MCTS 节点评估方差
让 SFT 成功轨迹可重复验证
让 RL 奖励更容易归因到当前动作
便于调试和复现实验
```

代价是策略没有学习传感器误差、设备失败和延迟恢复。论文把确定性仿真列为现实迁移限制，说明这是有意识的建模边界。

### 5.3 布尔条件压缩开放式生活目标

Blueprint 最终把复杂生活需求压缩为有限条件集合：

```text
“我要在书房舒服地练习书法”
            |
            v
空调状态 == on
空调模式 == heat
目标温度位于 [23.5, 24.5]
灯光亮度位于 [85, 100]
色温位于 [5000, 6500]
音箱静音 == true
```

这是一种目标表示精简。它丢弃了难以机器判定的体验维度，但带来：

```text
可自动过滤 SFT 数据
可计算 MCTS 终局成功
可计算 RL 条件完成率
可比较不同动作路径
```

因此，这项精简几乎完全由可验证训练需求驱动。

### 5.4 缩短 RL 交互边界

训练配置把交互限制在最多 3 个回合。这个限制不一定是 HomeEnv 的永久能力上限，更可能是 RL 实验的 rollout 配置。

它控制：

```text
上下文长度
用户模拟器调用成本
策略采样成本
环境步数
信用分配跨度
失败轨迹资源消耗
```

这直接服务强化学习的成本控制。它也限制了论文结果对真实长期家庭交互的代表性。

### 5.5 约束代码长度和危险操作

1000-token 代码上限及危险关键词限制，属于动作空间收缩：

```text
开放 Python
    |
    | 去除反射、动态执行和超长程序
    v
受控的设备操作子语言
```

它使 `pyexec` 仍保留条件与多操作表达能力，同时降低沙箱逃逸、奖励投机和 rollout 失控的风险。这主要服务 RL 安全和训练稳定，也提升 SFT 轨迹质量。

## 6. 哪些现象不能视为 HomeEnv 功能精简

### 6.1 SmartHome-Bench 少两个任务类别

HomeFlow 的 SmartHome-Bench 包含五类：

```text
原子控制
组合控制
模糊意图
上下文多轮
个性化记忆
```

SMH-Bench 另外包含：

```text
自动化任务调度
环境基础查询
```

这只能证明 HomeFlow 的主 benchmark 没有单独评测这两个类别，不能证明 HomeFlow 版 HomeEnv 删除了自动化或查询能力。

原因如下：

```text
查询能力：
  HomeFlow 智能体提示明确要求查询设备手册和状态。
  因此查询仍是执行流程的一部分，只是没有作为独立纯查询任务评分。

自动化能力：
  论文没有给出足够信息确认保留或删除。
  缺少 benchmark 类别不能推出环境内核没有自动化对象。
```

### 6.2 `pyexec` 看起来接口更少

一个 `pyexec` 工具可以替代多个结构化查询和控制工具，但它没有真正消除复杂性，而是把复杂性转移到代码解释器和安全沙箱：

```text
结构化工具复杂性
  schema、locator、arguments、多次调用

转移为

代码沙箱复杂性
  parser、runtime、权限、超时、审计、异常、输出捕获
```

所以工具数量减少不等于环境实现更简单。

### 6.3 目标统一为谓词不等于任务语义更简单

最终验证条件可能很短，但生成一个正确 Blueprint 仍需要理解用户画像、生活场景、设备依赖和参数边界。复杂性从评测时转移到了任务编译阶段。

```text
自然语言中的模糊语义
        |
        | GPT-5 生成 + 环境检查 + schema 检查 + 语义过滤
        v
有限、稳定的布尔谓词
```

这是“前置编译复杂度，简化训练期验证”，并非把任务本身简单化。

## 7. 限制边界为什么对 SFT 必要

SFT 学习的是数据中出现的动作模式。如果合成轨迹包含错误设备、越界参数或多余操作，模型会把这些行为一并模仿。

HomeFlow 的边界控制形成如下数据过滤链：

```text
LLM 生成候选 Blueprint
        |
        +-> 条件可解析吗
        +-> 设备存在吗
        +-> 属性和服务存在吗
        +-> 参数位于硬件范围吗
        +-> 与用户画像和意图一致吗
        |
        v
MCTS 生成候选轨迹
        |
        +-> 每个动作可执行吗
        +-> 是否触发代码审计
        +-> 终局是否满足全部目标
        |
        v
只保留验证成功的轨迹进入 SFT
```

因此，边界限制对 SFT 的核心价值是“定义正样本”。

纯文本角色扮演只能判断一段对话看起来是否合理；HomeEnv 可以判断动作在具体设备上是否真的有效。例如：

```text
文本上看似合理：
  “把主卧空调切换为自然风模式。”

设备事实：
  该空调只支持 heat / cool / auto / dry / fan_only。

环境验证：
  natural 不在枚举中，调用失败。

训练数据修正：
  查询设备规格后，把“自然风”接地为 fan_only，或请求澄清。
```

这正是 HomeFlow-SFT 相比纯文本 role-play 的主要方法价值。

## 8. 限制边界为什么对强化学习更必要

强化学习会主动寻找获得高奖励的捷径。环境边界不完整时，策略可能学习利用模拟器漏洞，而不是学习智能家居能力。

```text
可能的奖励投机：

直接修改内部属性，绕过设备服务
使用 eval/exec 访问未授权对象
一次性关闭所有设备以碰巧满足部分目标
输出超长代码枚举所有可能设备
读取 Blueprint 真值条件而非主动查询环境
通过异常或日志泄漏获取完整状态
```

因此，RLVE 需要比普通 benchmark 更严格的动作边界：

| 边界 | 防止的问题 |
|---|---|
| 设备服务白名单 | 绕过设备能力直接改状态 |
| 参数类型与范围 | 用非法值快速满足谓词 |
| Python 危险操作限制 | 沙箱逃逸和内部状态访问 |
| 部分可观测性 | 读取完整真值和目标答案 |
| 代码长度限制 | 暴力枚举和失控程序 |
| 回合上限 | 无限查询或拖延终止 |
| 动作审计惩罚 | 把非法试探变成无成本探索 |
| 目标进度奖励 | 缓解只有终局成功的稀疏反馈 |

对 RL 来说，环境既是世界模型，也是奖励函数和安全边界。三者有任何一个存在漏洞，训练结果都可能失真。

## 9. 调整与训练阶段的对应关系

| HomeFlow 调整 | MCTS / 数据合成 | SFT | RLVE | Benchmark |
|---|---:|---:|---:|---:|
| YAML 设备规格与随机实例化 | 高 | 高 | 高 | 中 |
| HomeMaker 多样家庭生成 | 高 | 高 | 高 | 中 |
| Blueprint 条件注册 | 高 | 高 | 高 | 中 |
| Gym `reset/step` | 高 | 间接 | 高 | 高 |
| `pyexec` / API 沙箱 | 高 | 高 | 高 | 高 |
| 部分可观测反馈 | 高 | 高 | 高 | 高 |
| 终局全条件验证 | 高 | 高 | 高 | 高 |
| 逐步条件完成率 | 低 | 低 | 核心 | 低 |
| 动作审计与阻断 | 高 | 高 | 核心 | 高 |
| 环境复制/回滚 | 核心 | 间接 | 低 | 低 |
| 动态用户模拟器 | 中 | 低 | 核心 | 低 |
| 三回合上限 | 低 | 低 | 高 | 低 |
| SmartHome-Bench 五类任务 | 低 | 低 | 低 | 核心 |

表中“间接”表示该能力不参与 SFT 损失本身，但决定 SFT 数据如何产生。

## 10. “归根结底为了 SFT 与强化学习”应如何表述

可以分三个层次回答。

### 10.1 从论文研究目标看：是

HomeFlow 的标题和方法链路都围绕智能体训练。论文把 HomeEnv 称为连接数据生成、轨迹扩展和策略优化的统一接地信号源。它的核心贡献也按以下顺序展开：

```text
HomeEnv / HomeMaker
  -> Blueprint
  -> MCTS-Flow
  -> SFT
  -> step-wise RLVE
```

因此，HomeEnv 的总体调整方向由后训练需求驱动。

### 10.2 从单个功能看：各项能力服务的阶段不同

```text
主要服务 SFT 数据生产：
  Blueprint 可执行性过滤
  MCTS 分支验证
  成功轨迹抽取
  环境多样化

主要服务 RLVE：
  Gym 在线生命周期
  每步完成率
  逐步奖励
  动态用户 rollout
  KL/熵等训练约束的环境配合

两者共同需要：
  确定性状态转移
  pyexec/API 执行
  部分可观测反馈
  参数验证
  动作审计
  可重置家庭状态
```

MCTS-Flow 不是模型训练算法，但它生产 SFT 冷启动数据，所以属于训练链路而非独立目标。

### 10.3 从系统工程看：更深层目标是“可验证、可规模化的策略学习”

单说“支持 SFT 和强化学习”仍然偏表面。HomeFlow 真正需要的是：

```text
开放式家庭任务
        |
        v
机器可执行、可检查的状态目标
        |
        v
可规模化搜索和采样的交互环境
        |
        v
可信的监督标签与强化奖励
```

所以最底层的设计目标是让训练信号具备四个性质：

| 性质 | 对应设计 |
|---|---|
| 正确 | 以真实状态转移验证动作结果 |
| 稠密 | 每一步计算条件完成度变化 |
| 低成本 | 符号化、确定性的轻量模拟 |
| 难以投机 | 沙箱、参数边界、动作审计和部分可观测性 |

SFT 和 RLVE 是这套训练信号被消费的两个阶段。

## 11. HomeFlow 的本质不是“更简单的 HomeEnv”

HomeFlow 对复杂度进行了重新分配：

```text
被削减的复杂度：
  连续物理
  随机噪声
  真实设备延迟
  协议异构
  长时间环境演化

被增加的复杂度：
  Gym 生命周期
  Python 执行沙箱
  目标条件注册
  每步奖励
  动作审计
  MCTS 状态分支
  动态用户交互
  大规模 rollout
```

这是一种训练导向的复杂度交换：

> 降低世界模拟的物理复杂度，换取更高的搜索和 rollout 吞吐量；增加验证、审计和状态管理复杂度，换取可用的 SFT 标签与 RL 奖励。

因此，不能只根据“确定性状态更新”判断 HomeFlow 更简单。它的单步物理计算较轻，完整训练系统更重。

## 12. 与 SMH-Bench 的根本分工

```text
SMH-Bench 问：
  给定一个固定任务，模型到底做对了吗？

HomeFlow 问：
  如何持续生成可验证经历，让模型学会做对？
```

这导致 HomeEnv 的使用方式不同：

| 维度 | SMH-Bench | HomeFlow |
|---|---|---|
| 主要用途 | 测量能力 | 生产能力 |
| 环境实例 | 固定 benchmark 家庭 | HomeMaker 大量采样 |
| 执行频率 | 每个模型运行固定样本 | 数据生成和训练中反复 rollout |
| 奖励 | 最终通过/失败 | 进度、成功、审计组成的逐步奖励 |
| 状态分支 | DR 回放或 EIA 单轨迹 | MCTS 多分支搜索 |
| 错误作用 | 记为评测失败 | 转为过滤信号或负奖励 |
| 环境边界 | 保证评分公平 | 同时防止训练数据污染和奖励投机 |

SMH-Bench 可以容忍环境执行较慢，只要评测准确且规模可接受。HomeFlow 的训练成本会把任何单步开销放大，因此更强烈地要求轻量化、确定性和可批量重置。

## 13. 仍无法确认的代码级调整

论文没有公开足够代码证据确认：

```text
HomeFlow 是否直接 fork 了 SMH-Bench 的 HomeEnv
两者谁先开发、哪个分支是共同主干
HomeFlow 是否删除了自动化执行对象
HomeFlow 是否保留 SMH 的无关状态严格比较
MCTS 使用深复制、快照回滚还是动作重放
pyexec 是否为每步新建进程或复用解释器
并行环境如何隔离 Python 全局状态
条件表达式是否使用安全 AST 或 Python eval
每秒环境步数和单环境内存占用
训练时是否真正并行运行大量 HomeEnv 实例
```

因此，当前能确认的是论文层面的功能架构，不能声称已经获得两版 HomeEnv 的源码 diff。

## 14. 对复现设计的直接启示

如果目标是复现 HomeFlow，HomeEnv 不应先追求设备数量，而应先满足训练闭环：

```text
第一优先级：状态与执行真值
  类型化设备属性
  服务参数校验
  确定性状态转移
  安全条件解释器

第二优先级：训练环境契约
  reset
  step
  observation
  terminated / truncated
  info
  随机种子

第三优先级：数据生产
  Blueprint 条件注册
  终局验证
  状态快照
  分支复制或回滚
  轨迹日志

第四优先级：RLVE
  每步条件完成率
  进度奖励
  终局奖励
  审计惩罚
  批量并行环境
```

若顺序颠倒，先扩充大量设备 YAML，却没有稳定的状态复制、条件求值和逐步奖励，仍然无法运行 MCTS 和 RLVE。

复现时还应把以下边界分开配置，避免把论文实验限制写死到核心环境：

```text
HomeEnv 能力边界：
  支持哪些状态、服务和动作

pyexec 安全边界：
  允许哪些 Python 语法和对象

任务边界：
  Blueprint 允许生成哪些目标条件

训练预算边界：
  最大回合数、最大代码长度、最大 token、超时

评测边界：
  SmartHome-Bench 实际覆盖哪些任务类别
```

这样才能判断某项能力究竟被模拟器删除、被任务生成器禁用，还是只在某次训练配置中受限。

## 15. 最终判断

HomeFlow 对 HomeEnv 的调整可以归纳为三组：

```text
功能补充
  Gym 环境契约
  pyexec/API 沙箱
  目标条件注册
  逐步完成度与奖励
  动作审计
  状态分支和高频 reset 能力

功能轻量化
  符号属性更新
  确定性状态转移
  布尔谓词目标
  短回合训练配置

边界收紧
  设备服务白名单
  参数类型和范围
  Python 危险操作限制
  代码长度限制
  部分可观测性
  非法动作惩罚
```

这三组变化指向同一个系统目标：让 HomeEnv 同时能够生产可信的监督轨迹，并提供稳定、稠密、难以投机的在线强化学习信号。

最终可以作出以下判断：

> HomeFlow 中 HomeEnv 的演化，归根结底是为了支持以环境验证为核心的后训练。SFT 需要它定义和筛选正确轨迹，RLVE 需要它持续产生状态、观察、奖励和安全边界。轻量化负责提高数据生成与 rollout 吞吐量，功能补充负责形成训练闭环，边界限制负责保证标签和奖励可信。

但应保留一个重要限定：论文没有公开两版 HomeEnv 的源码差异。当前结论描述的是系统功能和设计动机，不能等同于已经确认每一项代码增删。
