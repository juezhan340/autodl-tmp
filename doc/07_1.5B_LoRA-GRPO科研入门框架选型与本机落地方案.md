# 1.5B LoRA-GRPO 科研入门框架选型与本机落地方案

> 分析日期：2026-09-21  
> 目标：在保留 MiniMind 学习价值的同时，为 Qwen2.5-1.5B 级别模型搭建可复现、可扩展的 LoRA-GRPO + HomeEnv 研究框架。  
> 本机：单张 NVIDIA GeForce RTX 4090，24,564 MiB 显存，系统内存约 1TiB。

## 先看结论

```text
MiniMind：
  继续用于理解 Transformer、SFT、GRPO、工具调用和奖励计算的内部实现。
  不作为 1.5B 外部模型的长期训练框架。

1.5B LoRA-GRPO 主框架：
  第一推荐：Transformers + TRL + PEFT + Accelerate
  第二推荐：ms-swift
  第三推荐：OpenRLHF
```

```text
本机最合适的落地形态：

Qwen2.5-1.5B-Instruct（Transformers 权重）
                  |
                  v
       Transformers + PEFT LoRA
                  |
                  v
       TRL SFTTrainer 先做 HomeFlow SFT
                  |
                  v
       TRL GRPOTrainer + HomeEnv
                  |
                  v
       HomeEnv verifier 直接产生奖励
                  |
                  v
       单卡 RTX 4090 完成短序列 LoRA-GRPO
```

这里需要补充一个判断：**第一推荐符合省显存要求，但省显存不是框架名称自动带来的，而是由 PEFT、gradient checkpointing、序列长度、rollout 方式、reference model 和 logits 处理共同决定。**

```text
TRL + PEFT：     显存可控，科研可读性最好，但需要手动配置
ms-swift：       默认显存优化更积极，快速跑通更省事
OpenRLHF：       显存编排能力最强，但单卡配置复杂度最高
```

最终建议是：**MiniMind 保留为“看懂算法”的实验台，TRL 作为 1.5B HomeFlow 科研主线，ms-swift 作为省显存和工程吞吐对照，OpenRLHF 留作多轮 Agent 和更大规模实验的备选。**

## 适用范围：这是 LLM Agent 交叉研究的常见路线

这个方案可以视为交叉研究中的一条常见入门路线，但不能泛化为所有强化学习论文的统一框架。

```text
传统数值状态/动作的强化学习：
  Gymnasium 环境
        +
  Stable-Baselines3 / CleanRL / RLlib

语言模型生成文本或工具调用的强化学习：
  Transformers 模型
        +
  PEFT LoRA
        +
  TRL / OpenRLHF / veRL
        +
  自定义环境和 reward verifier
```

Gymnasium 的标准重点是 `reset()`、`step()`、`observation`、`reward`、`terminated` 和 `truncated`；Stable-Baselines3 的自定义环境也要求遵循 Gym 接口。这套路线适合机器人控制、交通调度、资源分配、游戏和其他数值状态空间任务。参考：[Gymnasium 环境创建文档](https://gymnasium.farama.org/main/tutorials/environment_creation/) 和 [Stable-Baselines3 自定义环境文档](https://stable-baselines3.readthedocs.io/en/sde/guide/custom_env.html)。

HomeFlow 的区别在于：模型不是直接输出一个离散动作编号或连续控制向量，而是生成文本，再经过工具调用解析，环境返回文本观察，模型继续生成。因此训练器还要处理：

```text
文本生成
  -> tool_call 解析
  -> HomeEnv 执行动作
  -> tool_response 拼回上下文
  -> 保存 completion token 和 logprob
  -> 结算整条 episode reward
```

这正是 TRL、OpenRLHF 等 LLM 后训练框架所解决的问题。TRL 官方文档把 `GRPOTrainer`、自定义 reward、PEFT 以及 Gymnasium-style 的 OpenEnv 连接在同一套训练生态中。参考：[TRL 官方文档](https://huggingface.co/docs/trl/index) 和 [TRL GRPOTrainer 文档](https://github.com/huggingface/trl/blob/main/docs/source/grpo_trainer.md)。

所以我们的方案应采用混合边界：

```text
HomeEnv 核心：       保留框架无关的 reset / step / snapshot / reward
Gymnasium adapter：  提供标准环境接口，方便评测、单元测试和传统 RL 对照
TRL adapter：        提供文本生成、工具循环、LoRA-GRPO 和 token-level loss
```

这样写入论文时，框架只是实验基础设施，真正的研究变量可以放在：

```text
HomeEnv 状态建模
工具调用协议
任务生成方法
reward shaping / verifier
SFT 到 RL 的数据衔接
LoRA 与全量更新的效率差异
```

这比把 MiniMind 自定义训练代码包装成一个“全新框架”更符合交叉研究的常见做法，也更容易让读者复现实验。

## 1. 为什么要从 MiniMind 切换到标准框架

MiniMind 的价值在于代码短、模块集中、训练流程可读。当前仓库已经覆盖 MiniMind 自己的 SFT、LoRA、GRPO、CISPO 和多轮 Tool-Use RL，这非常适合回答下面这些问题：

```text
GRPO 如何计算组内相对优势？
旧策略 logprob、reference logprob 和当前策略 logprob 如何对齐？
工具调用结果如何重新拼进对话？
环境奖励如何进入整条轨迹？
为什么奖励没有组内方差时，GRPO 几乎没有有效梯度？
```

但当前 MiniMind 训练代码把模型构造、checkpoint 格式、tokenizer、rollout 和优化器绑定在 MiniMind 自己的实现上：

```text
当前 train_grpo.py
  -> MiniMindConfig
  -> MiniMindForCausalLM
  -> 自定义 checkpoint
  -> 自定义 rollout_engine
  -> 自定义 reward_model
```

这对学习很合适，对 Qwen2.5-1.5B 研究不合适。若继续在 MiniMind 上硬改，会同时承担四类工作：

```text
模型适配：       MiniMind 权重结构改成 Hugging Face Qwen 结构
LoRA 适配：       当前 LoRA 只覆盖部分方形 Linear 层
训练逻辑适配：   policy/reference/logits 与 Qwen tokenizer 对齐
工程适配：       checkpoint、量化、vLLM、评测和分布式配置重新维护
```

这会让研究问题被框架移植问题遮住。更合理的边界是：

```text
MiniMind：验证算法概念和 HomeEnv 契约
标准框架：验证 1.5B 模型的 LoRA-GRPO 效果
```

## 2. 选框架时真正需要哪些能力

我们要的不是一个“能跑 GRPO 命令”的工具，而是一条可以观察、修改和复现实验的训练链路。

```text
模型加载层
  -> 能加载 Qwen2.5-1.5B Transformers 权重

参数高效训练层
  -> LoRA / QLoRA
  -> 明确 target_modules、rank、alpha 和 adapter checkpoint

RL 训练层
  -> GRPO
  -> 自定义 reward
  -> 可记录 group rewards、advantage、KL、completion mask

环境交互层
  -> 多轮工具调用
  -> 每个 rollout 独立 reset
  -> HomeEnv 状态和 reward 可追踪

采样层
  -> 先支持单卡 Transformers rollout
  -> 之后可以切 vLLM/SGLang

实验层
  -> 可固定随机种子
  -> 可恢复 checkpoint
  -> 可比较等步数、等 token、等 GPU-hours
```

因此不能只按“谁的 GRPO 实现最强”排序。需要同时看：

```text
科研可读性  +  自定义 HomeEnv 难度  +  单卡资源适配  +  后续扩展成本
```

## 3. 显存标准：框架支持 LoRA 不等于训练一定省显存

### 3.1 需要分别控制的显存来源

```text
模型权重：       1.5B BF16 约 3GB
可训练参数状态： LoRA 只为 adapter 保存梯度和 Adam 状态
反向激活：       与 batch、prompt 长度、completion 长度强相关
reference：      可能额外占一份基座权重
reward model：    HomeEnv verifier 可以直接移除这一项
rollout KV cache：取决于 rollout 数、上下文和推理引擎
vocabulary logits：大词表下可能成为最大的临时张量
```

所以，省显存标准应该按下面的顺序检查：

```text
1. 是否只训练 LoRA adapter？
2. 是否开启 gradient checkpointing 并关闭 use_cache？
3. 是否把 batch、group size、prompt 和 completion 限制在可控范围？
4. 是否移除了额外 reward model？
5. 是否避免在同一张卡上同时堆放 vLLM、policy、reference 和 optimizer？
6. 是否只计算需要的 completion token logprob，而不是保留完整 logits？
7. 是否真的需要 QLoRA，还是普通 BF16 LoRA 已经足够？
```

### 3.2 三套框架的显存判断

| 框架 | 能否省显存 | 省显存方式 | 本机判断 |
|---|---|---|---|
| TRL + PEFT | 可以 | LoRA、gradient checkpointing、短序列、可选 vLLM sleep mode、可关闭额外 reward model | 1.5B LoRA-GRPO 可行；首轮使用 Transformers 原生 rollout |
| ms-swift | 可以，默认更积极 | 默认 gradient checkpointing、LoRA/QLoRA、LoRA 权重同步、可选关闭 reference、vLLM rollout | 1.5B 最容易快速跑通；适合作为显存配置对照 |
| OpenRLHF | 可以，控制项最多 | LoRA/QLoRA、DeepSpeed、模型 colocate、vLLM sleep、offload 和动态 batch | 1.5B 可以做，但单卡上系统开销和排错成本最高 |

TRL 官方文档明确区分了 vLLM 的 colocate 和 server 两种模式：colocate 会和训练模型共享 GPU，可能产生显存竞争；server 模式需要独立 GPU。单卡 4090 第一阶段不能把 vLLM 当作默认省显存方案。必要时再尝试 sleep mode，但它是用主机和 GPU 间的数据搬运换显存，速度会下降。参考：[TRL vLLM 集成文档](https://github.com/huggingface/trl/blob/main/docs/source/vllm_integration.md)。

ms-swift 默认开启 gradient checkpointing 来降低训练显存，并支持 LoRA 权重同步；其文档还说明将 GRPO 的 `beta` 设为 0 可以不加载 reference model。但 `beta=0` 会改变 KL 约束实验，不能为了省显存而不记录这一算法变化。参考：[ms-swift GRPO 文档](https://github.com/modelscope/ms-swift/tree/main/docs/source/Instruction/GRPO)。

OpenRLHF 同时提供 LoRA/QLoRA、多轮 Agent executor、模型 colocate 和 vLLM sleep 等选项，显存控制能力强；代价是 Ray、DeepSpeed 和 rollout 进程管理会增加单卡实验复杂度。参考：[OpenRLHF 官方 README](https://github.com/OpenRLHF/OpenRLHF)。

### 3.3 1.5B 在本机的推荐显存配置

第一版应采用普通 BF16 LoRA，而不是一开始就 QLoRA。1.5B 的基座权重本身不大，普通 LoRA 更容易保持训练链路透明；只有在多轮上下文、较大 group size 或 vLLM 共卡导致 OOM 时，才切换 QLoRA。

```text
模型：                  Qwen2.5-1.5B-Instruct HF 权重
训练参数：              只训练 LoRA adapter
LoRA rank：             16 起步
target_modules：       q_proj、k_proj、v_proj、o_proj
precision：             bf16
gradient_checkpointing：开启
use_cache：             关闭
per_device_batch：      1
num_generations：       2 起步，稳定后再到 4
prompt：                256～512 tokens
completion：            128～256 tokens
gradient accumulation： 4～8
reward model：          不加载，使用 HomeEnv verifier
rollout：               Transformers 原生生成
vLLM：                  第一阶段关闭
```

```text
出现 OOM 时的降级顺序：

先减 completion 长度
  -> 再减 num_generations
  -> 再减 prompt 长度
  -> 再开启更强的 gradient checkpointing / micro-batch
  -> 再评估 beta=0 是否作为独立算法对照
  -> 最后才切 QLoRA 或 vLLM sleep mode
```

这样可以知道究竟是序列激活、rollout cache、reference 还是参数状态导致 OOM，而不是一开始把所有压缩选项同时打开。

## 4. 第一推荐：Transformers + TRL + PEFT + Accelerate

### 4.1 推荐定位

这是本项目的主推荐组合，适合科研入门和第一篇可复现实验。

```text
Transformers：模型、tokenizer、chat template
PEFT：        LoRA / QLoRA adapter
TRL：         SFTTrainer、GRPOTrainer、奖励和环境训练接口
Accelerate：  单卡启动、梯度累积、后续多卡迁移
HomeEnv：     自己维护的环境核心与 verifier
```

TRL 当前文档已经提供三种与本项目直接相关的机制：

```text
reward_funcs：       Python 可调用的自定义奖励函数
environment_factory：每个 rollout 创建独立环境，自动处理工具调用循环
rollout_func：       完全自定义生成、工具执行和轨迹返回逻辑
```

其中，`environment_factory` 适合 HomeEnv 这种“模型调用工具、环境返回观察、模型继续生成”的多轮过程；`rollout_func` 适合后续需要自定义 token mask、动作解析或外部 agent loop 的情况。TRL 的 OpenEnv 示例还直接展示了环境工厂、工具方法、奖励读取和 LoRA 配置组合使用的方式。

### 4.2 为什么最适合我们的科研目标

```text
可读：      trainer、reward、environment、PEFT 都是独立对象
可改：      可以从 reward_func 改到 environment_factory，再改到 rollout_func
可比：      SFT、GRPO、LoRA、QLoRA 共用 Transformers 权重格式
可复现：    训练配置和 adapter checkpoint 容易保存
可迁移：    后续能接 vLLM、OpenEnv、OpenReward 或多 GPU Accelerate
```

它还解决了当前 MiniMind 代码最容易出问题的两点：

```text
LoRA 不再手写 monkey-patch，而由 PEFT 管理 adapter、冻结基座和保存加载。
Qwen 不再被强行套进 MiniMindConfig，而直接使用 AutoModelForCausalLM。
```

PEFT 对 Qwen 等常见架构提供默认 target，也允许显式指定 `q_proj`、`k_proj`、`v_proj`、`o_proj`，后续还可以扩展到 `all-linear`。这比当前 `in_features == out_features` 的判断更适合做可控实验。

### 4.3 HomeEnv 如何接入

核心环境不需要一开始继承 Gymnasium，也不需要把状态压成传统向量。保留前一份方案中的框架无关核心：

```text
HomeEpisodeEnv
  reset(scenario, seed)
  snapshot()
  restore(snapshot)
  fork()
  execute(action)
  get_reward()
  is_terminal()
```

再为 TRL 增加一个很薄的 adapter：

```text
HomeEpisodeEnv
      |
      +--> TRL environment_factory
      |      reset() -> 初始观察
      |      public methods -> 模型工具
      |      get_reward() -> rollout reward
      |
      +--> SFTTrajectoryBuilder
      |      成功轨迹 -> messages/tool_calls/tool_response
      |
      +--> Gymnasium adapter（可选）
             用于环境测试和通用评测，不参与第一版训练主链
```

HomeEnv 工具方法可以设计为：

```text
query_device(device_id, fields)
control_device(device_id, command, value)
ask_user(question)
finish(summary)
```

每个 rollout 都创建独立环境实例，避免第一个样本改变家庭状态后污染同组其他样本。奖励由环境内部维护：

```text
完成度增加：       正奖励
合法查询：         小奖励或 0
非法参数：         负奖励
越界控制：         更强负奖励
达到目标：         终局奖励
超步数或未完成：   截断惩罚
```

### 4.4 本机配置建议

第一版不要同时启动 vLLM 服务和训练进程。单卡 4090 上先使用 Transformers 原生 rollout，等训练逻辑稳定后再评估 vLLM colocate 或 sleep mode。TRL 文档明确提醒，vLLM 与训练共用 GPU 会产生资源竞争；单卡调试阶段优先保证显存峰值可解释。

```text
模型：                 Qwen2.5-1.5B-Instruct HF 权重
训练方式：             LoRA-GRPO
LoRA rank：            16 起步，必要时比较 32
首轮 target_modules： q_proj、k_proj、v_proj、o_proj
batch_size：           1
num_generations：      2～4
prompt 长度：          256～512 tokens
completion 长度：      128～256 tokens
gradient accumulation：4～8
precision：            bf16，遇到算子问题再切 fp16
reward：               HomeEnv verifier，不加载额外 reward model
rollout：              Transformers 原生生成
```

### 4.5 当前本地依赖需要处理的问题

当前 `minimind/requirements.txt` 中写的是：

```text
transformers==4.57.6
trl==0.13.0
# peft 被注释
```

但当前 Python 环境实测没有安装 `transformers`、`trl`、`peft`、`accelerate`、`vllm` 等包。更重要的是，TRL 当前 `environment_factory` 文档要求 `transformers>=5.2.0`。因此不能把旧 MiniMind 依赖和新 HomeEnv 训练链直接混在一起。

建议单独创建实验环境：

```text
/root/autodl-tmp/envs/homeflow-trl/
  Transformers：按当前 TRL 兼容矩阵锁定
  TRL：          使用支持 environment_factory 的版本
  PEFT：         与 Transformers 兼容
  Accelerate：   单卡和后续多卡启动
  Datasets：     SFT / GRPO 数据读取
  bitsandbytes： 只有做 QLoRA 时再加入
  vllm：         第一阶段不装或暂不启用
```

旧 MiniMind 依赖保留在原环境，新框架使用独立环境。这样可以避免为了 1.5B 训练破坏当前 MiniMind 学习项目。

## 5. 第二推荐：ms-swift

### 5.1 推荐定位

ms-swift 是更偏工程效率的第二选择，尤其适合 Qwen、ModelScope、中文数据和快速跑通 GRPO。

官方项目目前提供：

```text
GRPO、DAPO、GSPO、SAPO、CISPO、RLOO 等算法
LoRA、QLoRA 和其他参数高效方法
自定义 reward function
多轮推理 scheduler
通过 plugin 接入环境交互
vLLM、SGLang、LMDeploy 推理后端
```

它对本机的优势是：

```text
Qwen 生态适配成熟
中文资料和 ModelScope 使用路径较顺
命令行参数覆盖模型、LoRA、GRPO、vLLM 和保存恢复
单卡小实验的启动成本低于分布式 RL 框架
```

### 5.2 为什么不是第一选择

ms-swift 能更快得到结果，但其抽象层更厚。对于我们的科研问题，最初需要频繁观察：

```text
每一轮 HomeEnv 状态是什么？
工具响应是否进入了正确位置？
哪一段 token 被计入 loss？
同一组 rollout 的 reward 是否真的来自同一任务？
```

这些内容在 TRL 的 Python trainer、reward function 和 environment factory 中更容易逐行追踪。ms-swift 更适合作为：

```text
同一模型、同一数据、同一 reward 的快速复现实验
LoRA 与 QLoRA 的工程基线
后续加入异步多轮 rollout 的效率对照
```

### 5.3 适合我们的使用方式

不要先把整个 HomeEnv 改成 ms-swift 专属接口。保留 HomeEnv 核心，通过 plugin 提供：

```text
reset_episode(sample)
advance_env(messages)
collect_trajectory()
calculate_episode_reward()
```

ms-swift 的多轮 GRPO 文档要求同一条 trajectory 的相关记录使用一致的 reward。HomeFlow 的 episode reward 应在轨迹结束后统一结算，工具调用过程中的中间分数只作为日志或内部 shaping 信号，避免同一轨迹被重复加权。

## 6. 第三推荐：OpenRLHF

### 6.1 推荐定位

OpenRLHF 适合在第一版 HomeEnv 已经稳定后，研究更完整的 Agent RL 训练形态：

```text
GRPO、REINFORCE++、RLOO、PPO
LoRA / QLoRA
自定义 reward
单轮和多轮 Agent executor
Ray 调度
DeepSpeed、vLLM 混合引擎
同步或异步 rollout
```

它的核心优势是算法与 Agent 执行器分离。HomeEnv 可以作为自定义 agent function 或 executor 接入，模型生成、工具执行、轨迹 token 和 reward 的职责边界比较清楚。后续如果要研究：

```text
同步 GRPO 与异步 Agent RL 的差异
rollout 与训练解耦
多环境并发
vLLM 生成吞吐
更大模型和多卡扩展
```

OpenRLHF 的上限高于 TRL 的单机入门路径。

### 6.2 为什么暂时排第三

OpenRLHF 的代价是系统复杂度：

```text
Ray 进程管理
DeepSpeed 配置
actor / reference / rollout 资源划分
vLLM 混合引擎同步
单卡下的进程和显存调度
```

对一张 RTX 4090 而言，这些机制的收益有限，却会增加排错路径。若 HomeEnv 还没有通过单元测试和小规模 rollout 验证，直接引入 OpenRLHF，很难判断问题来自环境、奖励、token mask，还是 Ray/DeepSpeed 配置。

因此它适合第二阶段之后使用，不适合作为第一条 1.5B 训练链。

## 7. 其他框架为什么不列入前三

### 7.1 veRL

veRL 是面向大规模 RL 后训练的强框架，支持 FSDP/Megatron 训练后端、vLLM/SGLang rollout 和可插拔 agent loop。它还明确提供了用户自定义的异步多轮 AgentLoop 接口。

但它当前的 AgentLoop API 仍标注为 alpha，整体配置依赖 Ray、Hydra、训练 worker 和独立 inference server。对单卡 1.5B LoRA-GRPO，它的能力大于当前需求，首轮会增加大量基础设施工作。

```text
现在：    TRL 先验证科学问题
之后：    veRL 验证吞吐、异步 rollout 和多 GPU 扩展
```

### 7.2 torchtune

torchtune 很适合阅读 PyTorch 原生 SFT、LoRA 和配置化训练代码，但目前不应把它作为本项目的首选 GRPO Agent 框架。我们需要的是“自定义多轮环境 + LoRA-GRPO”，而不是单纯的单卡 SFT/PEFT。

### 7.3 只使用 MiniMind 自己的训练代码

继续用 MiniMind 做 68.8M HomeEnv 闭环是合理的；把它扩展成通用 1.5B 训练框架则不划算。当前代码还存在：

```text
train_grpo.py 没有接入 LoRA
模型初始化固定为 MiniMind
当前 LoRA 目标层过窄
policy/reference 路径会保留完整 logits
默认依赖本地不存在的 reward model
```

它应作为“算法显微镜”，而不是“1.5B 实验平台”。

## 8. 三个推荐项对比

| 排名 | 框架组合 | 科研可读性 | HomeEnv 接入 | 单卡 4090 | 后续扩展 | 适合阶段 |
|---:|---|---:|---:|---:|---:|---|
| 1 | Transformers + TRL + PEFT + Accelerate | 高 | 高，environment_factory / rollout_func | 高，先用原生 rollout | 高 | 当前主线 |
| 2 | ms-swift + PEFT | 中 | 中高，plugin / 多轮 scheduler | 高 | 高 | 快速工程对照 |
| 3 | OpenRLHF + DeepSpeed + Ray | 中 | 高，Agent executor | 中，配置较重 | 很高 | 第二阶段扩展 |

可以用下面的判断记忆：

```text
TRL：       最适合看懂并修改科研问题
ms-swift：  最适合快速跑通 Qwen 训练工程
OpenRLHF： 最适合把已验证方案扩展成 Agent RL 系统
veRL：      最适合更晚阶段的高吞吐、多卡和异步 rollout
```

## 9. 针对本机和 HomeFlow 的最终落地方案

### 9.1 第一阶段：保留 MiniMind，完成环境正确性

```text
模型：       MiniMind-3 68.8M
框架：       当前 MiniMind 代码
环境：       HomeEpisodeEnv
训练：       先 SFT，再全量 GRPO，再 LoRA-GRPO
目标：       验证状态转移、工具解析、奖励构成和组内方差
```

这一阶段的产物不是最终模型，而是四个可测试契约：

```text
环境契约：   reset / step / terminal / snapshot
轨迹契约：   messages / tool_calls / tool_response / mask
奖励契约：   每条 rollout 一个可解释的 episode reward
评测契约：   task success / illegal action / step count / reward
```

### 9.2 第二阶段：TRL 上的 1.5B SFT

```text
模型：       Qwen2.5-1.5B-Instruct HF 权重
训练器：     TRL SFTTrainer
参数更新：   PEFT LoRA
数据：       HomeEnv 成功轨迹 + 少量失败纠正轨迹
目标：       先让模型稳定输出 query/control/finish 工具调用
```

SFT 阶段必须先完成，原因是未经工具格式对齐的 1.5B 模型可能在 GRPO 前期几乎不会产生合法工具调用，导致同一组 reward 全部相同，GRPO 没有有效优势信号。

### 9.3 第三阶段：TRL 上的 1.5B LoRA-GRPO

```text
训练器：          TRL GRPOTrainer
环境：            HomeEnv environment_factory
奖励：            HomeEnv get_reward / custom reward_func
LoRA：            PEFT r=16，q/k/v/o 起步
rollout：         Transformers 原生生成
batch：           1
group size：      2～4
上下文：          prompt 256～512，completion 128～256
保存：            adapter_config.json + adapter_model.safetensors
```

第一轮只回答一个科学问题：

```text
在固定 HomeEnv、固定任务集和固定 token 预算下，LoRA-GRPO 是否能提高任务成功率？
```

不要同时改变模型、环境、奖励、工具集合、LoRA target 和 rollout 引擎。

### 9.4 第四阶段：做框架对照

保持下面几项完全相同：

```text
同一 Qwen2.5-1.5B base checkpoint
同一 SFT adapter 或同一 SFT merged checkpoint
同一 HomeEnv 场景集
同一工具 schema
同一 reward 分解
同一 rollout token 预算
同一随机种子集合
```

然后比较：

```text
TRL：       作为科研主线
ms-swift：  作为工程实现对照
OpenRLHF：  作为多轮 Agent 扩展对照
```

评价指标不要只看训练 loss：

```text
任务成功率
合法工具调用率
非法动作率
平均 episode 步数
平均 completion tokens
reward 组内标准差
LoRA adapter 参数量
每个成功任务消耗的 GPU-hours
```

## 10. 具体推荐顺序

```text
1. 先用 TRL + Transformers + PEFT + Accelerate
   完成 Qwen2.5-1.5B 的 SFT -> HomeEnv LoRA-GRPO 闭环。

2. 再用 ms-swift 复现同一个 1.5B 实验
   主要比较工程吞吐、配置复杂度和多轮 rollout 便利性。

3. 最后评估 OpenRLHF
   只有当 HomeEnv、reward 和 token trajectory 已经稳定，才引入 Ray、DeepSpeed、异步 Agent executor。
```

不建议第一步就使用 OpenRLHF 或 veRL，也不建议第一步把 vLLM、QLoRA、异步 rollout 和多环境并发全部打开。那样无法分辨性能变化来自算法，还是来自系统配置。

## 12. 最终判断

```text
MiniMind 适合回答：算法到底怎么实现？
TRL 适合回答：1.5B LoRA-GRPO 对 HomeFlow 有效吗？
ms-swift 适合回答：同一方案能否更快、更方便地跑起来？
OpenRLHF / veRL 适合回答：多轮 Agent RL 如何扩展到更高吞吐和多 GPU？
```

所以当前最稳妥的研究架构是：

```text
MiniMind 学习闭环
        +
TRL 1.5B 科研主线
        +
ms-swift 工程对照
        +
OpenRLHF / veRL 后续扩展
```
