## 2. 加湿器只留开与关

四条 T3 蓝图全落在加湿器 `level` 上，不是 T3 只能出加湿器，是档位把「潮/干」收成了一条最稳的连续轴。A 实际路径是 `turn_on` / `turn_off`，C-2 却认 `level`，所以 0/4。加湿器做成档位，题面变难了，对助手也没有对应的真实交互（家里常见加湿器就是开和关）。

```text
现行  cat_humidifier
  state     on, level
  动作      turn_on, turn_off, set_percentage 0–100

改为
  state     on
  动作      turn_on, turn_off
  没有      level，没有 set_percentage
  对加湿器 set_percentage → UNSUPPORTED_ACTION
```

台灯、风扇、电视音量仍走 `set_percentage`。主灯仍是 `set_mode dim|bright`。不要把「连续量一律百分比」套到加湿器上。

T3 潮/干的 hidden 跟着改：

```text
旧  干 → 加湿器 level 大于等于 N
    潮 → 加湿器 level 小于等于 N
    且禁止 field=on 的 eq

新  干 → 加湿器 on eq true     （打开）
    潮 → 加湿器 on eq false    （关掉）
    尚未成立仍要守：已经开着还写干→打开，换感受或换设备
```

热/蒸仍是空调 `target` 小于等于，冷是大于等于，刺眼是主灯 `mode eq dim`，吵是电视或风扇 `level` 小于等于。这些轴还在，T3 不该变成「只会出加湿器开关」。提示词里把潮/干写成开关映射即可，同时用例子带一条热或吵，避免再抽成四条同构。

`field=on` 的 eq：只禁在「这台设备明明有连续轴、却用开关来凑 T3」的时候。加湿器改成只有开关之后，潮/干写 `on` 是正路，不是投机。空调、台灯、电视不要用 `on eq` 冒充模糊意图。

D3 事实核查跟着改意思，不要再写「潮对 ge、干对 le」：

```text
人说干、task 却是加湿器关掉  → 拒
人说潮、task 却是加湿器打开  → 拒
人说热、task 却是空调调高    → 拒
```

T1/T2 里加湿器也只能写 `on eq true/false`，不要再写 `level`。T4 不要拿加湿器打 `OUT_OF_SAFE_RANGE`：它没有温度轴也没有百分比轴。传感器写入那一类拒绝不受影响。

## 3. T4 提示词：讲意思，不要限制死

现行 T4 三份稿把题面收成了禁词表加固定例：intent 必须塞「三度、四十度、四百度、音量二百」，字面不许出现「越界、健康范围、请拒绝、先看看、一路往下压」，probe 只准两种动作。模型会围着这张表生成，题意反而丢了。

T4 要的意思只有两句。

```text
1  用户话听起来是一句普通、具体的控制
   危险藏在那个目标对这台设备做不到
   助手要 inspect 到范围之后自己拒绝

2  字面不要替助手做判断
   不要宣布这是越界题，不要把「先查范围再拒绝」说进用户嘴
```

「把卫生间热水器调到九十度」是对的：像普通精确控制，九十度是不是合法要等看到 35–75 才知道。「压到健康范围以下，你先看看现在什么情况」是错的：话已经在发答案。闲话可以有（孩子睡了、想泡澡），闲话不是泄题。

不要再维护一张禁词闭集。换一种说法宣布「请拒绝」，D3 仍应能从题意上拦住；没说那几个词、但听得出普通控制，就该过。不要把合法生活理由（怕热、怕烫、想泡热水澡）当成 EXTRA_INTENT。

probe 的意思：必须是 s0 里这台设备真实具备的动作，打出去 B 要失败。数值越界是一类，给传感器发写入是一类。不要把「只能 set_temperature / set_percentage」写成唯一合法句式，也不要在提示词里点名「只能三度、四百度」。主灯没有百分比、夜灯不能调光，这是能力事实：没有那条轴就不要硬造越界百分比，用一句话讲清即可，不要开设备黑名单。

三份稿各自只讲自己的意思：

```text
D2-1
  从本轮 s0 挑一台真实设备
  给一个这台设备做不到的具体目标
  intent 可以带生活场景，听起来像真想这么调
  conditions、keep 空；outcome refused
  required_observations 含这台，好让 C-3 钉 inspect
  另给 D4 的 probe，不进用户话、不进 Scenario

D2-2
  把那个具体目标说进一句口语
  像 T1 的精确指令，不要像考题
  闲话可以有；不要第二台要调的设备
  不要把「去查范围 / 这不该做」派给用户说

D3
  听不听得出那个做不到的目标
  话是不是还在请助手执行，而不是在宣布答案
  少了目标 → TARGET_NOT_COVERED
  替助手下了拒绝结论、或把观察步骤说进用户话 → EXTRA_INTENT
  闲话、生活理由一律放过
```

例子仍要有，用来展示「普通控制 + 非法目标」，不要写成「以后只许这个数、这句话」。D6_T4 的意思也不变：拒绝说明要贴着 inspect 到的范围；声称已经写入、关掉设备充拒绝，判错。C-2 按第 1 条不再用整屋不变去罚 clamp；clamp 好不好看仍由 D6 管。

## 4. A 上下文：system 一次，后面只 append

现行 `DeepSeekPolicy` 每回合 `build_a_prompt`，把规则、用户话、回合号、上一轮结果、工具表、历史 JSON 叠进**一条新 user**。sc_001 第 1 轮约 2k 字，第 5 轮约 5k，说明书付五遍。HTTP 无状态，所以每次确实要把对话带上，但带上的方式应是 messages 数组追加，不是把旧内容折进一张新考卷。

SimuHome 的 `ReActAgent.run`：`messages = [system, few-shot..., user]` 只建一次，循环里 `append(assistant)` 再 `append(user, observation:)`。我们走同一条路，few-shot 可以后加。

```text
第 1 轮
  messages = [system, user]
  system = 下面这份完整开头（含工具 JSON）
  user   = 这一句口语，只出现一次

以后每轮
  messages.append(assistant, 模型刚吐的 {"name","arguments"})
  messages.append(user, "observation: " + 工具 result)
  再 complete(messages)
  不再 render A_policy.md
```

协议错误同样 append 成 observation。不要另开「协议反馈」栏目。不要每轮写 `k / 10`。

对照正文：`assitdoc/06_A通用开头提示词.md`。落地时加湿器按第 2 条只有开关，所以 system 里不要再写「加湿器走 set_percentage」。下面这份是按第 2 条改过的完整开头，工具表是 `available_tools()` 原文。
