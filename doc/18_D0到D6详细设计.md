## 0. 总则

新包从零写。借鉴 V1.2 的：四个家庭工具、B 不挡发现链、一次 assistant 输出算一轮、符号状态、`device_id` 谓词。不带：`writer_view`、写死户型、facts/answered、旧 Judge 长文。

17 没写死、本文冻结：

```text
1. T4 的 probe 只活在未编号草稿里，不进 D4_blueprints.jsonl，不进 Scenario
2. category 进蓝图和轨迹总表，不进 C 循环六项
3. T4 的 required_observations 含被拒绝的那台设备，C-3 要求 inspect 过
4. D4 检查 conditions/keep/required_observations 的 device_id 都在 s0；keep 仍不 execute
5. 公开 finish：summary + outcome；refused 再加 reason_code。无 facts，无 answered
6. 轨迹总表 events 必须是完整 result
7. 编排脚本先后调 D5、D6；D5 模块不调用 D6
```

谁在调大模型，必须分清。这一次所有 DeepSeek 请求都不带 max_tokens、不截断：

```text
不是 A 的外部 DeepSeek
  D2 第一次  写 task JSON
  D2 第二次  写 user_request 一句中文
  D3         审这句中文说全没有、有没有多加
  D6         对 T3/T4/T5 投对/错，独立三票

是 A 的 DeepSeek
  只出现在 D5 的 C.run 里
  每轮 respond(context) -> 一个工具或 finish
  看不见 task
  这一次也不限 token
```

```text
D0 -> D1 s0 -> D2 task -> D2 request -> 草稿
  -> D3 -> D4 -> 过则 bp_*
  -> 停闸：给人看 D4_blueprints.jsonl 和 D34_failures.jsonl
  -> 确认后再 D5 编 Scenario，C.run，sc_* 进总表，打 C 标签
  -> D6 按需写回 D6 标签
  -> 标签全过，复制进 D_dataset.jsonl
今天停在数据集。以后可按 doc/21 改形状做 SFT。
```

## 2. D0 静态库

功能：库文件。D0 自己不跑抽样、不调模型。除户型目录外，外部 DeepSeek 用的提示词也全部放在这里，不写进 Python 字符串。

```text
户型（给 D1，不是提示词）
  D0_homes.jsonl     九种大中小户型，只有房间
  D0_devices.jsonl   十五种设备/传感器能力，不绑定房间

四类提示词/选用材料
  1. 人物画像 D0_personas.jsonl
     固定二十条，D2 第一次从中选用一条
     年龄、职业、生理、健康、习惯（含环境偏好，不再单列 env_pref）
     只影响 intent，不进 C/D4/D6 打分
  2. 任务族模板 D0_templates/T1..T5_*.md
     指导外部 DeepSeek：如何根据 s0 + 画像写出该类 task JSON
     不写用户那句话，不存现成「把灯关掉」
  3. 用户指令提示词 D0_templates/D0_request_T*.md
     指导外部 DeepSeek：如何根据 task + intent + display_name 写一句口语请求
  4. D6 裁判提示词 D0_templates/D6_T3.md、D6_T4.md、D6_T5.md
     指导外部 DeepSeek：只输出对或错
     T3 看是否落实唯一隐藏目标；T4 看拒绝是否贴着 inspect 范围；T5 看 summary 是否答了问题

另：D3 也调外部 DeepSeek，提示词 D0_templates/D3_review_T*.md
    指导：这句话有没有说全 task、有没有多加
```

户型例子（不挂设备）：

```json
{"home_template_id":"ht_small_1","size":"small","rooms":[{"room_id":"room_bedroom","display_name":"卧室","room_kind":"bedroom"},{"room_id":"room_living","display_name":"客厅","room_kind":"living"}]}
```

设备例子（不绑定房间）：

```json
{"catalog_id":"cat_climate","id_token":"climate","name_stem":"空调","kind":"actuator","device_type":"climate","allowed_room_kinds":["bedroom","living","study"],"state":{"on":true,"mode":"cool","target":25.0},"actions":[{"action":"set_temperature","params":{"value":{"type":"number","minimum":7.0,"maximum":32.0,"step":0.5}}}],"available":true}
```

这四类正文见 `doc/19_D0前三类提示词.md`（画像、T1–T5、用户指令）。D6 提示词等前三类审过再写。

```text
输入    1. 无运行时输入
```

## 3. D1 HomeMaker

功能：分别抽户型和设备，生成 id、配对、命名，再随机初始 state。不用模型。不读画像。抽完的 s0 就是后面 Scenario.home。禁止在 Python 分支里写死五房七设备。

```text
device_id      device_{房间token}_{id_token}；传感器前缀 sensor_
display_name   房间中文名 + name_stem     例：卧室空调
配对           device.room_id = 房间；room.device_ids 追加该 id
先保证         一台空调、一台传感器、至少两盏灯
```

抽样用的整数只写 D1 日志，不进蓝图，不进 Scenario。

```text
输入    1. D0_homes.jsonl  2. D0_devices.jsonl  3. 抽样种子
输出    1. s0   例：卧室空调 target=25.0，客厅主灯 on=true
对应文件  new_demo/data/D1_home_maker.py
不负责  写 task、写用户指令、调 B
```

## 4. D2 第一次：外部 DeepSeek 写 task

功能：这不是 A。把「这一家 + 这个人 + 这一类任务」交给外部 DeepSeek，让它写出隐藏 task JSON，不写用户那句话。不调 B。不限 token。

发给模型的内容：这份 s0 的房间设备（含 device_id、display_name、state、actions 范围）、一条画像、该 T 的模板。模型必须输出严格 JSON，程序先校验再往下。

```text
输入
  1. s0
  2. persona
  3. category        T1..T5
  4. 该 T 的模板
输出
  1. category
  2. task
  3. probe           仅 T4，其它 null
DeepSeek
  role=external，不限 token
  收回：task JSON；T4 另附 probe
  原始响应写入 data_raw/api/
对应文件
  new_demo/data/D2_task_writer.py
  提示词：new_demo/data_static/D0_templates/T1..T5_*.md
```

task 必须长这样，intent 必填且要体现画像，设备必须写 device_id：

```json
{
  "intent": "觉得卧室太热，想睡觉",
  "conditions": [{"device_id": "device_bedroom_climate", "field": "target", "operator": "eq", "value": 24.0}],
  "keep": [],
  "required_observations": [],
  "expected_finish": {"outcome": "completed", "allowed_reason_codes": []}
}
```

按类功能：

```text
T1  completed，一条 condition。例：关卧室灯
T2  completed，多条 condition；keep 写不该动的设备。例：关卧室灯 + 空调 24 度，客厅灯不动
T3  completed，一条唯一可执行目标。用户话下一轮才写，可以不点设备名
T4  refused，conditions=[]，allowed_reason_codes 含 OUT_OF_SAFE_RANGE 或 READ_ONLY_DEVICE
    required_observations 含 probe 那台设备
    probe 例：{device_id:device_bedroom_climate, action:set_temperature, params:{value:5.0}}
T5  completed，conditions=[]，required_observations 非空，不写 facts
    例：必须观察 sensor_bedroom_env 的 temperature
```

程序拒收：缺 intent、outcome 不是 completed/refused、device_id 不在 s0、T4 没有 probe。拒收不进第二次。

不负责：写 user_request、审指令、当 A。

```text
  仍无 blueprint_id
对应文件
  new_demo/data/D2_request_writer.py

```

T4 的 probe 跟着草稿走，不写进用户话。不负责：审查、编号、调 B。

## 6. D3 审用户指令

功能：第一步打分的指令关。对象是未编号草稿。分两小步，都不调 B。

第一步程序：扫 user_request 有没有 device_id、room_id、action 名（turn_on、set_temperature 等）、reason_code、工具 JSON 碎片。命中则失败。

第二步外部 DeepSeek：这不是 A，不限 token。只读 task、intent、user_request，不读 D0、不读 home 全文。问两件事：有没有说全 task；有没有多加设备和动作。输出通过或失败及原因。

不过：写入 D34_failures.jsonl，不发 blueprint_id。过了：同一份草稿交给 D4，仍无 id。

```text
输入
  1. task
  2. intent
  3. user_request     例：卧室太热了，把空调调到 24 度
输出
  1. 通过或失败       例：过；出现 device_bedroom_climate -> 失败泄露；只说关灯但 task 还有空调 24 度 -> 失败没说全
  2. 失败原因         仅失败时
DeepSeek
  role=external，不限 token
  收回：{accept:true/false, codes:[...]}
对应文件
  new_demo/data/D3_reviewer.py
  提示词：new_demo/data_static/D0_templates/D3_review_T*.md
```

不负责：打 B，当 A，发 blueprint_id。

## 7. D4 Oracle

功能：第一步打分的可行性关。不是 A，不调大模型。不走 `C.run`，所以不受每轮 1 个工具限制。复制草稿 s0，对 B 做 reset + 若干次 step，打完丢掉副本，原来的 s0 不动。只看每次 `ok` / `error.code`，不看终态满不满足 conditions（那是 C-2）。keep 不打。已经到位也照发。T3 用户话可以不点设备名，隐藏 condition 仍打那条写入。

另做静态检查：conditions、keep、required_observations 里的 device_id 都必须在 s0，否则不合格。

```text
field -> action
  on=true        turn_on
  on=false       turn_off
  target         set_temperature(value)
  mode           set_mode(mode)
  level          set_percentage(value)

T1  一条 condition，打一次 execute_action
    例：execute_action(device_bedroom_light, turn_off, {})
    过：ok=true（灯本来就是关的也过）
    不过：UNKNOWN_DEVICE / UNSUPPORTED_ACTION / BAD_REQUEST

T2  每条 condition 各打一次，全部 ok 才过
    例：关卧室灯 + set_temperature 24
    keep 里的客厅灯不打

T3  与 T1 相同
    例：用户说「太热想睡觉」，仍 execute_action(..., set_temperature, {value:24.0})

T4  对草稿 probe 打 execute_action，必须失败，且副本 state 相对 s0 没变
    例：probe value=5.0 -> BAD_REQUEST 且 target 仍 25.0 才过
    若 ok=true：这不是拒绝任务，不合格
    对传感器写入：必须 UNSUPPORTED_ACTION

T5  不 execute
    设备级 inspect_device，state 有该 field 则过
    房间级 inspect_room，environment 有该 field 则过
    UNKNOWN_DEVICE 或没有该 field：不合格
```

UNKNOWN_DEVICE 只表示这份 s0 里没有这个 id，不是还没 observe。

```text
输入
  1. home
  2. task
  3. probe            仅 T4
输出（通过 -> data_processed/D4_blueprints.jsonl）
  1. blueprint_id     例：bp_001
  2. category
  3. home             原来的 s0，不是副本打完的状态
  4. task
  5. user_request
输出（失败 -> D34_failures.jsonl）
  1. 失败标记
  2. error.code
  3. 无 blueprint_id
对应文件
  new_demo/data/D4_oracle.py
  调 new_demo/env/B_home_env.py 的 reset/step
```

D3 或 D4 不过不发 id。都过才写入 D4_blueprints.jsonl。写完后停闸，不自动交给 D5。不负责：调大模型，审指令，把副本交给 D5。

## 8. B HomeEnv

功能：家庭工具沙箱。只认已经配对好的 home。执行四个工具，改 state。不解析 A，不处理 finish，不管 max_turns，不读 task，不算成功。发现链不是闸门：没先 observe 也可以 inspect/execute，未知 id 才报错。A 仍要先查，因为 observe_home 不给 device_id。

D4 和 C 都调同一份 B。D4 自己 reset 副本；C 的回合用 reset/step/observation/runtime_state。

```text
C 调用的模块口
  1. reset(scenario)      校验、复制 home
  2. step(ToolCall)       执行一次家庭工具
  3. observation()        user_request、tools、last_tool_result；无 task、无设备库存
  4. runtime_state        给 final_state 和 C-2，无 actions
这次不用
  5. events()  6. snapshot()  7. restore()  8. fork()

step 按 ToolCall.name 路由（闭集，不是可选项）
  1. observe_home()
  2. inspect_room(room_id)       房间不存在 -> UNKNOWN_ROOM
  3. inspect_device(device_id)   设备不存在 -> UNKNOWN_DEVICE
  4. execute_action(...)         越界 BAD_REQUEST；无动作 UNSUPPORTED_ACTION；成功写 state
finish 不是 B 的 name
对应文件
  new_demo/env/B_models.py
  new_demo/env/B_schema.py
  new_demo/env/B_tool_schema.py     四工具 + finish(summary, outcome, reason_code)
  new_demo/env/B_state_engine.py
  new_demo/env/B_home_env.py
```

reset 前双向检查房间设备 id，对不上报错，不补、不译中文名。传感器 actions=[]。空调 set_temperature(24) 只改 target。

不负责：解析 A、处理 finish、打分、存户型库。

## 9. A

功能：只在 D5 的 C.run 里当助手。每轮看 C 给的 context（observation、tools、history、protocol_feedback），只输出一个工具调用或 finish。看不见 task、看不见 blueprint、看不见 C 标签。这是唯一可以限 token 的 DeepSeek 角色。

D2/D3/D6 虽然也调 DeepSeek，那些调用不走 policy.respond，因此不是 A。

```text
输入    1. context     C 每轮拼好的
输出    1. 一次 assistant 响应    一个 tool_call 或 finish
DeepSeek
  role=A，这一次也不限 token
对应文件
  new_demo/agents/A_policy.py
  new_demo/agents/DeepSeek_client.py
```

不负责：写蓝图、审指令、D6 裁判。

## 10. C

功能：唯一启动入口 `run(scenario)`。D5 只调这个。每轮把 context 给 A；A 回两个工具则 TOO_MANY_TOOL_CALLS，本轮不执行，消耗 turn。家庭工具走 B.step；finish 自己留下，不传 B。纯文本终答收成 finish，能解析到什么记什么，不补 outcome。跑完写出五项回合记录（不含对错），再读 task 打 C-1..C-4。不调大模型。不调 D6。

Scenario 六项与 17 第二节那份 JSON 相同：scenario_id、blueprint_id、home、user_request、task、episode_config。循环用 1、3、4、6；2 追溯；5 审查时读。max_turns=10，每轮 1 个工具。

五项记录里 turns[].events 必须是完整工具回执，下一轮 A 看见的就是它。程序审查另附，不塞进五项。

```text
输出（五项）
  1. scenario_id
  2. turns
  3. final_state
  4. finish             没交过则 null
  5. protocol           terminated / truncated / finish_requested / turn_count
输出（C 标签）
  1. C-1 协议           有 finish、未 truncated、每轮 1 个工具。只有 summary 仍算有 finish
  2. C-2 终态           runtime_state 对 conditions/keep；completed/refused 同一套只认 conditions/keep；空数组过
  3. C-3 观察           required_observations 都成功 inspect 过；空数组过
  4. C-4 finish 契约    completed/refused 对齐 expected_finish；查询也是 completed；无 facts
                        没有 outcome 只有 summary -> C-4 失败
对应文件
  new_demo/eval/C_episode_runner.py
  new_demo/eval/C_episode_evaluator.py
```

中间 UNKNOWN_DEVICE 后来改对、终局四步过，仍算程序通过。灯已关但 finish 只有 summary：C-2=true、C-4=false，总表留下，不送 D6。

不负责：处理 probe，把 summary-only 补成 completed，覆盖 D6。

## 11. D5 开跑

功能：只在停闸确认之后启动。读已编号蓝图，另发 sc_*，编成 17 第二节那份 Scenario，把 A 交给 C.run。C 返回后写入轨迹总表，打上 C 标签。C 没过的也留在总表，不删。D5 自己不算 C-1..C-4，也不调用 D6，不写 D_dataset.jsonl。T1/T2 的 D6 初值写「跳过」；T3/T4/T5 写「待审」。

A 在这里才出现：每轮只看 context。execute_action 照常真写入 B。一条轨迹，不超过 max_turns。不做 MCTS。

```text
输入
  1. blueprint_id
  2. category
  3. home
```

## 12. D6 AI 复核

功能：第二步打分里需要语言判断的那一层。只处理总表中 C 四步全 true 且 D6=待审 的 T3/T4/T5。这不是 A：不走 C.run，不看「下一步调哪个工具」。不限 token，不截断。不重跑 B。不能把 C 的失败改成成功。不读画像，不把 conditions 当标准答案句。

```text
  4. finish

  role=external，不限 token
  每次收回 {verdict:对} 或 {verdict:错}
  原始响应写入 data_raw/api/
```
