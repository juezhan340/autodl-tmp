# 范围题相对初值，不设门槛

> 日期：2026-10-01
> 性质：方案。**第 8 节已落地**（提示词在 27 / D0_templates，C-2 / D4 / D2 已改）。
> 触发：配额跑里 T1/T2/T3 的 C-2 挂在「调高一点却没到 26」。
> 对齐：`doc/26` 的 eq 对精确 / ge-le 对方向；本篇把 ge/le 的**检验对象**从门槛数字改成 s0 初值。

## 0. 这句话在说什么

范围题的用户话本来就是方向，不是终点。A 看不见 hidden 里的 26。现在却用 26 去打终态，等于拿助手看不见的数当及格线。

```text
现行
  人说   屋里有点冷，调高一点
  task   target ge 26
  s0     15
  A      15 → 17
  C-2    17 >= 26？  否，挂

要改成
  人说   屋里有点冷，调高一点
  task   target ge   （比现在高）
  s0     15
  A      15 → 17
  C-2    17 > 15？   是，过
```

音量同理：人说小了、再大声一点，s0=40，A 调到 55 就算过，不要 hidden 写成 ge 80。

eq 不动：关掉、调到二十二度、主灯暗档，仍是精确命中。keep 仍只许 eq。

## 1. 根因在检验，不在那一句「调高一点」

D2-2 / D3 已经要求：eq 说精确，ge/le 只说方向、不要念出 26。用户话这边是对齐的。挂掉的是 C-2 仍拿 `value=26` 做 `>=`。

配额里现成的例子：

```text
sc_T2_023  电视音量 le 30，s0=96，A 收到 60     60 不满足 ≤30
sc_T2_077  空调 le 24，s0=25.5，A 收到 24.5     24.5 不满足 ≤24
sc_T3_008  闷 le 26，s0=31，A 只开机不改温度    31 不满足 ≤26
sc_T3_005  冷 ge 26，s0=24，A 切制热仍 24       24 不满足 ≥26
```

A 按「高一点 / 低一点」做了。hidden 另藏了一道门槛。只改提示词、让 D2 不要写 26，C-2 若还按 value 比，要么模型仍乱填一个数，要么 value 填成 s0 后 `>= s0` 连没动也算过。检验语义必须一起改。

T3 的 `already holds` 也是这套门槛养出来的：冷 → ge 26，s0 已经 28，程序当废题扔掉。相对初值之后，28 再升高一档仍然合法，只要没顶到上限。

## 2. 新语义（建议定稿）

只作用于 conditions 里的 ge / le，且只用于连续量：空调/热水器/冰箱/烤箱的 `target`，台灯/电视/风扇的 `level`。

```text
eq    终态 == value                 不变
ge    终态 > 该字段在 s0 的值        比初值高，严格大于
le    终态 < 该字段在 s0 的值        比初值低，严格小于
keep  只许 eq，仍是终态 == value
```

严格大于/小于：原地不动不算。A 把 15 写成 15，C-2 不过。

```text
s0 target=20，人说有点冷
  写成 20.5 / 22 / 26     都过
  停在 20                 不过
  写成 19                 方向反了，不过

s0 level=40，人说声音小
  写成 41 或 70           都过
  停在 40 或改成 30       不过
```

主灯 dim/bright、开关、加湿器 on、洗衣机 mode，继续走 eq，不要用 ge/le。

## 3. JSON 里 value 怎么放

建议保留 `value` 字段，填**本轮 s0 的当前值**，给人看、给 D4 当起点，不当门槛。

```text
旧  {"device_id":"device_bedroom_climate","field":"target","operator":"ge","value":26.0}
新  {"device_id":"device_bedroom_climate","field":"target","operator":"ge","value":15.0}
                                                                                 ↑ s0 快照
```

C-2 比较时**不读这个 value 当门槛**，只读 `scenario.home` 里该字段的初值。value 填错成 26，只要 s0 是 15、终态 17，仍过。D2 形状检查可以要求：ge/le 的 value 必须等于 s0 当前值，写飞就在 D2 拦掉。

不要删掉 value：旧轨迹阅读、Oracle 写一步、程序核对都还用得上。也不要新发明 `gt_s0` 这种算子，operator 集合仍是 eq/ge/le。

## 4. 程序要动的三处（提示词之外）

C-2 今天只看终态和 condition.value，看不到 s0。Scenario 里有 `home`，就是初值。

```text
C-2  _conditions_hold
  eq     仍比 value
  ge/le  取 home.devices[id].state[field] 为初值
         ge：final > 初值
         le：final < 初值
  初值缺失、类型不能比  →  该条失败
```

D4 Oracle 今天把 ge/le 写成边界值 26。改成：沿方向写一档（step），证明「能比现在高/低」。已经在上限、无法再高的 ge，D4 失败，不当蓝图。

```text
D4
  eq     仍写成 value
  ge     若已无法升高（到 max）→ 失败
         否则写入 初值+step（夹在 min/max 内）
  le     对称，初值-step
  不要再出现「当前 22 已经 ≤26，跳过写入」
         相对初值后，22 对 le 仍要能再降，不能跳过
```

T3 `already holds` 今天是「s0 已经满足 ge 26」。改成：

```text
eq     s0 已经等于 value  → 废题（开关类仍适用）
ge     该字段已经是 max，无法再高 → 废题
le     已经是 min，无法再低 → 废题
不要再用「s0 >= 26」当废题
```

这样 T3 那 26 条「方向对、s0 已过门槛」会变成可出题：28 度还可以再高，14.5 还可以再低。

## 5. 提示词要改的口径

只改 ge/le 的说法。eq 例子、T4、T5、加湿器开关、主灯两档，不动。

```text
D2-1  T1 / T2 / T3
  删掉「大于等于 / 小于等于，写到边界值就算成立」
  改成：ge=比 s0 高，le=比 s0 低；value 填当前值；intent 只写方向
  例子里的 le 26 / ge 26 改成 value=s0（比如 27、15）
  T3「尚未成立」改成：还能往那个方向动一档，不要去卡 26

D2-2  T1 / T2
  已经是「ge/le 说方向、不要念数字」，这条留
  例子 JSON 同步改 value=s0
  「le 说成调到二十六度不行」留着，正好匹配新语义

D3  T1 / T2 / T3
  「ge/le 念出边界数字反而错」留
  T3 事实核查仍看方向：热→le，冷→ge，吵→le
  不要再暗示「要到 26 才算覆盖」

A_policy
  连续量「调高/调低」落到 set_temperature / set_percentage

```

T3 用户话仍然禁止「调低一点」这种控制口吻，感受句不变。变的是 hidden 不再藏 26。

## 6. 不动什么

```text
eq                 精确命中
keep               只许 eq
T4                 conditions 空，probe 越界
T5                 查询，conditions 空
加湿器             只有 on eq true/false
主灯               mode eq dim|bright，不是 ge/le
observe_home       仍只回房间名
C-2 不冻整屋       28 的第 1 条仍有效
已进集的 250 条    仍按旧门槛生成，不回放重打
```

旧 jsonl 用新 C-2 重打的话，当年「15→17、hidden ge 22」会从失败变成功。那是规则换了，不是同一批标签。新规则只用于改完之后的新跑次。

## 7. 边角

```text

只开机不改 target      终态 target 仍等于 s0 → ge/le 不过
                   （sc_T3_008 那种仍然挂，这是对的）
方向反了               冷却把温度打低 → 不过

```
