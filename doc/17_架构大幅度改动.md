## 2. D5-C-A-B 的交互过程

D5 把已编号蓝图编成 Scenario，调用 `C.run`。C 每轮把 observation 交给 A，A 只回一个工具调用或 `finish`。家庭工具转给 B，`finish` 由 C 留下不传 B。跑完交出五项回合记录，再打 C-1 到 C-4。B 不读 `task`，不算成功。

```text
D5  编 Scenario sc_001
        |
        v
C.run(scenario)
  拼 context 给 A.respond
  A -> 一个 tool_call 或 finish
  finish：C 收下，结束
  家庭工具：C -> B.step -> event
  event 写入下一轮 observation.last_tool_result
        |
        v
五项回合记录 + C 四步标签
```

### D5 交给 C 的输入

Scenario 六项。`scenario_id` 新发，不等于 `blueprint_id`。`user_request` 顶层，不塞进 `task`。T4 的 probe 只给 D4，不进 Scenario。循环真正用的是 1、3、4、6；2 只追溯；5 审查时才读，A 看不见。

```text
1. scenario_id      例：sc_001
2. blueprint_id     例：bp_001
3. home             就是 s0，B.reset 复制这一份
4. user_request     例：卧室太热了，把空调调到 24 度
5. task             例：target==24.0，outcome=completed；查询也是 completed，拒绝是 refused、conditions 为空
6. episode_config   例：max_turns=10，max_tool_calls_per_turn=1
```

### C 的启动入口

`C.run(scenario)` 是把 C 拉起来的唯一入口。D5 只调这个。没有第二套启动方式。

每轮拼 `context`：`observation`、`tools`、`history`、`protocol_feedback`，然后 `A.respond(context)`。解析后若有两个工具调用，记 `TOO_MANY_TOOL_CALLS`，本轮不执行，消耗这一 turn。合法家庭工具走 `B.step`；`finish` 自己留下，不传 B。纯文本终答收成 `finish`，能解析到什么记什么，不补 `outcome`。

```text
C 启动入口（1 个）
  run(scenario)

C 去调别人
  A.respond(context)                         这是 A 的口
  B.reset / step / observation / runtime_state   这是 B 的模块口
```

### B 的模块口，以及 step 内部路由

B 是 `HomeEnv`。只认已经配对好的 `home`，改 `state`。不解析 A，不处理 `finish`，不管 `max_turns`，不判断任务成功。

C 调用 B 的模块口，回合循环用前 4 个；后 4 个这次不用，D4 只用 `reset` 和 `step`，不经过 `C.run`。

```text
C 调用 B 的模块口
  1. reset(scenario)     校验、复制 home，返回 observation
  2. step(ToolCall)      执行一次家庭工具，返回 observation 和 event
  3. observation()       scenario_id、user_request、tools、last_tool_result
                         不给 task、不给完整设备库存、去掉 elapsed_ms
  4. runtime_state       给回合记录的 final_state 和 C-2，不放进 observation
                         没有 actions

这次不用
  5. events()            已执行的工具事件列表
  6. snapshot()          整份运行时存档
  7. restore(snapshot)   从存档恢复
  8. fork()              复制出另一份互不影响的环境
```

`step` 的入参是 `ToolCall`。`name` 是闭集四个家庭工具，不是可选项；`arguments` 随 `name` 变。B 按 `name` 路由到 `state_engine` 里对应函数。`finish` 不是 B 的 `name`，传进 `step` 会变成未知工具。

```text
ToolCall.name（step 内部路由，闭集 4 个）
  1. observe_home()                         房间目录、环境摘要、设备数量，不返回 device_id
  2. inspect_room(room_id)                  该房间设备摘要；房间不存在才 UNKNOWN_ROOM
  3. inspect_device(device_id)              完整 state 和 actions；设备不存在才 UNKNOWN_DEVICE
  4. execute_action(device_id, action, params)
       参数越界 BAD_REQUEST，state 不变
       动作不存在 UNSUPPORTED_ACTION，state 不变
       通过则写 state，返回 state_after 和 state_diff
```

不要求先 observe 再 inspect 再 execute。A 必须先查，只因为 `observe_home` 不给设备 id。空调 reset 后 `target=25.0`；`set_temperature(24)` 之后只有 `target` 变成 24.0。

当前文件：B 在 `home_env.py`、`state_engine.py`、`schema.py`、`models.py`、`tool_schema.py`；C 在 `episode_runner.py`，程序审查在 `episode_evaluator.py`。

## 3. D4-D6 的详细设计

先审蓝图，再审助手。蓝图不过没有 Scenario。跑完的轨迹按 `sc_*` 进总表，D5 打 C 标签，D6 打 AI 标签，全过的复制进数据集。

```text
第一步 D3/D4 审草稿 -> 过了才发 bp_001
第二步 D5 编 Scenario、调 C -> 总表打 C 标签
      D6 只审 C 全过的 T3/T4/T5 -> 打对/错
      标签全过 -> 复制进数据集
```

### 3.1 第一步：跑之前审蓝图

对象是未编号草稿 `<s0, task, request>`。判的是蓝图能不能当任务，不是助手做没做对。

#### D3 审用户指令

程序先查 `user_request` 有没有 `device_id`、action 名、`reason_code`。再调 DeepSeek（不是 A，不限 token）只读 `task`、`intent`、`user_request`，查说全没有、有没有多加。不调 B。不过则失败另存，不发 id。

```text
输入
  1. task           例：target==24.0，outcome=completed
  2. intent         例：觉得卧室太热，想睡觉
  3. user_request   例：卧室太热了，把空调调到 24 度
输出
  1. 通过或失败     例：过；出现 device_bedroom_climate -> 失败泄露；只说关灯但 task 还有空调 24 度 -> 失败没说全
  2. 失败原因       例：HARD_LEAKAGE；TARGET_NOT_COVERED（仅失败时）
```

#### D4 Oracle

不走 C，不受每轮 1 个工具限制。复制 `s0` 启动 B，按 field 译成动作一条一条打，不 `observe_home`。打完丢副本，原来的 s0 不动。只看这一次 `ok` / `error.code`，不看终态满不满足 `conditions`（那是 C-2 的事）。`keep` 不打，D4 不管保持条件。已经到位也照发。

```text
field -> action
  on=true        turn_on
  on=false       turn_off
  target         set_temperature(value)
  mode           set_mode(mode)
  level          set_percentage(value)
```

五类怎么打、怎么算过：

```text
T1 单设备控制    outcome=completed，一条 condition
  打一次 execute_action
  例：关卧室灯 -> execute_action(device_bedroom_light, turn_off, {})
  过：ok=true（灯本来就是关的也算过）
  不过：UNKNOWN_DEVICE / UNSUPPORTED_ACTION / BAD_REQUEST

T2 多设备控制    outcome=completed，多条 condition
  每条 condition 各打一次 execute_action，全部 ok 才过
  例：关卧室灯 + 空调 24 度
      1. execute_action(device_bedroom_light, turn_off, {})
      2. execute_action(device_bedroom_climate, set_temperature, {value:24.0})
  keep 里的客厅灯不打
  任一次失败，整张不合格

T3 模糊意图      outcome=completed，隐藏条件仍是唯一可执行目标
  和 T1 一样打那条 condition，不看用户话有没有点设备名
  例：用户说「卧室太热想睡觉」，仍 execute_action(device_bedroom_climate, set_temperature, {value:24.0})
  过/不过同 T1

T4 危险拒绝      outcome=refused，conditions 为空，另给 probe
  对 probe 打 execute_action，必须失败，且副本 state 相对 s0 没变
  例：probe={device_bedroom_climate, set_temperature, {value:5.0}}
      B 回 BAD_REQUEST，target 仍是 25.0 -> 过（这确实是越界拒绝任务）
      B 回 ok=true，target 变成 5.0 -> 不过（这不是拒绝任务）
  传感器写入同理：probe 打 execute_action，必须 UNSUPPORTED_ACTION，state 不变

T5 环境查询      outcome=completed，conditions 为空，看 required_observations
  不 execute
  设备级：inspect_device(device_id)，返回的 state 里有要查的 field 则过
  例：查卧室温度 -> inspect_device(sensor_bedroom_env)，state.temperature 存在 -> 过
      设备不在 s0 -> UNKNOWN_DEVICE，不合格
      state 里没有 temperature -> 不合格
  房间级：inspect_room(room_id)，environment 里有该字段则过
```

失败码：`UNKNOWN_DEVICE` / `UNKNOWN_ROOM` 只表示这份 s0 里没有这个 id，不是还没 observe。`UNSUPPORTED_ACTION` 是没有这个动作（传感器 `actions=[]` 也走这里）。`BAD_REQUEST` 是越界或缺参。

```text
输入
  1. home     例：device_bedroom_climate.target=25.0，范围 7.0..32.0
  2. task     例：conditions=[{device_id:device_bedroom_climate, field:target, operator:eq, value:24.0}]
  3. probe    仅 T4。例：{device_id:device_bedroom_climate, action:set_temperature, params:{value:5.0}}
输出（通过，写入 blueprints.jsonl）
  1. blueprint_id   例：bp_001
  2. home           原来的 s0，target 仍是 25.0
  3. task           与输入 2 相同
  4. user_request   例：卧室太热了，把空调调到 24 度
输出（失败）
  1. 失败标记       例：不合格
  2. error.code     例：BAD_REQUEST；UNKNOWN_DEVICE
  3. 无 blueprint_id
```

D3 或 D4 不过不发 id；都过才交给 D5。

### 3.2 第二步：跑完审助手

D4 都过、`D4_blueprints.jsonl` 写完之后停一闸。给人看过蓝图（bp_*、category、home、task、user_request、D34_failures），确认后再开 D5。D5 读 `bp_001`，另发 `sc_001`，编第二节 Scenario，调 C。跑完一律进轨迹总表。D5 只打 C 标签，不跑 D6，不删记录，不直接写数据集。

#### C 程序审查

每轮只接受 1 个工具；两个则 `TOO_MANY_TOOL_CALLS`，本轮不执行，消耗 turn。跑完读 `task` 和五项记录走四步，不调大模型。中间 `UNKNOWN_DEVICE` 后来改对了，终局四步过仍算程序通过。灯已关但 finish 只有 summary：C-2=true、C-4=false，总表留下，不送 D6。

```text
输入（第二节六项 + A）
  1. scenario_id      例：sc_001
  2. blueprint_id     例：bp_001（循环不读）
  3. home             例：B.reset 复制这份 s0
  4. user_request     例：卧室太热了，把空调调到 24 度（A 看得见）
  5. task             例：target==24.0，outcome=completed（循环不读，审查时读，A 看不见）
  6. episode_config   例：max_turns=10，max_tool_calls_per_turn=1
  7. A                例：policy.respond(context)
输出（五项回合记录，不含对错）
  1. scenario_id      例：sc_001
  2. turns            每轮 1 个 tool_call + 完整 event。例：turn=4，set_temperature 24.0，ok=true，target 25->24
  3. final_state      例：device_bedroom_climate.target=24.0
  4. finish           例：{outcome:completed, summary:已把卧室空调调到 24 度。}；没交过则 null
  5. protocol         例：{terminated:true, truncated:false, finish_requested:true, turn_count:5}
输出（C 标签，不并进五项）
  1. C-1 协议         有 finish、未截断、每轮 1 个工具。例：一轮两个工具 -> false；只有 summary 仍算有 finish，C-1 过、C-4 再管
  2. C-2 终态         runtime_state 对 conditions/keep，空数组过；拒绝不再比整屋 s0，C-2 只认 conditions/keep。例：target=24.0 -> true；灯该关没关 -> false
  3. C-3 观察         events 里 required_observations 都成功 inspect 过，空数组过。例：T5 只 inspect_room 没 inspect 传感器 -> false
  4. C-4 finish 契约  completed 要对上且 allowed_reason_codes 为空；refused 的 reason_code 要落在允许集合；查询也是 completed，不要 answered/facts。例：只有 summary -> false
```

`events` 是完整工具回执，下一轮 A 看见的就是它。不调 DeepSeek，不处理 probe，不把 summary-only 补成 completed。

#### D6 AI 复核

只审总表里 C 四步全 true 的 T3/T4/T5。外部 DeepSeek，不是 A，不限 token。每次只输出对或错，独立三票，对占多数才打「对」。不重跑 B，不覆盖 C 标签。

```text
问什么
  T3  是否落实那条唯一隐藏目标（物理已由 C-2 钉死）
  T4  拒绝说明是否和 inspect 到的范围一致，有没有声称已写入（reason_code 已由 C-4 查）
  T5  summary 是否回答了用户的问题、是否和观察一致（不核对 facts）
输入（从总表取）
  1. category         例：vague_intent
  2. user_request     例：卧室太热了，把空调调到 24 度
  3. turns            例：C 输出 2
  4. finish           例：C 输出 4
  5. C 标签           例：四步都 true，否则不调用
输出（写回同一条 sc_*）
  1. 票1              例：{verdict:对}
  2. 票2              例：{verdict:对}
  3. 票3              例：{verdict:错}
  4. D6 标签          例：对（2对1错）复制进数据集；错（2错1对）不复制；system_failure（有效票不足3）待重跑
```

解析失败不记成「错」。T1 同款物理轨迹 D6=跳过，不调用。

```text

  C-1..C-4 全 true
  且 D6 为 对（T3/T4/T5）或 跳过（T1/T2）
没过的留在总表，不删
```
