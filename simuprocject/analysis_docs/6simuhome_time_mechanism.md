# SimuHome 时间机制分析

## 一、先给结论：时间机制不是附属能力，而是整体流程的骨架

如果只把 SimuHome 的时间机制理解成“支持快进”或“支持定时任务”，会低估它在系统里的位置。更准确地说，时间机制承担的是三层职责：

1. 它给整个模拟过程提供统一的推进节拍。
2. 它把设备状态变化、环境状态变化、调度任务触发放进同一条执行链路。
3. 它让 Agent 的“现在执行”和“未来执行”都能在同一套仿真框架里被验证。

所以理解 SimuHome 的时间机制，最好不要一上来就看 `fast_forward`、`fast_forward_to` 这些“加速按钮”，而是先看：

```text
时间机制如何服务整体流程
  -> 如何定义“现在”
  -> 如何让系统每一步都按统一顺序推进
  -> 如何让设备影响环境、环境反馈任务、任务再触发设备
  -> 最后才是：为了评估效率，哪些地方允许加速或跳跃
```

这也是这份文档的组织顺序。

---

## 二、核心理念：逻辑时间而非真实时间

SimuHome 的时间系统**不是 1:1 真实时间对应**。模拟器的设计目标不是复刻“真实等待体验”，而是验证 Agent 能否在**正确的时间点**执行**正确的操作**。

因此它使用的是：

- **逻辑时间**
- **离散 Tick**
- **可控推进**

论文原文里有两个表述很能说明这一点：

> *"the simulator accelerates time so that scheduled workflows can be evaluated immediately."*

> *"SimuHome runs in sync with real time by default, but supports time acceleration to quickly reach any future point in the simulation."*

换句话说，SimuHome 真正在乎的不是“5 分钟必须等 5 分钟”，而是：

```text
如果某个任务应该在 5 分钟后触发，
那么当仿真时间到达那个点时，
系统是否会在正确的状态下触发正确的行为。
```

---

## 三、时间机制如何服务整体流程

### 3.1 整体链路

把时间机制放回整个模拟流程里看，最关键的是下面这条链：

```text
Agent / API 请求
  -> 进入 Home 的统一主循环
  -> 在某个 Tick 内被处理
  -> 改变设备状态
  -> 后续 Tick 中驱动环境聚合器重算
  -> 时间到达时触发调度工作流
  -> 再次改变设备与环境状态
```

也就是说，时间机制不是只服务“定时任务”，而是服务以下所有事情的统一编排：

- 设备何时更新内部状态
- 环境何时根据设备状态重算
- 调度任务何时到期触发
- Agent 发来的请求何时真正生效

如果没有这套统一时间轴，SimuHome 里的这些行为就会变成互相割裂的即时调用，很难验证“先后顺序”和“延迟影响”。

### 3.2 为什么时间是主流程的胶水

SimuHome 里至少有三类变化，它们必须被串起来：

1. **设备内部变化**
   例如窗帘逐 Tick 运动、亮度逐 Tick 变化、设备执行状态推进。
2. **环境变量变化**
   例如空调开启后，房间温度不是瞬时跳变，而是在后续 Tick 中持续下降。
3. **任务时序变化**
   例如 “5 分钟后关灯” 或 “18:30 启动洗碗机” 这种 workflow，需要在未来某个时间点自动触发。

时间机制的作用，就是把这三类变化都放进同一个可验证的因果顺序里。

## 四、先用几个例子建立直觉

如果只看抽象描述，时间机制很容易被理解成“一个时钟系统”。但对 SimuHome 来说，更好的理解方式是：它在不同任务里负责维持不同类型的时间语义。下面用四个短例子先把这个直觉立起来。

### 4.1 例子 A：立即开灯，不等于环境反馈也立即完成

假设 Agent 发出一条“现在打开客厅灯”的命令。

在 SimuHome 里，这件事不是一句话发出去就把所有结果同时改完，而更像下面这条链：

```text
Agent 发出开灯命令
  -> 命令进入 API 队列
  -> 当前或下一轮 Tick 的 API 阶段执行该命令
  -> 灯的设备状态变成 ON
  -> 后续 Tick 中照度聚合器读取到这个新状态
  -> 客厅 illuminance 开始上升
```

这个例子说明了一点：

```text
设备动作的生效
不等于
环境结果的立刻完成
```

也正因为这样，时间机制必须把“命令处理”和“环境反馈”串成前后两步，而不是一次性同步改完。

### 4.2 例子 B：空调降温是持续过程，不是瞬时跳变

假设当前客厅温度是 `28°C`，Agent 想把空调打开并设置成制冷 `24°C`。

在 SimuHome 里，更合理的时间语义不是：

```text
命令一执行
  -> 房间温度立刻从 28 变成 24
```

而是：

```text
第 1 步：空调状态变为 ON，模式切到 COOL
第 2 步：温度聚合器识别到空调正在持续施加冷却 effect
第 3 步：后续多个 Tick 中，房间温度逐步下降
第 4 步：设备上的温度读数也随之更新
```

这个例子说明，时间机制不仅服务“定时触发”，还服务**连续演化过程**。  
如果没有 Tick 推进，像空调降温、加湿器增湿、空气净化器降低 PM10 这种效果就只能被粗暴地写成瞬时赋值。

### 4.3 例子 C：5 分钟后关灯，本质是“现在注册，未来触发”

假设用户说：“5 分钟后把卧室灯关掉。”

Agent 的处理思路通常是：

```text
先读当前虚拟时间
  -> 算出 5 分钟后的绝对时间
  -> 注册一个 future workflow
  -> workflow 被换算成某个 due_tick
  -> 时间推进到该 due_tick 时自动执行关灯
```

这说明 SimuHome 的时间机制支持的是：

```text
现在这个时刻做出一个未来承诺，
然后在未来的正确时间点兑现它。
```

也就是说，时间机制在这里服务的是**任务生命周期管理**，而不是单纯的 sleep 或 delay。

### 4.4 例子 D：洗衣机运行完成，不只是“到了时间”，还要看中间状态

假设一个设备本身就有持续时间过程，比如洗衣机、洗碗机、窗帘电机。

以洗碗机为例，合理的模拟不是：

```text
启动洗碗机
  -> 等 40 分钟
  -> 直接从 running 变成 finished
```

而是更接近：

```text
启动后先进入某个运行阶段
  -> 中间 Tick 中设备内部状态持续推进
  -> 必要时切换 phase / mode / progress
  -> 到达结束条件时再进入 finished
```

这个例子强调的是：  
时间机制不仅服务“外部任务调度”，也服务**设备内部过程建模**。

## 五、基础：Tick 离散时间框架

时间系统核心实现在 [home.py](/d:/D_coderesource/simuhome/simuprocject/Simuhome_experiment/src/simulator/domain/home.py)。

### 4.1 Tick 的定义

```python
# home.py L23-27
self.tick_interval = tick_interval  # 默认 0.1 秒
self.current_tick = 0
```

- **1 Tick = 0.1 秒**，默认可配置
- Tick 是**逻辑时间单位**，不是现实世界里的强制等待单位
- 所有关键状态推进都在 Tick 边界上发生

这一点非常重要。SimuHome 不是连续时间系统，而是一个：

```text
每次前进一步，
就把设备、环境、调度、API 统一处理一轮
```

的离散时间系统。

### 4.2 虚拟时间公式

```text
虚拟时间 = 基准时间(base_time) + current_tick × tick_interval
```

代码对应：

```python
# home.py L635-642
def get_virtual_now_seconds(self) -> float:
    return self.virtual_offset_seconds + (
        float(self.current_tick) * float(self.tick_interval)
    )

def get_virtual_now_str(self) -> str:
    now_s = self.get_virtual_now_seconds()
    base_dt = datetime.fromtimestamp(self.virtual_epoch_seconds)
    now_dt = base_dt + timedelta(seconds=now_s)
    return now_dt.strftime("%Y-%m-%d %H:%M:%S")
```

这意味着 SimuHome 里的“现在几点”，不是从系统时钟直接读出来的，而是由：

- `base_time`
- `current_tick`
- `tick_interval`

共同计算出来的虚拟时间。

### 4.3 关键参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `base_time` | `"2025-08-23 00:00:00"` | 虚拟世界的基准时间起点 |
| `tick_interval` | `0.1` | 每个 Tick 代表多少虚拟秒 |
| `fast_forward` | `False` | 是否跳过真实等待 |
| `max_ticks` | `None` | 仿真运行上限 |

### 4.4 确定性保证

因为 Tick 是离散且确定的，给定相同 `seed`、`base_time` 和配置，时间推进路径就可以复现。  
这也是它适合做 Agent benchmark 的原因之一：同一个输入可以在同一套时间轴上反复验证。

## 六、主流程视角：一个 Tick 到底服务了什么

主循环 [`__simulation_loop`](file:///d:/D_coderesource/simuhome/simuprocject/Simuhome_experiment/src/simulator/domain/home.py#L167) 是时间机制真正落地的地方：

```python
def __simulation_loop(self):
    try:
        while self.is_running:
            tick_start = time.perf_counter()

            self.__process_time_aware_devices()
            self.__process_aggregators()
            self.__process_schedular_queue()
            self.__process_api_queue()

            elapsed = time.perf_counter() - tick_start
            if not self.fast_forward and elapsed < self.tick_interval \
               and not self._skip_sleep_once:
                time.sleep(self.tick_interval - elapsed)

            self.current_tick += 1
    except Exception as error:
        ...
```

### 5.1 每个 Tick 的执行顺序

每个 Tick 内部按顺序做四件事：

1. **处理时间感知设备**
   调用时间相关设备的 `on_time_tick()`，推进设备自己的内部过程。
2. **处理环境聚合器**
   根据当前设备状态，重算温度、湿度、照度、PM10 等环境量。
3. **处理调度队列**
   检查是否有 workflow 到期，需要在当前时间点触发。
4. **处理 API 请求**
   执行 Agent 在这个阶段提交的命令或属性写入。

### 5.2 这个顺序为什么重要

这个顺序本身就是“时间如何服务整体流程”的核心。

它表达的是下面这层语义：

```text
先推进已有状态
  -> 再据此重算环境
  -> 再检查是否到了该触发任务的时候
  -> 最后处理这一轮新进来的控制请求
```

这带来两个很重要的性质：

1. **环境变化不是命令发出瞬间立即完成**
   设备命令生效后，环境通常是在后续 Tick 中逐步反映出来。
2. **定时任务和即时命令共享同一条时间轴**
   它们不是两套独立系统，而是在同一个主循环里被验证。

## 七、再用两个流程例子把 Tick 主循环讲透

### 7.1 例子 E：为什么“本 Tick 发命令，下 Tick 才看到环境变化”是合理的

假设当前某一轮 Tick 已经开始执行，此时 Agent 提交了一条“打开空气净化器”的请求。

这轮 Tick 的顺序是：

```text
先处理 time-aware 设备
  -> 再处理环境聚合器
  -> 再处理调度队列
  -> 最后处理 API 请求
```

因此在这一轮里，净化器命令可能在最后阶段才被落地。这样一来：

```text
这一轮结束时
  -> 设备状态已经更新
但
  -> PM10 聚合器通常还没来得及据此重算
```

所以更常见的情况是：

- 这一轮把设备状态改对
- 下一轮开始时，环境聚合器才读到这个新状态
- 然后 PM10 开始下降

这个例子非常适合用来解释：  
SimuHome 为什么不是“API 一调，环境立刻全改”。

### 7.2 例子 F：为什么定时任务和即时命令必须共用同一个主循环

假设有两个动作同时存在：

1. 用户现在手动打开客厅灯
2. 系统里原本注册了一个 “2 分钟后关闭客厅灯” 的 workflow

如果这两类动作是两套彼此独立的时间系统，就很容易出现语义混乱：

- 当前命令在哪个时间点生效
- 定时关闭读到的是哪一版设备状态
- 谁先谁后无法统一判断

但在 SimuHome 里，它们共用同一套 Tick 主循环，于是逻辑变成：

```text
当前命令在某个 Tick 的 API 阶段生效
  -> 设备随后处于 ON 状态
  -> 时间继续推进
  -> 到 due_tick 时，调度队列触发关闭 workflow
  -> 灯再变回 OFF
```

这说明时间机制真正保障的是：

```text
所有动作都在同一条时间线上排序
```

## 八、Agent 视角：时间机制如何支撑完整任务流程

如果从 Agent 使用系统的角度看，时间机制至少支持两类任务：

1. **立即任务**
   例如“打开空调”“把客厅灯亮度调到 50%”
2. **未来任务**
   例如“5 分钟后关灯”“今晚 18:30 启动洗碗机”

这两类任务之所以能在同一系统里统一处理，是因为 Agent 操作的不是“真实世界时间”，而是**虚拟时间**。

### 6.1 Agent 能感知和操作哪些时间能力

| 工具 | 作用 |
|------|------|
| `get_current_time` | 获取当前虚拟时间 |
| `schedule_workflow(start_time, steps)` | 注册未来执行的工作流 |
| `run_workflow_now(steps)` | 立即执行一组命令 |
| `get_workflow_status` | 查询已调度工作流状态 |

### 6.2 一条典型的时间驱动任务链

以 “5 分钟后关灯” 为例：

```text
Agent 收到请求
  -> 调用 get_current_time() 读到当前虚拟时间
  -> 计算目标时间
  -> 调用 schedule_workflow(...) 注册未来任务
  -> 模拟器把它换算为 due_tick 放入调度队列
  -> 时间推进到该 Tick
  -> workflow 被自动触发
  -> 最终 home state 被拿来验证
```

这里真正关键的不是 “是否支持 schedule API”，而是：

```text
系统是否能在统一时间轴上，
把“现在注册”和“未来执行”连接起来。
```

## 九、为什么还需要加速、减速、跳跃机制

当整体流程理顺之后，再看加速机制就容易多了。

加速机制不是独立目标，而是为了解决下面这个评估问题：

```text
既要保留时间驱动的正确性，
又不能真的等 5 分钟、等 1 小时、等一整晚。
```

所以 SimuHome 需要几种不同层次的时间推进手段：

- 有时需要**逐 Tick 快速跑**，保留全过程
- 有时需要**直接跳到未来某个点**
- 有时需要**当前就把一组动作执行完**
- 有时需要**先注册未来任务，等时间到再触发**

这四种处理方式，本质上分别服务不同的验证场景。

## 十、四种时间加速/跳跃处理方式

### 8.1 `fast_forward=True`：逐 Tick 快速跑，但不等待真实时间

| 属性 | 值 |
|------|-----|
| 触发方式 | `Home(fast_forward=True)` |
| 核心效果 | 跳过 `time.sleep()` |
| 语义 | 仍然逐 Tick 执行，只是不与真实时间同步 |

关键点在于：

- 它**不跳过 Tick**
- 它**不跳过设备更新**
- 它**不跳过环境聚合**

它做的只是把：

```text
每 Tick 处理一次 + 每 Tick 真实等待一次
```

变成：

```text
每 Tick 处理一次 + 不等待
```

所以这适合需要保留完整动态过程的场景，比如环境量渐变、设备逐步过渡等。

**对应例子：**

- 看空调把房间从 `28°C` 缓慢降到 `24°C`
- 看灯光亮度或窗帘位置逐 Tick 渐变
- 看洗衣机、洗碗机中间 phase 如何变化

### 8.2 `_fast_forward_to(to_tick)`：跳到目标时间点

| 属性 | 值 |
|------|-----|
| 触发方式 | API `POST /api/simulation/fast_forward_to` |
| 核心效果 | 从当前 Tick 跳到目标 Tick |
| 语义 | 在“批量推进”和“逐 Tick 精确推进”之间切换 |

这是最核心的跳跃机制。它不是无脑瞬移，而是根据中间有没有关键事件决定推进策略。

算法逻辑可以概括成：

1. 看下一个调度事件离当前有多远
2. 如果事件还很远，并且中间没有不能跳过的设备工作
   则采用**批量推进**
3. 如果快到关键事件点
   则切回**逐 Tick 精确推进**
4. 到达事件点后触发 workflow，再继续往后推进

也就是说，它的设计重点不是“快”，而是：

```text
在不破坏关键时间语义的前提下尽量快
```

**对应例子：**

- 用户说“今晚 18:30 开启洗碗机”，评估时不想真的等到晚上
- 注册了“2 小时后关闭加湿器”的任务，想直接跳到触发点附近验证
- 想看未来某个时间点的最终 home state，而不关心中间每一秒的等待体验

### 8.3 `run_workflow_now`：立即执行，不额外等待下一轮

| 属性 | 值 |
|------|-----|
| 触发方式 | API `POST /api/schedule/run_workflow_now` |
| 核心效果 | 立即执行一组命令 |
| 语义 | 面向“现在就做”的动作编排 |

这里的关键不是“快进到未来”，而是：

```text
我不是要等未来某个时间点，
而是要在当前时刻把一个动作序列立刻落地。
```

它通过 `_skip_sleep_once` 让主循环在当前阶段不额外等待，从而让即时 workflow 更像“当前上下文内立刻执行”。

**对应例子：**

- 一键执行“回家模式”：开灯、开空调、拉开窗帘
- 一键执行“睡眠模式”：关主灯、关电视、把空调设到夜间温度

### 8.4 `schedule_workflow`：先注册未来动作，再等时间到触发

| 属性 | 值 |
|------|-----|
| 触发方式 | API `POST /api/schedule/workflow` |
| 核心效果 | 将绝对时间转换成 `due_tick` 放入调度队列 |
| 语义 | 面向“未来执行”的任务注册 |

它负责把 Agent 给出的自然时间表达映射到模拟器内部时间轴上：

```python
base_dt = datetime.fromtimestamp(self.virtual_epoch_seconds)
start_dt = datetime.strptime(start_time, "%Y-%m-%d %H:%M:%S")
start_s = (start_dt - base_dt).total_seconds()
due_tick = ceil((start_s - self.virtual_offset_seconds) / self.tick_interval)
```

这个机制本身不负责“加速”，它负责的是：

```text
把未来动作接入统一时间轴
```

随后它通常会和 `fast_forward_to()` 或评估流程中的统一快进一起配合，完成最终验证。

**对应例子：**

- “5 分钟后关灯”
- “明早 07:00 打开卧室窗帘”
- “晚饭后 30 分钟启动洗碗机”

## 十一、再给一组‘机制和例子一一对应’的速查表

如果读者更习惯通过例子记忆，可以把前面的机制直接映射成下面这张表：

| 例子 | 最关键的时间语义 | 最对应的机制 |
|------|------------------|--------------|
| 打开客厅灯后，照度不是同一瞬间就完成变化 | 命令与环境反馈分阶段发生 | Tick 主循环 |

| 5 分钟后关灯 | 现在注册，未来触发 | `schedule_workflow` |
| 直接验证“未来某个定时动作有没有发生” | 快速到达关键时点 | `_fast_forward_to()` |

```text
每一种时间机制背后，
其实都对应一种具体的智能家居任务语义。
```

## 十二、四种处理方式之间的关系

如果把这四种机制放回整体流程里看，它们并不是并列的“技巧清单”，而是对应不同层次的问题：

| 机制 | 解决的问题 | 是否逐 Tick | 典型场景 |
|------|------------|-------------|----------|
| `fast_forward=True` | 不想真实等待，但要保留全过程 | 是 | 连续环境变化验证 |
| `_fast_forward_to()` | 要快速到达未来关键时间点 | 混合 | 定时任务、未来状态验证 |
| `run_workflow_now` | 要在当前上下文立刻执行一组动作 | 近似当前 Tick 内完成 | 即时 workflow |
| `schedule_workflow` | 要把未来动作注册到时间轴上 | 不直接推进 | 定时任务注册 |

这样看会更清楚：

- `schedule_workflow` 负责**把未来任务挂上时间轴**
- `_fast_forward_to()` 负责**让仿真高效到达那个时间点**
- `fast_forward=True` 负责**逐 Tick 快速跑完整过程**
- `run_workflow_now` 负责**当前动作立刻落地**

## 十三、一个更顺的理解顺序

如果以后要向别人解释 SimuHome 的时间机制，建议按下面这个顺序讲：

1. SimuHome 用的是**逻辑时间**，不是 1:1 真实时间。
2. 逻辑时间以 **Tick** 为单位推进。
3. 每个 Tick 都统一处理：
   设备更新、环境更新、调度触发、API 请求。
4. 因此时间机制服务的是整个模拟主流程，而不只是定时任务。
5. 在这个基础上，才需要引入不同层次的加速和跳跃机制，提高评估效率。

这样读者先看到的是：

```text
时间如何维持系统因果顺序
```

而不是一上来就只看到：

```text
系统有哪些快进按钮
```

## 十四、结论

这份时间机制的核心，不是“SimuHome 可以快进”，而是：

```text
SimuHome 先用统一的 Tick 时间轴把设备、环境、调度、Agent 交互组织成一条完整流程，
然后才在这条流程之上提供不同粒度的加速和跳跃能力，
从而既保证时间语义正确，又保证评估效率可接受。
```

所以写作上也应该遵循同样的顺序：

- 先讲时间如何服务整体流程
- 再讲加速/减速/跳跃机制
- 最后再讲不同机制分别适合什么评估场景
