# SimuHome Benchmark QT（Query Type）分类说明

> SimuHome 的 benchmark 将测试用例按**查询类型（Query Type, QT）** 划分为 6 大类，每个 QT 代表一种**能力维度**，用于精细化评测 LLM Agent 在智能家居场景中的不同能力层次。

---

## 概述

所有 QT 又进一步分为两种**可行性**（Case）：

| 可行性 | 含义 | 数量 |
|:-----:|------|:---:|
| **Feasible（可行）** | 用户请求在逻辑上可以完成 | 每种 QT 各 50 条 |
| **Infeasible（不可行）** | 用户请求存在矛盾或无法完成 | 每种 QT 各 50 条 |

Infeasible 用例用于测试 Agent **能否识别任务不可行并及时告知用户**，而不是盲目执行。

---

## QT1：基础信息查询

> 测试 Agent 的**信息检索与问答能力**

### 问题本质

用户对当前家居状态有疑问，Agent 需要查询设备属性或房间环境状态，然后**仅回答问题，不执行任何操作**。

### 需要的能力

- 识别用户想查询哪个设备/哪个房间
- 调用 `get_room_devices` / `get_room_states` 获取信息
- 从观测结果中提取关键数值并回答

### 示例

> "我正在考虑洗衣服和快速清洗，洗衣房的照明现在有多亮，浴室现在感觉有点暗还是光线很好？"

### Feasible 与 Infeasible 的区别

| Feasible | Infeasible |
|:--------:|:----------:|
| 查询的目标设备和房间都存在，信息可以获取 | 查询的设备不存在于指定房间，Agent 应识别并告知用户设备不存在 |

### 难度

- 准确率最高的一类，当前模型约 **74%**
- 平均只需 3~4 步动作即可完成

---

## QT2：环境控制（因果推理）

> 测试 Agent 的**设备→环境因果推理能力**

### 问题本质

用户对环境状态（温度、湿度、照度、空气质量）感到不适，Agent 需要**推理出哪种设备能改变该环境指标**，并操作设备。

### 需要的能力

- 理解环境指标与设备类型的对应关系：

| 环境指标 | 影响设备 | 可调节方向 |
|:-------:|---------|:---------:|
| 温度 | 空调（降温）、热泵（升温） | 升降 |
| 湿度 | 加湿器（增湿）、除湿机（除湿） | 升降 |
| 照度 | 开关灯、可调光灯 | 升降 |
| PM10 | 空气净化器 | 仅降低 |

- 执行设备控制命令（开关、调档等）
- 验证设备是否已生效

### 示例

> "我刚从外面回来，客厅感觉有点闷热，能帮忙让客厅凉快一些吗？"

### Feasible 与 Infeasible 的区别

| Feasible | Infeasible |
|:--------:|:----------:|
| 房间内有对应的环境调节设备（如空调可降温），操作后可以达成目标 | 房间内缺少必要的设备，或现有设备的状态已无法进一步调节（如空调已开到最大制冷但温度还不够低） |

### 难度

- 中等难度，当前模型约 **49%**
- 需要理解物理世界中的因果关系，而不是简单的 API 调用

---

## QT3：多步设备配置

> 测试 Agent 的**多设备操作与参数配置能力**

### 问题本质

用户需要同时对**多个设备**进行**参数设置**（如模式选择、档位调节），涉及多个步骤。

### 需要的能力

- 理解复杂设备的属性层次（如洗衣机的模式、水温、转速）
- 按顺序完成多步配置操作
- 管理跨多个房间的设备操作

### 示例

> "我想洗衣服，请帮我把洗衣机设成轻柔模式，并且把烘干机设成强力烘干。"

### 关键设备与可配置参数

| 设备类型 | 可配置参数 |
|---------|-----------|
| 洗衣机 | 洗涤模式（标准/轻柔/强力等）、水温、转速 |
| 烘干机 | 干燥程度（标准/强力/节能等） |
| 洗碗机 | 清洗模式 |
| 扫地机器人 | 清洁模式 |

### Feasible 与 Infeasible 的区别

| Feasible | Infeasible |
|:--------:|:----------:|
| 请求的设备操作都是合理且可执行的 | 请求的操作与设备能力不匹配（如不存在的模式），或设备状态不允许 |

### 难度

- 当前模型表现最好的一类，约 **78%**
- 步骤数约 5~7 步

---

## QT4 系列：时间协同推理

> 这是 SimuHome 最具区分度的难点，测试 Agent 在**时间维度上的推理能力**

QT4 引入了 **OP 设备**（Operational State Device）的概念——即**拥有运行周期**的设备：

- 洗衣机、烘干机、洗碗机、扫地机器人
- 这些设备有运行状态：`STOPPED`（已停止）、`RUNNING`（运行中）、`PAUSED`（已暂停）
- 设备有自己的运行周期时长（如洗衣机标准模式需 60 分钟）

QT4 系列按"时间约束的复杂度"进一步分为三个子类：

---

### QT4-1：绝对时间调度（非 OP 设备）

> 测试 Agent 的**定时任务执行能力**

#### 问题本质

用户要求在未来某个**绝对时间点**（如"5 分钟后"、"15 分钟后"）控制**普通设备**（灯光、空调等非 OP 设备），可能包含**多个按序执行的定时操作**。

#### 需要的能力

- 使用 `schedule_workflow` 工具进行定时调度
- 多个定时操作之间的时间顺序管理
- 理解绝对时间（相对当前时刻的偏移）

#### 示例

> "我在客厅看书，5 分钟后帮我把阅读灯调到 70% 亮度，再过 10 分钟后关掉。"

#### Feasible vs Infeasible

| Feasible | Infeasible |
|:--------:|:----------:|
| 调度时间合理，设备可被控制到目标状态 | 时间错位——要求的执行时间与可用时间不可调和（如要求的"5 分钟后"实际上已过期） |

#### 难度

- 当前模型较低，约 **27%**
- 动作数约 6~8 步

---

### QT4-2：OP 设备锚点 + 非 OP 目标

> 测试 Agent 的**相对时间推理能力**

#### 问题本质

以**正在运行的 OP 设备完成时刻**为时间锚点，在其前后相对偏移 N 分钟来控制其他**非 OP 设备**。

#### 需要的能力

- 获取正在运行的 OP 设备的剩余时间
- 计算锚点完成时间
- 基于锚点的相对时间调度

#### 示例

> "洗衣机还有 30 分钟洗完，帮我设成洗衣机洗完 10 分钟后打开烘干机，记得把烘干机设成强力模式。"

#### Feasible vs Infeasible

| Feasible | Infeasible |
|:--------:|:----------:|
| 锚点设备正常运行，偏移时间合理 | 偏移时间导致矛盾（如洗衣机还没洗完但要求提前 20 分钟启动其他设备） |

#### 关键代码参考

锚点设备通过 `sample_op_device(sample_running_anchor=True)` 选取——即有正数倒计时且正在运行的 OP 设备。

#### 难度

- 当前模型约 **43%**
- 比 QT4-1 简单一些，因为"相对时间"更贴近实际生活场景

---

### QT4-3：OP 设备锚点 + OP 设备目标（双设备协同）

> 测试 Agent 的最复杂的**多设备周期对齐推理能力**

#### 问题本质

**两个 OP 设备**之间需要协同工作，而它们各自都有运行周期。Agent 需要规划好时间，使两个设备的**运行周期对齐**。

#### 三种子场景

| 子场景 | 含义 | 示例 |
|:------:|------|------|
| **pause_at_anchor_end** | 启动目标设备，锚点完成时暂停它 | "启动洗碗机，等洗衣机洗完就把洗碗机暂停" |
| **delayed_start** | 锚点完成后延迟 N 分钟再启动目标 | "洗衣机洗完等 15 分钟后，再启动烘干机" |
| **align_end_with_anchor** | 让目标设备与锚点同时结束 | "让烘干机和洗衣机同时洗完" |

#### 需要的能力

- 获取两个 OP 设备的运行周期时长
- 计算周期对齐方案（谁先启动、何时暂停/启动）
- 使用 `schedule_workflow` 进行精确的时间调度
- 知道如何暂停设备（`Pause` 命令）

#### Feasible vs Infeasible

| Feasible | Infeasible |
|:--------:|:----------:|
| 两个设备的运行周期可以协调对齐 | 四种冲突类型：<br>1. **绝对时间错位**—指定的时间不可能<br>2. **完成vs暂停冲突**—既要完成又要暂停的矛盾<br>3. **延迟时间冲突**—等待时间不可行<br>4. **不可能提前结束**—目标设备周期太长，无法在锚点结束前完成 |

#### 难度

- 当前模型可行约 **65%**，不可行仅 **11%**
- 这是整个 benchmark 中最难的类别
- Feasible 相对好一些，但 Infeasible 极其困难——说明 Agent 几乎无法识别"双设备周期无法对齐"的矛盾

---

## 整体难度阶梯

```
能力维度递进：

QT1           ─ 信息检索（最基础）
  └→ QT2      ─ 环境因果推理（增加物理世界理解）
    └→ QT3    ─ 多步设备配置（增加操作复杂度）
      └→ QT4  ─ 时间推理（增加时间维度）
          ├─ QT4-1  绝对时间调度
          ├─ QT4-2  相对锚点调度
          └─ QT4-3  双周期对齐（最难）
```

## 实验准确率对比

| 类别 | 综合准确率 | 平均动作数 | 平均耗时 |
|:----:|:--------:|:--------:|:-------:|
| QT1 | 73.7% | 3.4 | 8.9s |
| QT2 | 48.8% | 6.7 | 17.4s |
| QT3 | 77.5% | 5.7 | 15.4s |
| QT4-1 | 27.4% | 6.0 | 23.4s |
| QT4-2 | 43.2% | 7.5 | 33.3s |
| QT4-3 | 39.5% | 8.0 | 33.8s |

> 数据来源：基于 deepseek-v4-flash + ReAct 策略的实验报告

## 各 QT 评价维度总结

| QT | 核心能力 | 关键工具 | 时间维度 | 设备类型 |
|:--:|---------|---------|:-------:|:-------:|
| 1 | 信息检索与问答 | 查询类工具 | 无 | 任意 |
| 2 | 因果推理（设备→环境） | 设备控制 + 环境查询 | 无 | 环境调节设备 |
| 3 | 多步配置操作 | 设备控制 | 无 | 任意，含复杂模式 |
| 4-1 | 绝对时间调度 | schedule_workflow | 绝对时间 | 非 OP 设备 |
| 4-2 | 相对锚点调度 | schedule_workflow | 相对锚点 | 锚点 OP + 目标 非OP |
| 4-3 | 双周期对齐 | schedule_workflow + pause | 双周期对齐 | 锚点 OP + 目标 OP |
