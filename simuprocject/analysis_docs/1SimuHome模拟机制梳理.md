# SimuHome 模拟机制梳理

## 1. 先给结论

如果把 SimuHome 压缩成一句话，它本质上是一个：

```text
按房间组织环境状态
    + 按 Matter 风格组织设备能力
    + 按 tick 推进状态演化
    + 用聚合器把设备状态翻译成环境变化
    + 用 workflow / fast-forward 支持时间任务验证
```

它不是一个高精度物理仿真器，也不是完整 Matter 协议栈模拟器。  
它更像一个**离散时间的智能家居语义模拟器**：

- 时间是离散的
- 设备能力是结构化的
- 环境反馈是持续的
- 调度任务是可验证的

这也是论文里强调的三件事：

```text
1. 设备操作存在依赖关系
2. 设备会持续影响环境变量
3. 可以注册未来任务并把时间快速推进过去验证结果
```

---

## 2. 整体层次

最容易看懂这套系统的方法，不是先盯代码文件，而是先看层次。

```text
+------------------------------------------------------+
| Agent / API Layer                                    |
| execute_command / write_attribute / schedule_workflow|
+------------------------------+-----------------------+
                               |
                               v
+------------------------------------------------------+
| Home Simulation Loop                                 |
| tick -> devices -> aggregators -> scheduler -> api   |
+------------------------------+-----------------------+
                               |
          +--------------------+--------------------+
          |                                         |
          v                                         v
+-----------------------------+      +-------------------------------+
| Device Layer                |      | Environment Layer             |
| Device -> Endpoint ->       |      | room -> temperature           |
| Cluster -> attribute/command|      |      -> humidity              |
|                             |      |      -> illuminance           |
|                             |      |      -> pm10                  |
+-----------------------------+      +-------------------------------+
          |                                         ^
          |                                         |
          +------------- state / effect ------------+
```

这个图里最重要的是中间那一层 `Home Simulation Loop`。  
SimuHome 的核心不在某一个设备类，也不在某一个聚合器类，而在于：

- 所有设备状态变化
- 所有环境状态更新
- 所有调度任务触发

都被收束进一个统一的 tick 驱动循环里。

---

## 3. 一次 tick 内到底发生什么

从核心逻辑上看，一个 tick 做的事情可以总结成下面这条链：

```text
Tick Start
   |
   v
[1] 推进 time-aware 设备内部状态
   |
   v
[2] 根据设备当前状态更新房间环境量
   |
   v
[3] 检查有没有到点的 workflow
   |
   v
[4] 处理本轮进入队列的 API 请求
   |
   v
[5] tick + 1
```

这条链意味着一个非常关键的建模选择：

```text
环境不是在“命令发出那一刻”立刻变化，
而是在后续 tick 中，根据设备的新状态逐步演化。
```

所以在 SimuHome 里，一条控制命令会带来三类后果：

```text
命令成功
  -> 设备状态变了
     -> 聚合器下一轮读到新状态
        -> 房间环境开始变化
```

这三步不是同一件事，而是三层不同的结果。

## 4. 房间为什么是环境计算的基本单位

论文里说得很明确：一个 home 由多个 room 构成，每个 room 有四个环境变量。  
代码实现也完全沿用了这个思路。

可以直接把它理解成：

```text
Home
├─ living_room
│  ├─ devices
│  ├─ temperature
│  ├─ humidity
│  ├─ illuminance
│  └─ pm10
├─ kitchen
│  ├─ devices
│  ├─ temperature
│  ├─ humidity
│  ├─ illuminance
│  └─ pm10
└─ bedroom
   ├─ devices
   ├─ temperature
   ├─ humidity
   ├─ illuminance
   └─ pm10
```

这意味着：

```text
客厅空调默认影响客厅温度
而不是整套房子的统一温度
```

这也是当前实现和真实物理世界之间的一个重要简化点：

```text
当前主实现里，房间之间基本是解耦的；
没有明显的跨房间热传导、光照泄露或空气扩散模型。
```

所以理解 SimuHome 时，不要把它想成一个“整屋连续物理空间”，而是想成：

```text
多个相互独立的房间状态容器
+ 每个房间里有设备
+ 每个房间里有环境变量
+ 设备只影响自己所在房间的环境
```

## 5. Matter 在这里扮演什么角色

这个问题特别容易理解偏。

SimuHome 里的 Matter，不是指它在模拟：

- 真实设备配网
- 底层网络发现
- 真正的 Matter 报文收发
- Fabric / session / commissioning

它真正采用的是 Matter 的**能力组织方式**。

可以画成这样：

```text
Device
  └─ Endpoint
      └─ Cluster
          ├─ Attributes
          └─ Commands
```

例如空调不是一个“大类里面塞所有字段”，而是：

```text
air_conditioner
  └─ endpoint 1
      ├─ OnOff
      ├─ Thermostat
      └─ FanControl
```

所以，这个项目里的 “遵循 Matter” 更准确地说是：

```text
遵循 Matter 的应用层能力抽象
而不是完整复现 Matter 协议栈
```

因此一条命令是否“符合 Matter”，在这里通常意味着：

```text
endpoint 对
cluster 对
command / attribute 对
参数形式对
参数值满足约束
当前设备状态允许执行
```

如果满足这些，它就算一个合法的 Matter 风格控制操作。

## 6. 设备是怎么被模拟的

设备这层可以用一句话概括：

```text
设备 = Matter 风格能力容器
```

但这个概括还不够，因为它还少了一层关键内容：**设备级约束**。

更准确的结构是：

```text
Device
├─ cluster 级能力
├─ cluster 级属性
├─ cluster 级命令
└─ device 级前置条件 / 依赖规则
```

例如空调、风扇、加湿器这类设备，并不是“只要写属性就生效”，而是通常要先满足：

```text
先开机
再切模式
再改 setpoint / 风速
```

也就是说，设备层做的不是纯粹的字段存储，而是：

```text
把“什么能力存在”交给 cluster
把“哪些动作必须按顺序来”交给 device
```

这是论文里“operational dependencies”在代码层的真正落地方式。

## 7. 环境量不是设备自己算，而是聚合器统一算

这是 SimuHome 最核心的一层设计。

不要把系统想成：

```text
空调自己维护 room_temperature
灯自己维护 room_illuminance
加湿器自己维护 room_humidity
```

实际不是这样。  
真正的结构是：

```text
设备只维护自己的状态
        |
        v
聚合器读取设备状态
        |
        v
聚合器统一计算房间环境量
```

换句话说：

```text
设备负责“我现在是什么状态”
聚合器负责“这种状态对房间环境意味着什么”
```

这个分层非常重要，因为它把：

- 设备控制语义
- 环境动力学语义

拆开了。

这使得同一个设备状态可以被不同环境逻辑解释，也让“环境变化是叠加效果”这件事更容易实现。

## 8. 温度、湿度、光照三种环境量的核心差别

这三个环境量都在做“设备状态 -> 房间环境”的映射，但它们不是同一种模型。

### 8.1 温度：持续效应模型

温度的核心逻辑是：

```text
设备如果处于有效工作状态
    -> 产生一个持续 effect
    -> 每个 tick 把这个 effect 加到当前温度上
    -> 然后再向 baseline 慢慢回归
```

所以温度是：

```text
连续效应叠加
+ 基线回归
```

这很好地对应了论文里那句：

```text
room temperature gradually decreases toward the target temperature
```

### 8.2 湿度：持续效应模型，但边界更明确

湿度和温度结构类似，也是：

```text
设备工作
  -> 产生持续增湿 / 除湿 effect
  -> effect 随风速和当前湿度区间变化
  -> 每个 tick 生效
  -> 再向 baseline 回归
```

但它还有一个额外特点：

```text
湿度值会被强制裁剪到有效区间
```

所以湿度模型比温度更像一个“带边界的持续调节系统”。

### 8.3 光照：直接重算模型

光照就不一样了。

它更接近：

```text
当前房间总光照
= baseline 光照
+ 所有灯具当前贡献之和
```

因此它不是“先积累 effect 再回归”的模型，而是：

```text
按当前灯状态直接重算结果
```

但这不意味着光照不能连续变化。  
如果调光灯本身的亮度是逐 tick 渐变的，那么光照聚合器每次读到的灯亮度都不同，于是房间光照也会呈现连续变化。

所以这里要分清：

```text
温度/湿度的连续性
    主要来自聚合器内部的 effect 模型

光照的连续性
    更多来自设备内部亮度状态本身的渐变
```

## 9. 传感器回写：环境不只是“外部状态”

论文里有一句很关键：

```text
Sensor attributes on devices ... are also updated to reflect current environmental variables
```

从设计上看，这意味着环境量在 SimuHome 里不是“只存在于房间对象外部”的。

更准确的链路应该画成：

```text
设备状态
   -> 聚合器计算环境
       -> 房间环境值更新
           -> 回写到设备传感器属性
               -> agent 后续再读取这些属性
```

这条回路让 agent 面对的不是静态世界，而是一个真正会“反馈回来”的系统。

但这里还有一个实现层面的区别需要明确：

```text
温度、湿度的传感器回写是明确实现了的
光照、PM10 的回写在当前代码里则明显更弱，甚至是空实现
```

所以如果你想用一句话评价当前实现：

```text
环境反馈闭环已经存在，
但闭环完整度在不同环境量上并不完全一致。
```

## 10. workflow 和 fast-forward 为什么重要

如果没有 workflow / fast-forward，这个项目就只是“会变化的环境”。  
但论文要评测的是更难的问题：

```text
现在不只是控制设备，
还要在未来某个时刻协调一串动作。
```

因此系统多了两层：

```text
schedule_workflow
   -> 把未来任务登记为 due_tick
   -> 不提前保证未来一定成功

fast_forward_to
   -> 把模拟时间推进到目标 tick
   -> 让未来任务真的执行
   -> 让环境变化真的被观测到
```

这部分最重要的建模选择，不是“它能调度”，而是：

```text
调度注册成功
!=
未来执行一定成功
```

这和现实智能家居平台非常接近，也正是论文为什么说 QT4 难的核心原因之一。

## 11. 一条完整因果链应该怎么理解

如果把这套系统中最核心的因果链压缩成一个图，我会这样画：

```text
Agent 产生结构化命令
        |
        v
API / Queue 接收命令
        |
        v
Device / Cluster 校验命令是否合法
        |
        v
设备内部状态更新
        |
        v
Aggregator 读取设备状态
        |
        v
房间环境值更新
        |
        v
环境值回写到传感器属性
        |
        v
Agent 下一轮再观察到新的世界状态
```

这条链揭示了 SimuHome 和很多静态 benchmark 的本质区别：

```text
它不是“给命令，判对错”
而是“给命令，改变世界，再观察世界有没有按预期变化”
```

## 12. 这套系统最值得把握的三个本质

### 本质一：它是“世界状态演化系统”，不是接口调用回放器

关键不是命令有没有发成功，而是：

```text
命令有没有让设备进入正确状态
设备状态有没有引发正确环境变化
环境变化有没有在后续时刻被观测到
```

### 本质二：它的 Matter 重点在能力语义，不在底层协议

关键不是“报文发出去没”，而是：

```text
这个设备有没有这个 cluster
这个 cluster 有没有这个 command / attribute
这个动作在当前状态下合不合法
```

### 本质三：它的环境模拟是“规则驱动连续近似”，不是精确物理

关键不是“真实世界热力学是否严谨”，而是：

```text
设备状态变化是否能稳定、持续、可重复地映射为环境反馈
```

这正好服务于论文的 benchmark 目标。

## 13. 用一句更成熟的话来总结

如果把这份文档收束成一句更完整、也更适合写在报告里的话，我会这样写：

```text
SimuHome 将智能家居环境抽象为“按房间组织的环境状态容器”，
将设备抽象为“按 Matter 风格组织的能力对象”，
再通过 tick 驱动的模拟主循环，把设备内部状态演化、房间环境更新、
未来任务执行和传感器反馈串成一个闭环。
```

再压缩一点，就是：

```text
它模拟的不是“设备接口”，
而是“设备接口如何改变一个会随时间演化的家庭环境”。
```

## 14. 你接下来最值得看的两个方向

如果你后面还想继续深入，而又不想掉进“逐文件讲实现”的细节里，我觉得最值得继续写的其实是两类“链路图”：

```text
1. 空调制冷链路
命令 -> 设备状态 -> 温度聚合 -> 房间降温 -> 传感器回写

2. workflow 调度链路
schedule -> due_tick -> fast_forward -> 到点执行 -> 环境验证
```

这两条链路基本就把 SimuHome 的静态结构和动态行为全串起来了。
